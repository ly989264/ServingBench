# 接口二（数据库接口 pd_diag_db/v1）规范

接口二由 ClickHouse 侧提供：入库进程（`pd_ingest.py`）把接口一读到的文档写进 ClickHouse 的库 `vllm_pd`。调用方是面板端：Grafana 数据源（看板的查询）和看板生成器（`generate.py`，按 `segment_def` 生成看板）。

本规范只固定表的结构和列的规则。当前有哪些段只记在 `segment_def` 的行里，面板端不自行推导列名。

同目录的文件：

| 文件 | 内容 |
|---|---|
| `schema.sql` | 建表语句：`request_doc` 的固定列、`status_doc`、`segment_def`、版本表 `db_interface`、视图 `request_json` |
| `SHA256SUMS` | 本规范和 `schema.sql` 的 SHA-256，发布脚本据此核对两端软件包中的副本相同 |

## 1. 接入参数

| 一方 | 参数 | 所在文件 | 说明 |
|---|---|---|---|
| 提供方 | `CLICKHOUSE_ADDR`、`CLICKHOUSE_HTTP_PORT` | `clickhouse.env` | ClickHouse 容器名或 IPv4 地址，以及映射到本机的 HTTP 端口 |
| 提供方 | `CH_READER_PASSWORD` | `clickhouse.env` | 只读账号 `vllm_reader` 的密码 |
| 调用方 | `CLICKHOUSE_ADDR`、`CLICKHOUSE_HTTP_PORT`、`CH_READER_PASSWORD` | `grafana.env` | 面板端连接 ClickHouse 的地址、端口和只读账号的密码。地址为容器名时端口为容器内的 8123，为 IPv4 地址时为映射到该机器的端口 |
| 调用方 | `DB_INTERFACE` | `grafana.env` | 调用方依赖的接口名称和主版本，随软件发布写为 `pd_diag_db/v1`，不需填写 |

## 2. 账号与权限

| 账号 | 使用方 | 权限 |
|---|---|---|
| `vllm_writer` | 入库进程 | `vllm_pd` 各表的 `SELECT`、`INSERT`；`request_doc` 的 `ALTER ADD COLUMN`；`system.columns`、`system.tables` 的 `SELECT` |
| `vllm_reader` | Grafana 数据源、看板生成器、诊断工具 | `vllm_pd` 各表的 `SELECT`；设置模板 `vllm_reader_profile`：单条查询最长 120 秒、内存上限 6 GB |

调用方只用 `vllm_reader`，不写入任何表。

## 3. 表

### 3.1 `request_doc`

一个请求的每个文档版本一行。列 `doc` 存接口一的请求文档原文，其余各列都由 `doc` 计算（`MATERIALIZED`），入库进程只写 `doc`。

- 引擎 `ReplacingMergeTree(doc_version)`，按 `ts` 的日期分区，`ORDER BY (cluster, request_id)`；保留 `SUMMARY_TTL_DAYS` 天（`clickhouse.env`，缺省 30）。
- 查询加 `FINAL`，取每个请求 `doc_version` 最大的一行。
- 判为 `complete`、`no_proxy` 的第一份 `doc_version` 为 1，判为 `incomplete`、`evicted` 的第一份为 0（接口一第 4.1 节）。采集进程已写出完整文档、又由迟到的记录为同一请求建出一份不完整文档时，后者的 `doc_version` 为 0，`FINAL` 仍取完整文档。

固定列（单位：时延为毫秒，时刻为 UTC 毫秒）：

| 列 | 类型 | 取自文档 |
|---|---|---|
| `doc` | String | 整份文档 |
| `schema`、`cluster`、`seq`、`doc_version`、`closed`、`request_id` | | 同名字段 |
| `ts` | DateTime64(3, 'UTC') | `ts`：请求到达的时刻 |
| `session_id`、`client_request_id` | Nullable(String) | 同名字段 |
| `model` | String | `model` |
| `route_p`、`route_d` | String | `route.p`、`route.d`，为空时为空串 |
| `retries` | Nullable(UInt8) | `route.retries` |
| `status`、`finish_reason` | String | `result.status`、`result.finish_reason`，为空时为空串 |
| `http_status` | Nullable(UInt16) | `result.http_status` |
| `prompt_tokens`、`cached_tokens`、`output_tokens` | Nullable(UInt32) | `tokens.prompt`、`tokens.cached`、`tokens.output` |
| `e2e_ms`、`ttft_ms`、`tpot_ms`、`p_total_ms`、`d_total_ms`、`retry_ms` | Nullable(Float64) | `latency_ms` 下的 `e2e`、`ttft`、`tpot`、`p_total`、`d_total`、`retry_ms` |
| `starts_at` | String | `latency_ms.starts_at`：端到端时延的起点，`proxy` 或 `instance` |
| `p_e2e_ms`、`p_ttft_ms`、`d_e2e_ms`、`d_ttft_ms` | Nullable(Float64) | vLLM 自身统计的两侧时延：`latency_ms.official` 下的 `p.e2e`、`p.ttft`、`d.e2e`、`d.ttft` |
| `steps` | Nullable(UInt32) | `tpot.steps` |
| `p_level`、`d_level`、`p_recorded_level`、`d_recorded_level` | UInt8 | `diag_level`、`recorded_level` |
| `attempts` | UInt32 | `attempts` |
| `p_start`、`d_start` | Nullable(DateTime64(3, 'UTC')) | `sides.p.start`、`sides.d.start` |
| `p_executions`、`d_executions` | Nullable(UInt32) | `sides.p.executions`、`sides.d.executions` |
| `p_unattributed_ms`、`d_first_unattributed_ms` | Nullable(Float64) | `checks` 下的同名字段 |
| `missing` | Array(String) | `missing` |

**每段一列的规则：** 每段一列，类型 `Nullable(Float64)`，单位毫秒，值取自文档中该段的 `doc_path`（段定义的 `doc_path`）。列名就是段定义的 `column`，写进 `segment_def.column_name`。入库进程读到新的 `config_version` 时，为不存在的列执行 `ADD COLUMN IF NOT EXISTS`；段删除后，列保留，新文档中该列为空。调用方从 `segment_def` 取列名，不由代码名推导。

### 3.2 `status_doc`

一份状态文档一行，`doc` 存原文，其余各列由 `doc` 计算。

- 引擎 `ReplacingMergeTree`，按 `ts` 的日期分区，`ORDER BY (cluster, scope, instance, ts)`；保留 `SUMMARY_TTL_DAYS` 天。

| 列 | 取自文档 |
|---|---|
| `schema`、`cluster`、`seq`、`scope`、`instance`、`ts` | 同名字段；`ts` 为这一分钟结束的时刻 |
| `side`、`run_id`、`config_version`、`diag_level` | 同名字段（只在 `scope` 为 `instance` 的文档中有值） |
| `fetch_errors`、`fetch_backoffs`、`behind_seconds`、`run_changes`、`ring_overwritten_lines`、`rejected_429` | `fetch` 下的同名计数 |
| `buffer_overwritten` | proxy 缓冲区被覆盖的记录数 |
| `filter_dropped`、`filter_errors`、`version_dropped`、`outlet_dropped_lines` | `processes` 各项相应计数之和；`filter_errors` 为 `errors` 与 `config_errors` 之和 |
| `open_requests`、`docs_written`、`late_dropped`、`log_dropped`、`segment_changes`、`config_mismatch` | 采集进程状态文档的同名字段 |

计数从进程启动起累计；某一时段的值为时段末减时段初。没有对应字段的文档中，计数列为 0。

### 3.3 `segment_def`

每个 `config_version` 的每一段一行，由入库进程从段定义接口写入，`ReplacingMergeTree(written_at)`，`ORDER BY (config_version, column_name)`。

| 列 | 含义 |
|---|---|
| `config_version` | 段定义的版本 |
| `written_at` | 写入时刻 |
| `ord` | 段在看板上的顺序 |
| `code` | 代码名：段的路径以 `.` 连接，例如 `schedule.queue_time` |
| `grp`、`side`、`phase`、`parent`、`depth` | 所属的组（`ttft`、`tpot`、`background`）、侧（`p`、`d`）、阶段（`proxy`、`ttft`、`tpot`、`background`）、上级段的代码名、深度 |
| `from_level` | 从哪一级粒度起有值 |
| `unit` | `ms` |
| `column_name` | 该段在 `request_doc` 中的列名 |
| `doc_path` | 该段在请求文档中的路径 |
| `label`、`short`、`proc` | 看板上的标签、短名、所属进程 |
| `optional`、`compare`、`outside_total`、`parallel`、`before_proxy`、`has_src` | 标志（0 或 1） |
| `side_name`、`side_total_label` | 该侧在看板上的名称和总时长标签 |

看板生成器取最近写入的 `config_version` 的全部行。

### 3.4 版本表 `db_interface`

| 列 | 含义 |
|---|---|
| `name` | 接口名称 `pd_diag_db` |
| `major` | 主版本，当前为 1 |
| `written_at` | 写入时刻 |

建表时写入一行。看板生成器运行时先读版本表，与 `grafana.env` 的 `DB_INTERFACE` 比较；不符时不生成看板、不改动已有看板，并写明双方的版本。

### 3.5 视图 `request_json`

参数化视图：`SELECT doc FROM vllm_pd.request_json(id = '<请求号>')` 返回一个请求最新版本的文档。

## 4. 版本规则

| 变更 | 是否升主版本 | 双方要做的事 |
|---|---|---|
| 新增列、新增表 | 否 | 面板端不需要升级 |
| 删除或改名固定列；改变列的类型或含义；改变表名 | 是：版本表的 `major` 加 1 | ClickHouse 侧与面板端在同一次升级中完成：先改表，再重新生成看板 |
| 段的新增、删除、改名 | 否：`segment_def` 增加新 `config_version` 的行 | 需要显示时重新生成看板 |
