# 面板二诊断工具说明

面板二的数据经过两端：集群端的采集进程读取各实例和 proxy 的诊断记录，按请求汇总成文档；监控机上的入库进程读取这些文档，写进 ClickHouse，看板从 ClickHouse 查询。诊断工具按这两端拆分为两个程序，各自只检查本端的部件：

| 端 | 程序 | 检查的部件 | 在哪里执行 |
| --- | --- | --- | --- |
| 监控机 | `bin/diag.sh`（`scripts/diag.py`） | 入库进程、ClickHouse、`status_doc` 中的状态文档；ClickHouse、Prometheus、Grafana 的容器 | 监控机上，集群目录中 |
| 集群端 | `fetcher_check.py`（随采集进程安装在 `pd-diag-fetcher/` 中） | 采集进程读取每个来源的情况、写出队列、段定义版本、采集进程自身的计数 | proxy 机器上，或任何能访问采集进程端口的机器上 |

本文用到的部件和名称：

| 名称 | 说明 |
| --- | --- |
| 采集进程（`pd_fetcher.py`） | 运行在 proxy 机器上，按 `fetcher.json` 读取每个实例的记录读取接口和每个 proxy worker 的只读套接字，按请求合并记录、计算各段时延，每个请求写一份请求文档到写出队列 |
| 来源 | 采集进程读取的对象：一个 vLLM 实例（`P0`、`D3` 等），或一个 proxy worker（`proxy.<进程号>`） |
| 写出队列 | 采集进程在 proxy 机器上保存文档的目录 `spool/`，按序号追加，总量超过上限时删除最旧的文件 |
| 接口一 | 采集进程提供的 HTTP 接口（默认端口 9300）：文档读取接口 `GET /pd_diag/v1/docs`、段定义接口 `GET /pd_diag/v1/contract`、状态接口 `GET /pd_diag/v1/status` |
| 请求文档 | 一个请求的汇总结果，写入 ClickHouse 的 `vllm_pd.request_doc` 表 |
| 状态文档 | 采集进程每分钟写出的计数文档，写入 `vllm_pd.status_doc` 表；按 `scope` 分三种：每个实例一份（`instance`）、每个 proxy worker 一份（`proxy`）、采集进程自身一份（`fetcher`） |
| 入库进程（`ingest/pd_ingest.py`） | 运行在监控机上，每个集群一个，经接口一读取文档并写入本集群的 ClickHouse；由 `bin/ingest.sh` 启动和停止，状态端口为 `clickhouse.env` 的 `INGEST_STATUS_PORT`，提供 `/metrics`（供 Prometheus 抓取）和 `/status`（JSON） |

两个程序都只诊断，不修复；`→` 后面是处理办法，由运维人员执行。

## 概要

| 现象 | 命令 | 端 |
| --- | --- | --- |
| 看板没有新数据、状态面板「最近文档距今秒数」变红、升级前自查 | `bin/diag.sh all` | 监控机 |
| 看板中部分实例没有数据，或 `diag.sh chain` 指出某个来源读取失败 | `python3 fetcher_check.py --url http://<proxy 机器>:9300` | 集群端 |
| 告警「入库进程停止」「无法连接采集进程」「写出队列丢弃文档」之后，确认故障时段 | `bin/diag.sh history "<起>" "<止>"` | 监控机 |
| 看板中的请求只有 P 侧或只有 D 侧 | `bin/diag.sh pair <proxy 地址:端口>` | 监控机 |
| 拿到一份新的 vLLM 日志，需要确认记录格式是否变化 | `bin/diag.sh log <日志文件>` | 监控机 |

## 1. 监控机：`bin/diag.sh`

### 1.1 执行位置、配置与权限

- **机器与目录：** 监控机，集群目录中（`bin/panel2_cluster.sh add` 建立的目录，例如 `/data/grafana/vllm-pd-grafana-panel2/<集群>`）。`bin/diag.sh` 只诊断它所在的集群。
- **配置：** 没有单独的配置文件，只读集群目录中的三个文件：
  - `clickhouse.env`：ClickHouse 的地址和端口、只读账号 `vllm_reader` 的密码、入库进程的状态端口 `INGEST_STATUS_PORT`、Prometheus 的地址 `PROMETHEUS_URL` 和抓取任务名 `INGEST_JOB`、告警阈值 `ALERT_STALE_SECONDS`、容器名；
  - `grafana.env`：Grafana 的地址 `GRAFANA_URL` 和容器名；
  - `ingest.json`：采集进程的地址 `fetcher_url`，用于提示在集群端执行的命令。
- **Python：** 与包中其他脚本相同（`bin/lib.sh` 的 `need_python`）：先用环境变量 `PYTHON`，再找 `PATH` 中 3.9 及以上的版本，都没有时用离线目录中自带的 Python。不需要安装其他包，不生成 `__pycache__`。
- **权限：** 执行 `docker inspect`（容器状态）；访问本机的 ClickHouse HTTP 端口、入库进程的状态端口、Prometheus 和 Grafana。

### 1.2 子命令

| 子命令 | 检查内容 | 使用时机 |
| --- | --- | --- |
| `all` | 依次执行 `monitor`、`chain`；屏幕上最多 40 行，`FAIL`、`WARN` 优先 | 第一步；升级前自查 |
| `monitor` | · ClickHouse、Prometheus、Grafana 容器的状态、重启次数、是否因内存耗尽被终止（OOMKilled）；<br>· ClickHouse 数据盘的使用率（`CLICKHOUSE_DATA_DIR`，为空时取容器的数据挂载）；<br>· 监控机可用内存；<br>· 入库进程：`run/ingest.pid`、`run/ingest-loop.pid` 中的进程是否存活，状态端口是否应答；<br>· Prometheus 中抓取任务 `INGEST_JOB` 的目标是否为 up；<br>· Grafana 的健康检查接口 `/api/health` | 看板整体打不开，或某个面板没有数据 |
| `chain` | · 入库进程的 `/status`：是否停止读取（`blocked`）、连续连接采集进程失败的次数（`fetch_failures`）、序号跳号（`ingest_gap`）、写入 ClickHouse 失败的次数；<br>· `request_doc` 中最新请求文档的时刻和最近 15 分钟的份数；<br>· 采集进程状态文档（`scope` 为 `fetcher`）：距今秒数、`config_mismatch`、`log_dropped`、`late_dropped`、`open_requests`；<br>· 每个来源最新的状态文档：距今秒数、读取失败与退避次数、`behind_seconds`、`ring_overwritten_lines`、proxy 的 `buffer_overwritten`、过滤器的出错数和丢弃数、实例的段定义版本是否与采集进程相同 | 看板没有新数据，或部分实例没有数据 |
| `history "<起>" "<止>"` | Prometheus 中抓取任务 `INGEST_JOB` 在这段时间内的序列：`up` 为 0、最近文档距今超过 `ALERT_STALE_SECONDS`、连续连接失败 3 次以上、停止读取、序号跳号、`log_dropped` 增加、请求文档写入速率为 0 的时段。时间为监控机的本地时间，6 小时以内每 60 秒一个点，更长时每 300 秒一个点 | 事后确认故障的开始和结束时刻 |
| `log <文件> [--save-profile]` | 一份 vLLM 日志的离线格式检查：`tools/check_pd_diag_format.py` 的格式校验；面板二读取的 9 种记录是否齐全；与已知样本（`samples/profiles/`）比较记录种类、进程种类和字段 | vLLM 或补丁升级以后；收到新的日志样本 |
| `pair <proxy 地址:端口> [--model M] [--count N] [--wait S]` | 经 proxy 发送 N 个（默认 3 个）短请求，在 `request_doc` 中按请求体的 `request_id`（文档的 `client_request_id`）查找对应的请求文档，判断 P、D 两侧是否都在（`route_p`、`route_d`）以及完成方式 `closed` | 看板中的请求只有 P 侧或只有 D 侧 |

命令写法：

```bash
bin/diag.sh all
```

```bash
bin/diag.sh chain
```

```bash
bin/diag.sh history "2026-11-27 10:30" "2026-11-27 12:00"
```

```bash
bin/diag.sh log /data/logs/prefill.log --save-profile
```

```bash
bin/diag.sh pair 10.1.0.10:8000
```

- `log` 的日志文件先复制到监控机。`--save-profile` 把这份日志的统计保存为 `~/vllm-pd-diag-reports/<集群>/profiles/<文件名>.json`，其中只有计数和字段名，不含日志内容。
- `pair` 的模型名默认取最近一份请求文档的 `model`；没有请求文档或 proxy 要求别的名字时，用 `--model <模型名>` 指定。

### 1.3 判据

| 项 | `OK` | `WARN` | `FAIL` |
| --- | --- | --- | --- |
| 状态文档距今秒数（采集进程、每个来源） | 不超过 130 秒（状态文档每 60 秒一份） | 不超过 390 秒 | 超过 390 秒，或最近 1 天没有 |
| 最新请求文档距今秒数（请求开始时刻） | 不超过 `ALERT_STALE_SECONDS`（默认 120 秒） | 超过，但采集进程的状态文档未过时：最近可能没有请求 | 超过，且采集进程的状态文档也已过时 |
| 入库进程连续连接采集进程失败的次数 | 0 | 1–2 | 3 次以上（与告警「无法连接采集进程」的条件相同） |
| 入库进程停止读取（`blocked`） | 无 | — | 有，并给出原因 |
| 序号跳号（`ingest_gap`）、`log_dropped`、`late_dropped` | 0 | 大于 0 | — |
| 来源的读取失败、`ring_overwritten_lines`、`buffer_overwritten` | 0 | 大于 0 | — |
| 来源的 `behind_seconds`：等待这个来源的请求中最早一个已等待的秒数 | 不超过 150 秒 | 不超过 450 秒 | 超过 450 秒 |
| 过滤器出错数（`errors` 与 `config_errors` 之和） | 0 | — | 大于 0 |
| 实例的段定义版本、`config_mismatch` | 与采集进程相同 | — | 不同 |
| ClickHouse 数据盘使用率 | 低于 80% | 80%–90% | 90% 以上 |
| 入库进程、Prometheus 抓取目标、Grafana、容器 | 在运行、up、健康 | 状态端口有应答但没有进程号文件；容器一天内重启过 | 未运行、down、无应答、容器不存在或被 OOMKilled |

**计数的区间：** 状态文档中的计数从采集进程（或过滤器所在的进程）启动起累计。`chain` 把每个来源最新的状态文档与 10 分钟前的一份相减，判断的是最近 10 分钟的增量；没有 10 分钟前的文档，或采集进程在这 10 分钟内重启过时，用启动以来的累计值，输出中写明「采集进程启动以来」。

**不再判断的来源：** 超过 1 小时没有状态文档、而采集进程的状态文档正常的来源，视为已从 `fetcher.json` 中去掉，只列为 `INFO`。已退出的 proxy worker（状态文档中 `gone` 为真）同样只列为 `INFO`。

**输出行数：** 各来源都正常时合并为一行；有 `WARN` 或 `FAIL` 的来源每个一行。

### 1.4 输出格式

- **第一行：** 子命令、集群、集群目录，以及「只读」或「会发 N 个请求」。
- **每段标题：** 以 `==` 开头。
- **每一行：** 级别加内容。

| 级别 | 含义 |
| --- | --- |
| `OK` | 这一项正常 |
| `WARN` | 可能有问题，或者已经发生过数据丢失；不影响其他项 |
| `FAIL` | 这一项不正常；`→` 后面是处理办法 |
| `INFO` | 只是记录，例如计数、版本、已退出的 proxy worker |

- **最后两行：** `报告：<路径>`，完整报告在 `~/vllm-pd-diag-reports/<集群>/` 下，权限 0600，其中有入库进程 `/status` 的原文和各次查询的原始数据，诊断时把它发回；`RESULT: OK`、`RESULT: WARN（n 项）` 或 `RESULT: FAIL（n 项）`。
- **退出码：** 有 `FAIL` 时为 1，否则为 0。
- **报告中没有：** 密码、请求内容。

### 1.5 样例

实验室输出：1 个 P 实例、1 个 D 实例、1 个 proxy worker，输入为回放的节点记录，所以最新请求文档的时刻较早；地址和路径已换成示例值。D0 停止应答约 1 分钟后的 `chain`：

```text
bin/diag.sh chain：集群 glm53-1（/data/grafana/vllm-pd-grafana-panel2/glm53-1），只读
== chain（采集进程 → 入库进程 → ClickHouse）
OK   入库进程：采集进程 http://10.1.0.10:9300，游标 1795770592549934，连续连接失败 0 次
OK   序号跳号 0 份（入库进程启动以来）
INFO 入库进程启动以来写入请求文档 13 份、状态文档 8 份
WARN 最新的请求文档 3389 秒前，超过 ALERT_STALE_SECONDS（120 秒）；采集进程的状态文档 1 秒前写入：最近可能没有请求，或各实例的记录没有到达采集进程（见下面各来源的行）
OK   采集进程的状态文档 1 秒前，段定义版本 pd-diag-v3.3-extra-glm53-2026-11-20a@0a2312c6，在途请求 0 个
OK   采集进程启动以来：log_dropped 为 0
OK   采集进程启动以来：late_dropped 为 0
OK   2 个来源正常（P0 proxy.4242）：状态文档最多 1 秒前，采集进程启动以来读取无失败、无覆盖，过滤器无出错，段定义版本与采集进程相同
WARN D0：状态文档 1 秒前；读取失败 5 次、退避 1 次（计数为采集进程启动以来）
INFO 采集进程启动以来过滤器丢弃的记录 517 条（dropped：不属于面板二的记录，或缺少请求号的记录）
报告：/root/vllm-pd-diag-reports/glm53-1/diag-chain-20261127-171153.txt
RESULT: WARN（2 项）
```

- 「最新的请求文档」一行为 `WARN`：回放的记录时刻在 1 小时以前，而采集进程的状态文档是新的。
- D0 的读取失败已经出现在它的状态文档中，原因在集群端用 `fetcher_check.py` 查看（第 2.3 节）。

随后停止采集进程，入库进程连续连接失败 3 次后，`chain` 中入库进程的一行变为：

```text
FAIL 入库进程：采集进程 http://10.1.0.10:9300，游标 1795770592549934，连续连接失败 3 次；采集进程停止或网络不通 → 在 proxy 机器上执行 python3 fetcher_check.py --url http://10.1.0.10:9300
```

### 1.6 常见的 `FAIL` 与处理办法

| 输出 | 原因 | 处理办法 |
| --- | --- | --- |
| `入库进程没有应答（状态端口 …）` | 入库进程未运行，或 `INGEST_STATUS_PORT` 与实际不符 | `bin/ingest.sh start`；查看 `logs/ingest.log` |
| `入库进程：… 连续连接失败 n 次` | 采集进程停止，或监控机到 proxy 机器的 9300 端口不通 | 在 proxy 机器上执行 `fetcher_check.py`；采集进程未运行时按部署说明手动启动 |
| `入库进程停止读取：接口版本不符 …` | 采集进程提供的接口主版本不受这一版入库进程支持 | 升级入库进程；文档留在写出队列中，升级后从原位置继续 |
| `入库进程停止读取：集群名不符 …` | `ingest.json` 的 `fetcher_url` 指向了另一个集群的采集进程 | 核对 `fetcher_url` |
| `采集进程的状态文档 n 秒前 …`（`FAIL`） | 采集进程停止，或入库进程停止 | 先看入库进程的行；入库进程正常时在集群端执行 `fetcher_check.py` |
| `<实例>：过滤器处理出错 n 次` | 这个实例的过滤器在处理记录或读取配置时出错 | 查看这个实例 vLLM 日志中的过滤器报错 |
| `段定义版本与采集进程不同的实例（config_mismatch）` | 这些实例的 `segments.json` 与 proxy 机器上的不是同一版 | 把同一版 `segments.json` 下发到这些实例 |
| `Prometheus 中没有抓取任务 …` | 抓取任务和告警规则没有加入面板一的 Prometheus | `bin/prometheus_job.sh` |
| `<请求>只有 P 侧`（`pair`） | proxy 发给 P、D 的 `X-Request-Id` 不同，采集进程无法合并两侧的记录 | 核对 proxy 的转发设置 |

## 2. 集群端：`fetcher_check.py`

### 2.1 执行位置

`fetcher_check.py` 与采集进程放在同一目录（`pd-diag-fetcher/`）。在 proxy 机器上，或任何能访问采集进程 `listen_port` 的机器上执行；`--url` 默认为 `http://127.0.0.1:9300`：

```bash
python3 fetcher_check.py --url http://10.1.0.10:9300
```

- 只调用一次状态接口 `GET /pd_diag/v1/status`，不读写任何文件，不改变采集进程的状态。
- 只用 Python 标准库，Python 3.9 及以上。
- 采集进程运行在 proxy 容器中时，可以在宿主机上执行，也可以执行 `docker exec <proxy 容器> python3 <目录>/fetcher_check.py`。

### 2.2 输出各行

| 行 | 内容 | 判据 |
| --- | --- | --- |
| 采集进程 | 集群名、接口版本、启动时刻 | 接口不是 `pd_diag/v1` 时 `FAIL` |
| 每个来源一行（实例、proxy worker） | 运行号、已读序号（`read_seq`）与来源的最新序号（`head_seq`）、最近一次读取成功距今秒数（`last_ok_seconds`）、读取失败次数（`errors`）、退避次数（`backoffs`）、运行号变化次数、`ring_overwritten_lines`、`behind_seconds`；有失败时附最近的错误（`last_error`） | 启动以来没有读取成功过，或最近一次成功超过 35 秒（退避上限 30 秒加读取超时）时 `FAIL`；`behind_seconds` 超过 150 秒或 `ring_overwritten_lines` 大于 0 时 `WARN`；已退出的 proxy worker（`gone`）为 `OK` |
| 写出队列 | 最新序号、最旧序号、写出队列和请求摘要日志的占用、已写出的请求文档数 | 只记录 |
| 段定义版本 | 采集进程的 `config_version`；与之不同的实例（`config_mismatch`） | 有不同的实例时 `FAIL` |
| 段定义变化 | 变化次数和最近一次的版本；`segments.json` 读取失败的次数 | 读取失败时 `WARN` |
| `log_dropped` | 写出队列在入库进程读取之前删除的文档数 | 大于 0 时 `WARN` |
| `log_write_errors` | 写出队列、请求摘要日志写入失败的次数 | 大于 0 时 `FAIL`：检查 proxy 机器的磁盘空间 |
| `late_dropped` | 超过延迟到达窗口被丢弃的记录数 | 大于 0 时 `WARN` |
| 在途请求 | 在途请求数（`open_requests`），已写出的请求按完成方式的份数（`complete`、`no_proxy`、`incomplete`、`evicted`） | 只记录 |

- 计数都从采集进程启动起累计。
- 来源超过 30 个时，没有发现问题的来源合并为一行，有问题的来源每个一行。
- 最后一行为 `RESULT: OK` 或 `RESULT: FAIL`；有 `FAIL` 时退出码为 1。
- 采集进程没有应答时只输出一行 `FAIL` 和 `RESULT: FAIL`。

### 2.3 样例

与第 1.5 节同一次实验室运行，D0 停止应答约 40 秒后：


## 3. 由计数定位故障

| 情形 | 监控机（`bin/diag.sh`） | 集群端（`fetcher_check.py`） |
| --- | --- | --- |
| 采集进程停止 | `chain`：入库进程连续连接失败；采集进程的状态文档过时；最新请求文档超过阈值 | 采集进程没有应答 |
| 某个实例停止应答或网络不通 | `chain`：这个来源的读取失败、退避次数增加，`behind_seconds` 增大 | 这个来源的最近成功时刻超过 35 秒，附最近的错误 |
| 采集进程停止的时间超过缓冲区能维持的时长 | `chain`：`ring_overwritten_lines`、proxy 的 `buffer_overwritten` 增加 | 同左的计数 |
| 入库进程或 ClickHouse 停机超过写出队列可容纳的时长 | `chain`：序号跳号、`log_dropped` 增加；`history` 给出时段 | `log_dropped` |
| proxy 机器磁盘写满 | — | `log_write_errors` 增加 |
| 延迟到达的记录超过延迟到达窗口 | `chain`：`late_dropped` 增加 | `late_dropped` |
| 实例与采集进程的 `segments.json` 不是同一版 | `chain`：`config_mismatch`、实例的段定义版本不同 | 段定义版本一行 |
| vLLM 实例重启 | `chain`：运行号变化（`INFO`） | 运行号变化次数 |
| 接口版本不符、不认识的文档 | `chain`：入库进程停止读取，并给出原因 | — |

## 4. 只读范围与 `pair` 的例外

- **集群目录：** `bin/diag.sh` 只读 `clickhouse.env`、`grafana.env`、`ingest.json` 和 `run/` 中的进程号文件，不写集群目录，不调用 `bin/ingest.sh`。
- **ClickHouse：** 以只读账号 `vllm_reader` 经 HTTP 接口查询，每条查询都带 `readonly=1`。
- **服务：** 不重启、不停止、不修改入库进程、采集进程、ClickHouse、Prometheus 或 Grafana。
- **写的位置：** 只有 `~/vllm-pd-diag-reports/<集群>/`。
- **`pair`：** 经 proxy 发送 N 个 `max_tokens` 为 8 的请求，请求体的 `request_id` 为 `diag-<时刻>-1` 到 `-N`；这几个请求会出现在看板上，以 `diag-` 开头的是诊断发送的。除此以外 `pair` 也只读。
- **`fetcher_check.py`：** 只调用状态接口。
