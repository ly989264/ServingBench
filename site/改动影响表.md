# 改动影响表

改仓库里任何文件之前先查这两张表：表一说明每个目录对应内网的哪套部署、能不能改；表二列出监控机上各套面板共用的资源，新增或修改时按「新增时的取值」一列取值。现场的实际值见 [`内网现状.md`](内网现状.md)。

仓库里的改动不会自动到达内网：由用户出包，在内网执行。

## 表一 仓库目录与内网的对应

| 目录 | 内网对应 | 改动后果 | 规则 |
|---|---|---|---|
| `interface/` | test-glm53 采集进程（proxy 机器，端口 9300）与监控机入库进程之间的接口一 | 两端不一致时入库停止 | 只由用户改 |
| `panel1/` | 8 个线上集群的 16 张面板一看板和 8 个 Prometheus | 下一次升级或加集群时带到全部线上看板 | 不改；新建同类面板复制到新目录 |
| `panel2-v3/` | 线上 glm53-1 的面板二（`v3.4-extra-t53`） | 重跑部署时带到线上 | 冻结，不改；缺陷报给用户 |
| `panel2-v4/` | test-glm53 的面板二（`v4.0-extra`，已部署、待验收；本地全链路运行已跑通，见 `interface/README.md` 6.1 节） | 只影响测试集群，直到用户执行线上升级 | 新面板二的维护者可改 |
| `site/` | 无（记录） | 记录与现场不符 | 现场变更后由用户按检测脚本的输出更新 |

## 表二 监控机共用资源

| 资源 | 被谁使用 | 改错的后果 | 新增时的取值 |
|---|---|---|---|
| Grafana（容器 `vllm-pd-grafana`，端口 3000，全部集群共用一个） | 面板一 16 张、面板二 2 张看板，10 个数据源 | 看板或数据源被覆盖、移动，影响全部线上集群 | 新面板装在同一个 Grafana 时，只新增自己的看板和数据源，不改已有的 |
| 看板 UID 与数据源 UID | 面板一 `vllm-pd-prefill-<集群>`、`vllm-pd-decode-<集群>`、`prometheus-<集群>`；面板二 `vllm-pd-request-<集群>`、`vllm-pd-clickhouse-<集群>` | UID 相同时导入会覆盖已有看板或数据源 | 不用 `vllm-pd-` 前缀，也不用 `prometheus-<集群>` 的形式；用新面板自己的前缀并带集群名 |
| 看板标题 | 面板一升级脚本 `panel1_upgrade.py` 和各部署包按标题查找看板（`arrange_boards.py` 按注册表里的 UID 查找） | 标题相同或前缀相同的看板会被一并移动或升级（曾出现未登记的看板被升级） | 标题不以「vLLM 服务侧监控面板」开头，也不与「vLLM 请求侧拆解面板」「面板二：请求时延拆解（P / D）」相同 |
| Grafana 文件夹 | 两层：模型组 / 集群（`GLM-5.3/glm53-1`、`dsv4.1-flash/dsv4.1-flash-N`），顶层 `GLM-5.3-test`；由 `arrange_boards.py` 按 `boards_layout.txt` 整理 | 部署包只认顶层文件夹，任何 add、update、rollback 之后不跑 `arrange_boards.py apply`，看板会回到顶层 | 新面板用自己的文件夹，不放进上述文件夹，不写入 `boards_layout.txt` |
| 端口基数 | 每个集群占 10 个端口：18100、18120 至 18190 已用，18110 现场无容器占用（见 `内网现状.md` 2.1） | 端口冲突时容器起不来，或接到别的集群 | 新增从 18200 起，每类每集群占 10 个；先在监控机上确认端口空闲 |
| 注册表 `/root/.vllm-pd-clusters.json` | 面板一、面板二的部署脚本、`arrange_boards.py`、`make_inventories.py` 都读它 | 字段不合规时这些脚本报错，或把看板移到错误的文件夹 | 新一类面板不往注册表里写；确需登记时沿用同样的字段，并先报给用户 |
| docker 网络 `vllm-pd-monitor` | 我方全部容器：Grafana、9 个 Prometheus、2 个 ClickHouse、Vector | 删除或重建网络会断开 Grafana 与全部数据源 | 新容器可以加入这个网络，不删除、不重建 |
| 容器名与数据卷名 | `vllm-pd-prometheus-<集群>`、`vllm-pd-clickhouse-<集群>`、`vllm-pd-vector-<集群>`、`vllm-pd-grafana`；数据卷 `vllm-pd-prometheus-data-<集群>`、`vllm-pd-grafana-data` | 同名容器或数据卷会覆盖已有的数据 | 不用 `vllm-pd-` 前缀 |
| 面板一的 Prometheus 被面板二借用 | glm53-1 面板二的告警规则写在 `vllm-pd-prometheus-glm53-1` 的 `prometheus.yml` 标记段里 | 重新生成这份 `prometheus.yml` 而不保留标记段，会丢掉面板二的告警 | 改面板一 Prometheus 配置时保留标记段（`panel1/` 的生成脚本已保留） |
| Grafana 账号的来源 | 面板一升级、`arrange_boards.py`、test-glm53 都从 glm53-1 面板二的 `deploy.env` 读 Grafana 账号 | 删除或改动这份 `deploy.env`，面板一升级和文件夹整理会找不到账号 | 新面板从同一处读账号，不改这份文件 |
| Grafana 的 provisioning 与 dashboards 目录 | 挂载自 `/data/<个人目录>/vllm-pd-grafana-panel1/grafana/` | 删除或移动该目录后，Grafana 重启时加载失败 | 不往这两个目录里放新面板的文件；新面板经 Grafana API 导入 |
| Grafana 镜像 | 标签为 `latest`，实际版本 12.4.2 | 重建容器并重新拉取镜像时可能升级，看板和 ClickHouse 插件的兼容性未验证 | 不重建 Grafana 容器；需要重建时先把标签固定为 `grafana/grafana:12.4.2` 并报给用户 |
| 监控机上的推理容器 | `vllm-ascend-glm53-v30` 等 vLLM 容器与面板组件在同一台机器上 | `docker system prune`、重启 docker、大量写盘会影响推理服务 | 不执行 prune，不重启 docker；写盘前看 `/data` 的剩余空间 |
| ClickHouse 数据目录 | `/data/clickhouse-glm53-1`（ClickHouse 与 Vector 挂载）、`/data/clickhouse-test-glm53` | 误删即丢失全部面板二数据 | 新的 ClickHouse 用新的数据目录，不放进这两个目录 |
| 拉取程序运行目录 `/data/grafana/vllm-timing/` | glm53-1 拉取程序的 pid 文件和状态 | 删除后拉取程序的循环找不到 pid 文件 | 不删、不放新文件 |
| 节点目录 `/data/pd-diag/`（P、D、proxy 机器） | 节点配置、日志、T62 备份、采集进程 | 改动影响推理容器读取的配置 | 新面板不在节点上放文件；需要时先报给用户 |
