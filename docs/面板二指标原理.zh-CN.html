    面板二 P/D 指标原理

    面板二把一个请求的时延拆成若干段。本讲义说明 P 侧、D 侧每一段的起止时刻、所在进程、使用的时钟、来源字段和算法，以及这些记录从各节点到看板经过的程序。内容以面板包 v3.2-extra（段定义 pd-diag-v3.2-extra-glm53-2026-11-20a）和 glm5.3 上 vLLM、vllm-ascend、Mooncake、proxy 四处计时补丁的代码为准。

    框架

    1请求路径与段的定义

    本节是全篇的基础：先画出一个请求在 P/D 分离集群里经过的进程和线程（图 1），再给出确定一个段所需的六个要素（定义 1），第 2 至第 5 节都按这两样展开。

    1.1 P/D 分离下一个请求的路径

    P/D 分离（prefill/decode disaggregation）把一个请求的推理拆到两组实例上。P（prefill）实例计算整段提示，产出第一个 token，并把提示的 KV 缓存留在自己的 NPU 显存里。KV 缓存指注意力层为每个位置算出的键（K）和值（V），后续每个 token 的计算都要读它们。D（decode）实例从 P 读走这份 KV 缓存，再逐个生成后面的 token。两组实例前面有一个 proxy，它先把请求送到 P，再送到 D。

    本讲义的对象是 glm5.3 集群：vLLM v0.30.0，vllm-ascend d4ad49796（现场有本地改动），Mooncake 同时用作 P→D 的 KV 传输和缓存池的后端。P 每台机器 1 个实例，每个实例做 TP16 张量并行，即一个模型切分到 16 张 NPU 上；D 每台机器 16 个实例，每个实例 TP1，整个 D 侧是 dp=64 的数据并行组。两侧都开了 MTP 投机解码，P 的草稿长度 k=1，D 的 k=5；D 以图模式加异步调度运行。

    按图 1 的编号，一个请求依次经过下面几步。

    1. ①客户端把请求发给 proxy。proxy 为请求生成自己的请求号（下文称请求键 X），发给 P、D 的请求都带这个号。
    2. ②proxy 把请求改成非流式、max_tokens=1，发给选中的 P。P 的 API server 解析请求、套聊天模板、分词，经 ZMQ 交给 EngineCore；EngineCore 的调度器排队、计算块哈希、查前缀缓存和缓存池、分配 KV 块，把这一步交给 16 个 Worker；Worker 在 NPU 上算完整段提示（分块 prefill 时分几步算），采样出第一个 token。
    3. ③P 上的请求随即结束，响应里带回 kv_transfer_params，其中有 D 读 KV 所需的对端信息。这份 KV 留在 P 的显存里等 D 来读；同时 Worker 的保存线程在后台把它写进缓存池。
    4. ④proxy 把原请求加上 kv_transfer_params 发给选中的 D。D 的 API server 再解析、分词一次，交给 EngineCore。
    5. ⑤D 的调度器第一次选中这个请求时只发起读取，KV 接收线程按 kv_transfer_params 从 P 的显存读 KV。读完以后，调度器把请求排进运行队列，Worker 开始逐步生成。
    6. ⑥D 的输出以流式经 proxy 回到客户端。

    所以一个请求在面板二上分成两侧：P 侧从 P 的 API server 收到请求起，到它发出响应为止；D 侧从 D 的 API server 收到请求起，到最后一个字节为止。每一侧之前各有一段在 proxy 里的时间。

    1.3 段的六要素

    段是一个请求在某一侧经过的一段时间。面板二上的每一段都由下面六个要素确定，第 2、3 节对每一段逐项给出它们。

    定义 1　段的六要素

    1. 层级：L1 是阶段，L2 是阶段下的子段，L3 是子段下的子段。有下级的段称为父段。
    2. 起止：起点和终点，各对应代码里的一个时刻。
    3. 位置：起止时刻所在的进程或线程。
    4. 时钟：量这段时间用的时钟，主机单调时钟（CPU）或 NPU 设备事件（NPU），见 1.4 节。
    5. 来源：数值所在的记录种类和字段，写成「记录[范围] · 字段路径」，例如 api_summary[http] · stages.tokenize.duration_ns，见 1.5 节。
    6. 取值：从记录到段值的算法，共五种，见 1.5 节。

    六个要素里，层级、来源、取值写在段定义文件 profiles/glm53/segments.json 里，面板二的过滤器、采集器和看板查询都只读这一份文件；起止、位置、时钟由计时补丁的代码决定，记录格式约定（glm5.3 版 1.4.0）写明了每个字段的口径。段在代码里的名字（id）是英文，看板上显示的标签大多与它相同，少数段另有标签（例如 wait_for_put 显示为「等 put 完成」），本讲义两者并列。

    两侧的段树。P 侧 27 段分三部分：proxy 里 2 段，请求路径上到第一个 token 为止 16 段，后台保存 9 段。D 侧 29 段也分三部分：proxy 里 1 段，到第一个 token 为止 19 段，第二步起 9 段。「第二步起」指 D 产出第一个 token 之后的各步。

    合计与对照行。P 合计、D 合计不是段，它们是各侧 API server 从收到请求到发出最后一个字节的时长，取自 api_summary[http] 的 end_ns − start_ns，是看板上各段占比的分母。proxy 里的段和后台的段都不计入合计。对照行是 vLLM 自己算出的三个时长 queued_time、prefill_time、decode_time，放在它所对照的几段旁边，不计入合计，也没有占比。另有 5 条累加规则只把数据写进数据库、不上看板：step_device_span、graph_full、graph_piecewise、graph_none、bookkeeping，供 5.5 节的第一步开销分析使用。

    有了定义 1，一个段的全部含义由六项确定，任意两段可以逐项比较。

    1.4 两种时钟

    主机单调时钟（CPU）。Python 的 time.monotonic_ns() 返回自开机以来的纳秒数，不随系统时间的调整而跳变。记录里所有 *_ns 字段（*_wall_ns 除外）都取本进程的单调时钟。同一台机器上各进程读的是同一个时钟，可以直接比较；不同机器的单调时钟起点不同，不能比较。用它量出的是主机线程经历的时间：一段主机代码从开始到返回的时长。

    NPU 设备事件（NPU）。主机向 NPU 提交的算子在计算流（stream）上按提交顺序排队执行，主机提交完即返回，不等执行结束。图模式加异步调度时更是如此：一步的整张计算图一次提交，主机量到的 forward 只是提交命令的耗时。设备事件是插进计算流的标记（torch.npu.Event(enable_timing=True)），NPU 执行到它时记下设备上的时间。在被测调用前后各插一个事件，两个事件的时间差是这次调用在设备上的执行区间，写作 device_duration_ns。

    设备事件的读取有几条规则，它们决定了一个 NPU 段什么时候有值：

    • 事件不加同步，延后读取。Worker 用 4 个槽位的环形池轮换事件，读取前先用 query() 查两个事件是否都已完成，完成了才算差值。所以这一步的 worker_summary 推迟到读到设备值以后才写出，最多推迟 4 步；到期仍读不到，记录照常写出，只是不带 device_duration_ns，也不写 0。
    • 只在 TP rank 0 上记。同一步里同一阶段被调用两次时不给设备值，因为一对事件量不出两次调用之和；捕获计算图期间不记。
    • 包住纯主机工作的段（D 的 prepare_inputs、bookkeeping）也取事件之差，量到的是计算流在这段主机工作期间空等的那部分。一步里的 6 个设备段在同一条计算流上先后排队，区间互不重叠，可以直接相加。

    其他时钟。proxy 也用单调时钟，它的 6 个时刻都在 proxy 机器上，所以 proxy 里的段可以直接相减。Mooncake 的 C++ 计时用 steady_clock，取整到微秒。墙钟（time.time_ns()，日历时间）只用在两处：把 Mooncake 的日志行和保存任务对上（native_calls[] 里的 start_wall_ns、end_wall_ns），以及在时间线上安放每一侧（日志行前缀的时间，精确到毫秒）。

    所以每个段值都是同一进程或同一台机器上两个时刻之差；CPU 段量的是主机线程经历的时长，NPU 段量的是计算流上的执行区间，两者不能互相代替。

    段的来源是一种记录里的一个字段。表 2 列出面板二读的全部记录种类，每种记录的示例和字段在第 4 节给出。

    从记录到段值的算法共五种。

    （1）直接取。取一条请求级记录（每个请求一条）里的一个字段。同一条记录里有两个字段映射到同一段时两者相加，例如 req_resolve 是 stages.req_resolve 加 stages.render。core_summary[request] 一个请求偶尔有几条，取最后写出的一条。

    （2）累加。每步一条的记录（core_summary[execution]、worker_summary）不属于单个请求，只带这一步的请求列表 request_ids。节点上的过滤器把这一步的值加到列表里每个请求的部分和上，每个请求在每个进程里记三个数：总和 ns、步数 steps、第一步的值 first_ns。第一步指这个请求在这个进程里第一次出现的那一步。段取其中之一：全部步之和（total）、第一步（first）、第二步起（rest，即总和减第一步）。图 2 是一个算例。

    累加有两点要记住。第一，整步的值记给这一步的每一个请求：两个请求同在一步，各自的部分和都加上这一步的全部时长。所以累加段的值是这个请求参与的那些步花的时间，其中包括同一步里为别的请求做的工作；把同一步里各请求的段值相加会重复计数。第二，需要先等 KV 的请求，调度器第一次选中它的那一步（首次候选）只发起读取，这一步的记录不列这个请求。过滤器先按步骤号 execution_id 暂存这一步的值，等同一进程里出现带「请求号 + 步骤号」的映射记录时再记给请求；用到它的是 D 的 submit，以及异步加载缓存池时的 lookup、alloc、other。

    （3）最大值。D 从 P 读一个请求的 KV 要分成多个读任务（glm5.3 测试集群上是 16 个，等于 P 的 TP 端口数乘分片数），不同 P 端口的任务并行，同一端口的任务串行。receive_queue 和 prepare_read 取各任务的最大值，最大值由 KV 接收线程在写请求汇总时算好。

    （4）墙钟包络。一组并行活动从最早开始到最晚结束（或到标记完成）的时长，用于 D 的 wait_for_transfer（读取包络）和 start_load_kv（等 KV 的包络）。包络不等于各部分之和，因为各部分在时间上重叠。

    （5）子段之和。父段没有自己的来源时显示子段之和；有自己的值时用自己的值（D 的 start_load_kv）。子段都为空时父段为空。

    所以每一段的取值都属于这五种之一，段名后的「第一步」「第二步起」指的是累加的哪一部分。

    本节的结论是：一个请求先后经过 proxy、P、proxy、D 四处（图 1），面板二上的每一段都可以用层级、起止、位置、时钟、来源、取值六项完整描述（定义 1）。

    2.1 proxy 与 API server：6 段

    这 6 段对应图 1 的 ①② 两步和 P 的 API server。proxy 是一个 asyncio 程序，进入请求处理函数时取时刻 t_enter，随后读请求体、用共享的调度器选出 P（持锁调用）、构造发给 P 的请求，在调用 client.post 之前取时刻 t_p_send，两者之差为 lb_proxy。proxy 前面如果还有网关，网关里的时间是 api_gateway；四个被测组件里都没有这一段的时刻，它按设计为空。

    请求进入 P 的 API server 以后，事件循环依次做四件事。入口中间件在 ASGI 入口取起点，接口处理函数开始时取终点，这是 req_resolve；接着 render 按聊天模板把消息列表渲染成提示文本，render 的时长并入 req_resolve。tokenizer 是分词，分词在线程池里执行，事件循环等待结果。add_request 从分词返回算起，到构造好的引擎请求经 ZMQ 发送完成为止。P 的第一个 token 回到 API server 以后，输出处理任务对它去分词，这是 detokenizer。

    2.2 EngineCore 的调度：schedule 与 5 个子段

    EngineCore 的主循环每转一圈是一步：调用一次 schedule() 选出这一步要算的请求和 token 数，把调度结果发给 Worker 执行，再处理 Worker 返回的输出。计时补丁把原来的 schedule() 拆成外层计时加内层 _schedule()，外层量出这一次调度的总时长，内层记下其中各区间：

    • lookup：查本地前缀缓存（kv_cache_manager 找出已算过的块），以及问连接器缓存池里能命中多少 token；
    • alloc：allocate_slots，为这一步要算的 token 分配 KV 块；
    • other：总时长减去 lookup、alloc 和外部查找这几个互不重叠的区间，剩下的选请求、排序、组装调度结果等工作。

    每一步写一条 core_summary[execution]，带这一步有 token 要算的请求列表 request_ids，过滤器按 1.5 节的累加把三个值记给列表里的请求。请求生命周期里的两段记在请求结束时写出的 core_summary[request] 里：queue_time 从进入等待队列到第一次被选为候选；hash 是计算块哈希的总时长。前缀缓存以固定长度的 token 块为单位，每个块的哈希由前一块的哈希和本块的 token 算出，查前缀缓存和缓存池都按块哈希进行。

    glm5.3 的 P 同步加载缓存池（load_async=false），命中缓存池的请求在被选中的同一步里加载并执行，没有首次候选的空步，所以 lookup、alloc、other 中首次候选那一项在 P 上为空。P 的提示较长、开了分块 prefill 时，一个请求会经过几步，这三段是这几步之和。

    2.3 Worker 主线程：wait_for_put、加载、forward、sampling

    Worker 收到调度结果后执行一步，glm5.3 默认的 V1 runner（vllm-ascend worker/model_runner_v1.py）按下面的顺序工作：

    1. 等 put 完成（wait_for_put）。这一版 vllm-ascend 的缓存池只等被释放请求的保存：一个请求结束或被抢占以后，它的 KV 块立即可以分给别的请求，所以这一步 forward 之前，Worker 要等这些已释放请求尚未写完的保存（KVCacheStoreSendingThread.wait_for_requests_saved）。等待按 1 ms 间隔轮询。这段时间按谁在等就记给谁，记给这一步的请求。P 的请求只产出一个 token、随即结束，几乎每一步都有刚释放的请求，所以 P 的 wait_for_put 里主要是前面请求的保存时间。
    2. 加载（start_load_kv）。连接器的 start_load_kv。P 同步加载，命中缓存池的请求在这个调用里逐个完成 Mooncake get，每个请求写一条 pool_task[load]，这是 submit；没有后台加载，所以 wait_for_transfer 为空。
    3. forward。目标模型的一次前向，设备事件紧贴 run_model() 前后。
    4. sampling。采样；有草稿 token 时是 rejection sampler，决定接受几个草稿。
    5. 草稿与提交保存。MTP 草稿模型为下一步猜 k=1 个 token；之后提交这一步的保存。P 上草稿没有对应的段（T56 新加的段只在 D 上写），它的时间落在未归属里（2.5 节）。

    P 的 16 个 TP rank 各自执行同一步，各等各的保存线程，各写一条记录；面板只取 rank 0。forward、sampling 只取设备时长，读不到设备值的步不加，不用主机时长代替。

    2.5 P 合计与未归属的时间

    P 合计是 P 的 API server 从收到请求到发出响应的时长（api_summary[http] 的 end_ns − start_ns），另加 api_gateway，后者为空、按 0 计。请求路径上到第一个 token 为止的 9 个 L1（req_resolve、tokenizer、add_request、schedule、wait_for_put、start_load_kv、forward、sampling、detokenizer）覆盖不了 P 合计的全部，P 合计减去这 9 段之和称为未归属时间，单请求 JSON 的 checks.p_unattributed_ms 即这个差。按读码，未归属时间主要包括：

    • P 上的 MTP 草稿（k=1），它在 sampling 之后、同一步里执行；
    • Worker 在 forward 之前准备输入的主机时间，以及设备段之间的空隙，P 上都没有对应的段；
    • 进程之间的交接：API server 到 EngineCore 的 ZMQ 接收，EngineCore 把调度结果发给 16 个 Worker，输出回到 EngineCore 和 API server；
    • API server 等待引擎输出、组装响应的时间。

    P 侧 27 段按执行单元分为 proxy 与 API server 6 段、EngineCore 6 段、Worker 主线程 6 段、保存线程 9 段。到第一个 token 为止的 16 段覆盖了 P 合计的主要部分，未归属部分主要是 P 上的草稿和进程之间的交接；后台 9 段描述这个请求留下的保存工作，它会出现在后面请求的 wait_for_put 里。

    P 是同步加载（load_async=false），没有后台加载线程，也就没有等待后台加载完成的阶段，段定义把它的来源写为 null。Mooncake get 在 start_load_kv 调用里同步完成，传输时间含在 start_load_kv/submit（pool_task[load] 的 duration_ns）里。

    习题 2.2

    列出 P 侧不计入 P 合计的段，并写出各自的原因。

    api_gateway 与 lb_proxy：发生在 P 的 API server 收到请求之前，P 合计按 API server 口径计（api_gateway 为空，按 0 计入）。后台 9 段（wait_for_save 及其子段）：在保存线程里异步执行，P 的响应不等它。

    3.2 等 KV：start_load_kv 与 4 个子段

    D 从 P 读 KV 的过程如下，图 4 是对应的时间线。

    1. 首次候选（步 X）。调度器选中请求，发现它的 KV 要从远端取，为它分配块，把它置为 WAITING_FOR_REMOTE_KVS 状态。P→D 连接器（MooncakeConnectorV1）的调度端在同一次 schedule() 末尾写一条映射记录 pd_transfer_summary[link]，带请求号和步骤号 X。这一步不为这个请求做 forward，它不在这一步的 request_ids 里。
    2. 提交读任务（submit）。Worker 在步 X 的 forward 发出以后调连接器的 start_load_kv，按 kv_transfer_params 里的对端信息为每个 P 端口和分片各调用一次 add_request，把读任务放进 KV 接收线程的队列，glm5.3 测试集群上每个请求 16 个任务。这个调用只入队，不等传输。
    3. 处理读任务。接收线程取出一个任务时记下开始时刻，开始时刻减入队时刻是这个任务的排队时长 queue_wait_ns。随后取对端信息（meta_fetch；对端信息没有缓存时向 P 发一次 metadata_request），组读表（prepare：拼出源地址、目的地址、长度三个列表），调一次 Mooncake 的原生读取 batch_transfer_sync_read，必要时重排 KV 的布局（reformat）。不同 P 端口的任务并行，同一端口的任务串行。
    4. 标记完成。最后一个任务结束读取时，连接器把这个请求标记为完成，这一刻是 request_done_ns（图 4 的 t1）。之后各任务还要给 P 发结束信号、等一次应答，这段时间请求已经可以运行，不属于等 KV。
    5. 写请求汇总。全部任务结束以后，接收线程写一条 pd_transfer_summary[request_generation]，带三个最大值、读取包络 transfer_envelope_ns 和等 KV 的包络 kv_load_envelope_ns。

    3.3 调度器一侧的等待：kv_ready_wait 与 queued_time (vLLM)

    请求在 t1 被标记完成以后，还要经过两次交接，调度器才知道它的 KV 已经到齐。第一次在 Worker 进程里：Worker 主线程要等到某一步 forward 之后调 get_finished，才把这个请求取走（G1）。第二次在进程之间：这件事随那一步的输出交回 EngineCore，EngineCore 先处理排在前面的事务；D 是异步调度，这中间至少隔一次 schedule()（G2）。EngineCore 在 _update_from_kv_xfer_finished 里收到 finished_recving、请求还处在 WAITING_FOR_REMOTE_KVS 时，取 kv_ready_wait 的起点 d。请求随后被提升出等待状态（记下 promoted_ns），到下一次把它放进运行队列的 schedule() 开始时取终点 f；提升以后如果这一步的 token 预算或块不够，它还要再等几步，ranges[].promoted_ns 用来区分这两种等待。

    kv_ready_wait 只在 D 上写，只在走过一轮异步加载的请求上写。D 的判断只用一个函数 is_pd_decode(vllm_config)，它取的是 vllm-ascend 自己的条件：顶层 kv_role 为 kv_consumer，并且开了 recompute_scheduler_enable。P 上这个条件不成立，所以 P 的记录和加这一段之前逐字段相同。

    终点 f 与 vLLM 打 SCHEDULED 时刻在同一次调用里，两者只差进入 _schedule() 之前的几条语句。vLLM 的 queued_time 是 scheduled_ts − queued_ts（v0.30.0 vllm/v1/metrics/stats.py，只取第一次调度，不计抢占），从 QUEUED 到 f。把图 4 从左到右读一遍，它等于 queue_time，加首次候选那一步里选中之后的调度工作和 G0，加 start_load_kv，加 G1、G2，再加 kv_ready_wait。G0 是步 X 分配完块到 Worker 调 start_load_kv 之间的时间。面板只显示日志里量到的段，不跨记录相减，所以 G0、G1、G2 不上看板，把 queued_time (vLLM) 和三段之和对着看即可看出它们的总量。

    思考题 3.1

    判断下列说法是否成立并说明理由：start_load_kv 的 4 个子段之和一定不大于 start_load_kv。

    解答

    不成立。start_load_kv 取等 KV 的墙钟包络，receive_queue、prepare_read 取各任务的最大值，这些最大值可能来自不同任务，彼此重叠，也和 wait_for_transfer 重叠，所以子段之和可能大于包络。只有在包络为空、退回子段之和时，两者才相等。

    习题 3.2

    写出 queued_time (vLLM) 与 queue_time、start_load_kv、kv_ready_wait 三段之和的差由哪几部分组成。

    解答

    首次候选那一步里选中之后的调度工作；G0：步 X 分配完块到 Worker 调 start_load_kv；G1：请求被标记完成到 Worker 主线程取走它；G2：这件事交回 EngineCore、被调度器处理之前的时间。

    4.1 记录行与公共字段

    计时补丁用 logger vllm.v1.metrics.pd_diagnostics 以 INFO 级写记录，消息是 [PD_DIAG] 后接一段 JSON。经过节点上的过滤器以后，记录文件里的一行如下：行首是带毫秒和 UTC 偏移的本机时间，括号里是进程名和 pid，然后是源文件与行号、标记和 JSON。

    4.4 进程内过滤器

    过滤器 pd_diag_logfilter.py 是一个 Python logging 处理器，经 VLLM_LOGGING_CONFIG_PATH 指向的日志配置装进每个 vLLM 进程（API server、EngineCore、Worker）。日志配置给 logger vllm 挂两个处理器：控制台处理器加了一个过滤条件，不再输出 [PD_DIAG] 行；另一个是过滤器本身。过滤器读和监控机同一份 segments.json，文件变化后约 2 秒内重读，不用重启 vLLM。装了面板二以后，vLLM 进程里写出的 [PD_DIAG] 行全部出自过滤器；proxy 自己也写 [PD_DIAG] 行，不经过过滤器（4.3 节）。在现场的部署里，proxy 跑在集群的一个节点上，它的文件和这台机器的节点记录放在同一个日志目录下。

    每条记录到达过滤器后依次经过下面几步：

    1. 记录种类不是 segments.json 读的，丢弃（自检计数 dropped）。
    2. 定角色：按进程名，EngineCore → engine、Worker → worker、APIServer → api；再按记录种类改写，EngineCore 进程写的 worker_summary 归 worker（D 的 TP1 情形），pool_task 归 pool。
    3. rank 0 规则：worker、pool 两种角色只留 tp_rank 为 0 的记录（字段缺失时从进程名里的 _TP<n> 取），其余丢弃（rank_dropped）。D 的 request_generation 在 TP1 时归 engine 角色，不按 rank 过滤，这时本来只有 rank 0。
    4. 记录的 version 不等于 segments.json 的 record_version（2），丢弃（version_dropped）。
    5. 首次候选：按 execution_id 暂存候选规则的值（最多 8192 步、120 秒），遇到同一进程里的映射记录时记给请求；一步自己的记录已经列了这个请求时不重复记。
    6. 匹配某条累加规则：把值加进请求的部分和，记录本身不写出（accumulated）。
    7. 匹配原样写出规则：原样写进本进程的文件（written）。
    8. 其余丢弃。
    处理哪些记录写出什么
    原样写出api_summary、core_summary[request]；以及任何一段的来源直接读的记录：pd_transfer_summary[request_generation]、pool_task[save]、4 种终态的 pool_task[load]记录原文
    累加core_summary[execution]、worker_summary[phase=execute]、[phase=sample]每个请求一行累计的部分和 pd_seg_partial
    丢弃其余：映射用的 pd_transfer_summary[task]、[link]，pool_task[load_submit]、[save_submit]，非 rank 0 的记录，版本不符的记录等只在自检行里计数

    累加规则的值可以是一个字段路径，也可以是路径列表。列表时取第一个不为 null 的路径；v3.2-extra 里 forward、sampling 和 4 个新段都写成只有一项的列表，只取 device_duration_ns，这一步有这个阶段、却没有设备值时，这一步不加，自检行的 acc_fallback 按规则记一次。记录缺 execution_id 时，这条记录自成一步，并把它所属规则的第一步值记为未知（first_ns 为 null），自检计数 exec_missing。

    文件。每个进程按角色各写一个文件：<日志目录>/<实例>/<角色>.<启动时刻>.<pid>.<序号>.log，角色是 api、engine、worker、pool 之一。日志目录取 segments.json 的 line.log_dir，可由环境变量 PD_DIAG_LOG_DIR 改写；实例目录名默认是这个 vLLM 的 --port，监控机按清单把它对应到 P0、D17 这样的实例名。文件满 256 MiB 就关闭、换一个新名字，从不改名；超过 12 小时的文件删除。每个文件的第一行是 pd_file_open，写明文件名，采集器靠首行区分文件。

    习题 4.2

    5口径与局限

    第 1 至第 4 节讲每一段怎样量、怎样算、怎样到达看板；本节讲按定义 1 量出的数在解读时受到的限制，依次是时钟、共享与重叠、设备计时的覆盖面、计时本身的开销，以及第一步多出的时间怎样查。

    5.1 跨机器的钟差与不量的空隙

    每一段都是同一进程或同一台机器上两个时刻之差（1.4 节），所以段值不受机器之间钟差的影响，不需要对时。钟差只影响单请求的时间线。时间线把每一侧放在它自己那台机器的墙钟上：一侧的起点是 api_summary[http] 那一行的时间（精确到毫秒）减去 end_ns − start_ns，P 用 P 机器的钟，D 用 D 机器的钟。两台机器的钟差多少，时间线上两侧就错开多少，P 的结束和 D 的开始之间可能出现负的间隔，看板不做修正。一侧之内，子段从父段的起点开始首尾相接地排列，位置由时长推出，与各段自己的时刻无关；对照行不画，P 的后台保存画在请求路径的各段之后。

    面板只显示日志里量到的段，不跨记录相减，所以凡是要用两条记录的时刻相减才能得到的时间都不上看板：D 上的 G0、G1、G2（3.3 节），P 合计和 D 合计里的未归属时间（只在单请求 JSON 的 checks 里给出差值），以及 proxy 与 P、D 之间的网络时间（proxy 行的 p_total_ms 与 P 合计之差）。proxy 的 6 个时刻都在 proxy 机器的同一个钟上，lb_proxy 两段和 proxy 量的 TTFT、E2E 不受钟差影响。所以段值和合计都在单机时钟上，可以直接用；时间线上两侧的相对位置受钟差影响，只能作参考。

    5.2 共享的步与互相重叠的最大值

    累加的段把整步的值记给这一步的每个请求（1.5 节），lookup、alloc、other、wait_for_put、forward、sampling 和 D 上的 5 个设备段都是这样。一个请求的这些段值是它参与的那些步的时长之和，批次越大，同一段时间被记给的请求越多；各请求的段值相加会重复计数，不能用来估算资源的占用。另外几处共享与此同理：一个保存任务含多个请求时，wait_for_save 及其子段整段记给每个请求；D 上同一步有几个请求一起发起读取时，每个请求的 submit 都是整步的值。

    D 的等 KV 段另有两种重叠。receive_queue、prepare_read 取 16 个任务的最大值，几个最大值可能来自不同的任务，彼此重叠，也和 wait_for_transfer 重叠，所以 start_load_kv 的子段之和与它不相等（3.2 节）。receive_queue 还包括排在同一 P 端口前面、属于别的请求的任务。P 的 wait_for_put 也类似，它等的主要是前面已结束请求的保存（2.3 节）。所以这些段量的是这个请求经历的等待和执行时间，其中有一部分花在别的请求上；比较请求之间的段值没有问题，把段值按请求相加则没有意义。

    5.3 设备计时的覆盖范围

    图模式只记目标模型。cudagraph_runtime_mode 取 runner 已经算好的本步目标模型的图模式。草稿模型自己做一次图分发，用的是它自己的 token 数，只沿用目标模型的 uniform_decode；草稿单独设为 eager 时直接不走图。草稿的图模式不另记，要记就得改 vllm-ascend 的 llm_base_proposer.py，这不在本套补丁里。所以 graph_* 三条规则只说明目标模型这一步走了哪种图。

    只在 rank 0、只在 V1 runner。设备事件只在 TP rank 0 上记，P 的其余 15 个 rank 没有设备值；DP 下空闲 rank 为配合通信跑的空批次不写 Worker 记录，它们不属于任何请求，不影响段值。P 只有 forward、sampling 两段设备时间，P 上的输入准备和草稿都没有段。

    服务期间不捕获计算图。所有计算图在启动时捕获完毕，捕获走的是启动时的空跑路径，不经过 execute_model、sample_tokens，不写 Worker 记录；服务期间遇到没捕获过的形状，分发器直接按 eager 执行，不会再捕获。所以不存在「这一步在捕获图」的情形，设备值缺失只有三种原因：4 步之内没读到，同一步里同一阶段被调用两次，这一步本来就没有执行这个阶段。

    不用主机时长代替。forward、sampling 和 4 个新段都只取设备时长，缺设备值的步对段值没有贡献，过滤器自检行的 acc_fallback 按规则记下次数；第二步起的每步均值用的步数也只计有 forward 设备值的步。首批核对要求稳态下这些计数接近 0。所以 NPU 段只覆盖 rank 0 上被设备事件包住的 6 个阶段，图模式字段只描述目标模型，acc_fallback 接近 0 时段值才完整。

    5.4 开销判据

    T56 把 D 上每一步的设备事件从 2 对（forward、sampling）增加到 6 对，记录事件要花主机时间。判据不另设开销字段，只比较升级前后的 TPOT：用同一组参考请求、同样的并发，升级前（T51 版）和升级后（4 段全开）各跑 3 遍，各取 TPOT 中位数；升级后中位数减升级前中位数大于 max(2% × 升级前中位数, 波动) 时，把 VLLM_PD_DEVICE_STAGES 改成 lm_head,draft；只改环境变量，不重出补丁包，改完照升级手册的停机步骤停整个集群再拉起。波动是同一版本 3 遍 TPOT 的最大值减最小值，升级前后各算一次，取大的。

    2% 是阈值，不是预测：它按 D 每步约 60 ms、每次记事件几十微秒估出，没有实测过。改成 lm_head,draft 以后，prepare_inputs、bookkeeping 两段整段不写，连主机时长也不写，看板上 prepare_inputs 为空，分布表「有值 / 请求」一列显示 0 / n；step_device_span_ns 也不再写（它要求 prepare_inputs 和 draft 都开着），第一步开销分析就少了空隙这一项。计时开销按 TPOT 的变化判断，超过阈值时以关掉两段为代价换回开销。

    本小节数字的出处

    2% 阈值、3 遍、「每步约 60 ms、每次几十微秒」的估算，均出自记录格式约定（glm5.3 版 1.4.0）第 5 节的开销判据，层级为 vLLM 前端的 TPOT（官方计时），场景为 glm5.3 测试集群的 D（TP1、MTP k=5、图模式加异步调度）；基线是升级前的 T51 版。这些都是判据和估算，本讲义没有测量。

    6结论

    本节按框架的顺序重列各节的结论，回答开头的问题。

    1. 一个请求先后经过 proxy、P、proxy、D 四处（图 1），面板二上的每一段都可以用层级、起止、位置、时钟、来源、取值六项完整描述（定义 1）。
    2. P 侧 27 段分布在 proxy 与 API server、EngineCore、Worker 主线程、保存线程四处；到第一个 token 为止的 16 段覆盖了 P 合计的主要部分，未归属部分主要是 P 上的草稿和进程之间的交接；后台 9 段描述这个请求留下的保存工作，它出现在后面请求的 wait_for_put 里。
    3. D 侧 29 段由与 P 同源的前 8 段、等 KV 的 6 段、第一步的 6 段与第二步起的 9 段组成；3 行对照分别对照等 KV、第一步和第二步起。
    4. 只有过滤器和看板查询做计算：过滤器把请求级记录原样写出、把每步记录累加成每请求的部分和，看板按 segments.json 把同一请求的行合成段值；拉取和入库只搬运。
    5. 段值和合计都在单机时钟上，可以直接使用；累加段是请求参与的各步之和，不能按请求相加；NPU 段只覆盖 rank 0 上的 6 个阶段；第一步多出的时间用第一步开销分析定位。

    所以面板二上的每一个数，都是某个进程里两个时刻之差，经五种取值之一算出，沿过滤器、节点目录、拉取程序、Vector、ClickHouse 到达看板；读数时按第 5 节考虑钟差、共享与重叠和设备计时的覆盖面。
