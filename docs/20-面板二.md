## 1. 显示什么

每个装了面板二的集群在 Grafana 里有一个看板「面板二：请求时延拆解（P / D）（<集群>）」，顶部有模型、实例、排序依据、请求 ID 四个选择项；集群有面板一时，另有跳到面板一 Prefill、Decode 两张看板的按钮（说明书 3.1、3.5）。

| 区域 | 内容 |
|---|---|
| 所选时间段概况 | 请求数；官方 E2E（P / D）；官方 TTFT（P / D）；TPOT；P 合计 / D 合计；P 侧轮次、D 侧总步数；P 侧、D 侧分段时延分布（p50、p90、p99、均值、均值占比） |
| 最慢请求 | 按「排序依据」取最慢的 100 个请求，带每侧最大的段；最慢 20 个请求的分段条形图；P、D 两侧的子段明细 |
| 单请求拆解 | 选定一个请求 ID 后，它的官方 E2E、TTFT、TPOT、token 数、P / D 时间线和两侧分段明细 |
| 单请求事件 | 这个请求两侧的请求级记录，按时间排列 |

出处：说明书 3.1；`P2/README.md`「看板上有什么」。「排序依据」在看板定义 `P2/grafana/board_style.json` 里有 5 个选项：总时间（D 官方 E2E）、P 官方 TTFT、P 侧执行最慢（P 侧合计）、D 侧执行最慢（D 侧合计）、TPOT。

**段**是一个请求在某一侧经过的一个阶段。L1 是阶段，L2 是阶段下的子段，L3 是子段下的子段；有下级段的叫父段，父段没有自己的来源时显示子段之和（说明书 3.1）。

显示规则（[40-规则](40-规则.md) P1、P2、P11）：

| 规则 | 内容 | 来源 |
|---|---|---|
| 只显示日志里有的内容 | 每个值都必须能在补丁写出的记录里找到；不按补丁代码反推，不分摊，不估算；日志里没有的段留空，不计入分位数 | 用户决定，2026-11-12（T29） |
| 段严格等于名单 | P、D 两侧的段只能是用户的 L1/L2/L3 名单（包根目录与 dsv4.1 段定义 47 段；glm5.3 段定义另有用户在 T56 加的 D 侧 9 段和 3 行对照，3.9 节）。名单之外只保留 T28 的几项：P 侧轮次、D 侧总步数、最慢 Top-100 的排序、分布统计的查询内存有上限（时间段内请求超过 20 万个时按请求抽样，`P2/README.md`「看板上有什么」） | 用户决定，2026-11-12（T29）；2026-11-16（T40）、2026-11-19（T51）重申 |
| 增删由用户定 | 段名单的增减、显示项和范围由用户决定；取哪个字段、怎样配对这类实现上的取舍由维护者决定，并写进说明书 | 用户决定，2026-11-16（T40） |

另外几点看板行为，都是「只描述、不推断」的直接结果：

- P、D 两侧靠请求头 `X-Request-Id` 配对；proxy 没有给同一个请求的 P、D 发相同的 `X-Request-Id` 时，单请求拆解里另一侧为空（说明书 3.1）。
- 官方 E2E、官方 TTFT 是 vLLM 自己在本侧统计的值，P、D 两侧分列，不相加；客户端视角的 E2E、TTFT 要 proxy 补丁和 proxy 的行（`P2/README.md`「看板上有什么」；说明书 3.6.4 的 C5）。
- 看板只读当前 `segments.json` 的 `config_id` 写出的行（视图 `vllm_pd.phase_line_cur`）；旧版本写的行留在表里，到保留期删掉（说明书 3.2）。
- 记录里有、但段定义不展示的字段（例如 `preemptions`）不加到看板上，需要时到 ClickHouse 的 `vllm_pd.diag_event` 里临时查（说明书 3.6.5「被抢占过的请求」）。

## 2. 由哪些组件组成

### 2.1 数据链路

```
[节点]   打了插桩补丁的 vLLM（mock 模式下是 mock 写入程序）
           │  logger vllm.v1.metrics.pd_diagnostics 写 [PD_DIAG] <JSON>
           ▼
[节点]   过滤器 pd_diag_logfilter.py：在 vLLM 的每个进程里，按 segments.json 挑行；
         请求级记录原样写盘，按步记录在进程里按请求累加、每 5 秒写一行累计值，只留 TP rank 0
           │  写 NODE_LOG_DIR/<实例端口>/<进程>.<启动时间>.<pid>.<序号>.log
           ▼
[监控机] 拉取程序（后台进程，不是容器）：每 10 秒经 SSH + rsync 复制到镜像目录 PULL_DIR
           ▼
[监控机] 采集器 Vector（容器 vllm-pd-vector-<集群>）：读新行、解析，攒批最多 5 秒
           ▼
[监控机] ClickHouse（容器 vllm-pd-clickhouse-<集群>，库 vllm_pd；写账号 vllm_writer）
           ▼
[监控机] Grafana 数据源「vLLM ClickHouse（<集群>）」（只读账号 vllm_reader）→ 面板二看板

旁路：Prometheus 抓拉取程序和采集器的状态，用于告警（glm53-1 用面板一的 Prometheus，test-glm53 用自己的）
v3.1-extra 的两个可选来源（deploy.env 打开时才有）：
  proxy 机器上 proxy 写的行   ──拉取程序──▶ PULL_DIR/_proxy   ──采集器──▶ 表 proxy_line
  vLLM 标准错误里的 Mooncake [BatchPutTiming] 行 ──拉取程序配给缓存池保存记录──▶ PULL_DIR/_native ──采集器──▶ 表 phase_line
```

出处：说明书 1.4（图 1）、3.2（图 3）。从节点写下一行到看板查得到，实验室实测中位数约 10 秒、最长约 16 秒（说明书 3.2）。存储保留期：汇总表 30 天、事件表 15 天，节点日志 12 小时（说明书 1.1、3.2）。

### 2.3 两种模式

模式写在集群 `deploy.env` 的 `NODE_MODE` 里，决定节点上由谁写日志（说明书 3.4）：

| | `NODE_MODE=mock` | `NODE_MODE=vllm` |
|---|---|---|
| 用途 | 机器上还没有接入面板二的 vLLM 时，先把整条链路跑起来 | 读真实 vLLM 的日志 |
| 节点上写日志的 | mock 写入程序 | 打了插桩补丁、写 `[PD_DIAG]` version 2 记录的 vLLM |
| 节点文件怎样加载 | mock 进程自己加载 | vLLM 启动脚本在 `vllm serve` 之前加两行 export（`VLLM_LOGGING_CONFIG_PATH`、`PYTHONPATH`），节点目录的 `conf`（只读）和 `logs` 挂进 vLLM 容器（说明书 7.3） |
| 请求速率 | `MOCK_RATE`（全集群每秒请求数），每个 D 实例不超过 1.5 请求/秒 | 真实流量 |
| 启停 | 监控机上 `bin/nodes.sh start` / `stop` | 随 vLLM |
| 现在用这种模式的集群 | glm53-1 | test-glm53 |

从 mock 切到 vllm 按说明书 10.3 的六步做。只改 `segments.json` 不用重启 vLLM（过滤器每 2 秒查看它的修改时间）；改了 `pd_diag_logfilter.py` 或 `pd_diag_logging.json` 要重启 vLLM 才生效（说明书 3.3）。

## 3. 段

本节 3.1–3.8 按 v3.1-extra 的两份段定义写（47 段）；glm5.3 段定义在 v3.2-extra、v3.3-extra、v3.4-extra 的变化见 3.9 节。

段由 `segments.json` 的 `sides` 定义，这是段的唯一定义处；`P2/scripts/segtree.py` 读它，`P2/scripts/generate.py` 由它生成 ClickHouse 的表、视图和看板（[60-文件地图](60-文件地图.md)）。下表由两份段定义逐个节点列出，层级按段树的深度计（`segtree.py` 的 `level`）：

- 「glm53 段定义」列取自 `P2/profiles/glm53/segments.json`（`config_id` `pd-diag-v3.1-extra-glm53-2026-11-19c`），test-glm53 在用；与 v3.1-extra 包 `e3885b93` 里的同一文件逐字节相同（sha256 前 12 位 `99a6062049ec`）。
- 「包根目录段定义」列取自 `P2/segments.json`（`config_id` `pd-diag-v3-2026-11-16`），glm53-1 在用；与 v3 包 `3e98c2b4` 里的 `segments.json` 逐字节相同（sha256 前 12 位 `86d81d6793c0`）。两份相同时写「同左」。
- `P2/profiles/dsv41/segments.json` 是 dsv4.1 的段定义，段树相同；dsv4.1 已暂停（T51，2026-11-19），它和 glm5.3 的差别见说明书 3.6.4、3.6.5。

两份段定义的段树和 `panel2/tests/t41/test_segments_mock.py` 里的名单 `TREE` 相同（P 侧 proxy 2 段、TTFT 16 段、后台 9 段；D 侧 proxy 1 段、TTFT 13 段、TPOT 6 段），合计 47 段：P 侧 27、D 侧 20；L1 25、L2 19、L3 3。

表中写法：

| 写法 | 含义 |
|---|---|
| `event[键=值].字段` | 这种记录里满足条件的那一条，取这个字段；纳秒值换算成毫秒 |
| 按请求累加 | 过滤器在节点上按记录的 `request_ids` 把每一步的值累加给这一步的每个请求，写成累计行；「取合计」是所有步之和，「取第一步」「取第二步起」把 D 的第一步和其余各步分开 |
| 首次候选那一步 | 调度器第一次挑中一个请求的那一步；这一步的记录不带请求号，过滤器按写明「请求号、步骤编号」的映射记录（段定义的 `candidate`）把它计给请求（说明书 3.6.3、3.6.4 的 C2） |
| ＋ | 几项来源相加。P 的 `start_load_kv/submit`（glm53）的 4 条按终态区分，一条记录只对得上其中一条（说明书 3.6.5 的 C11） |
| 父段，子段之和 | 段本身没有来源，显示子段之和 |
| 空（无来源） | 段定义里 `src` 为 `null`：日志里没有这一段的计时，看板上为空 |
| proxy 行 | v3.1-extra 打了 proxy 补丁的 proxy 每个请求写的一行，`deploy.env` 的 `PROXY_COLLECT=1` 时才采（说明书 3.2） |
| `pd_native_put` | 拉取程序把 Mooncake 的 `[BatchPutTiming]` 行配给缓存池保存任务以后写出的记录，`MOONCAKE_LOG_COLLECT=1` 时才有（说明书 3.2、3.6.4 的 C4、C10） |
| `device_duration_ns` | 设备上的计时；glm53 段定义的 forward、sampling 只取它，一步没有设备值时这一步留空，不退回 host 侧的 `duration_ns`（说明书 3.6.5 的 C15） |

## 7. 怎么加集群

装一个集群的核心是一条命令 `bin/panel2_cluster.sh add <集群> …`，在部署包目录里执行；它依次做 `P2/README.md` 的步骤 3–18：导入镜像、预检监控机和节点、启动 ClickHouse 和采集器、装插件、导入数据源和看板、写 Prometheus 段、下发节点文件、节点自检、mock 模式下启动 mock、启动拉取程序、升级安全检查。可以重复执行，内容不变的步骤跳过（说明书 13.1）。

| 情况 | 做法 | 详见 |
|---|---|---|
| mock 模式、已有面板一的集群（如 glm53-1） | 一条 `add`：`--mode mock`，`--inventory` 用面板一的清单，`--env-from` 已装集群的 `deploy.env`，`--set` 写 `MOCK_RATE` 和两个磁盘门槛 | 说明书 10.1 |
| vllm 模式、没有面板一的集群（如 test-glm53） | 取端口基数（`names.py alloc`）→ 写清单（[`tools/make_inventories.py`](../tools/make_inventories.py)）→ 起这个集群自己的 Prometheus → `add --mode vllm --set SEGMENTS_PROFILE=glm53 --env-from <glm53-1 的 deploy.env>` → vLLM 一侧打补丁、加两行 export 和两个挂载、重启 → `arrange_boards.py apply` → 打开两个可选来源 → 检查 | 《新增 test-glm53 集群操作说明》；操作手册第 11–22 步 |

前提（说明书 10.1）：新集群的机器不属于任何已有集群；监控机能免密 SSH 到这些机器；数据目录所在盘的剩余空间够两个磁盘门槛。装完以后执行一次 `arrange_boards.py apply`（[40-规则](40-规则.md) P6）。

相关操作：卸掉一个集群见说明书 10.2（vllm 模式的集群不删正在写的日志，另有逐条做法）；从 mock 切到 vllm 见 10.3；用更新脚本升级和回滚见 10.4；日常操作、重启以后和排障见第 9、12、15 节；查问题先用只读的 `bin/diag.sh all`（10.5）。在用手册的索引见 [`manuals/README.md`](../manuals/README.md)。

## 8. 怎么改

### 8.1 先分清改的是什么

| 改动 | 谁定 | 做法 |
|---|---|---|
| 段名单、显示项、范围（加段、删段、加一个整请求指标、看板上加说明文字等） | 用户 | 不由维护者自行增删；记录里有、但 47 段不展示的字段需要看时，到 ClickHouse 临时查（第 1 节末） |
| 某一段取哪个字段、多条记录取哪一条、怎样配对 | 维护者 | 改段定义或代码，写进说明书 3.6 的口径，并有测试支撑 |
| 补丁写出的记录格式 | 补丁与面板二两边 | 按《记录格式约定》第 0 节：行格式不变、只做加法、不新增 `event` 种类、新增字段要写明核对用途；改约定先经两边确认（[01-全景](01-全景.md) 第 6 节） |

### 8.2 日志变了：改 `segments.json`

`segments.json`（version 2）是唯一的映射文件，监控机和节点用同一份（`P2/README.md`「映射规则：日志变了怎么改」）。

- **只改这个文件就够的：** 事件或字段改名，条件增减，新增一个「直接取字段」「两个字段相减」「按 `request_ids` 逐步累加」形状的段，换 TP rank。
- **要改代码的：** 新的归属规则（例如按 token 数分摊）、新的进程类型。v3.1-extra 加的 `candidate`、`shared_members`、`missing_execution_id`、路径列表形式的累加字段都属于这一类，键的含义见说明书 13.4。
- **按环境分的差别只放在各自的段定义里，代码相同**（说明书 3.3）：glm5.3 的差别在 `P2/profiles/glm53/segments.json`；包根目录的 `segments.json` 是 v3 的那一份，读现有日志的行为和 v3 相同（说明书开头「本版相对 v3 的改动」）。
- **口径变了就换 `config_id`。** 看板只显示新 `config_id` 写的行，数值和旧数据不可比；glm53 段定义用末尾字母区分各版（第 5 节）。
- **改完在集群目录里执行** `bin/vector_test.sh && bin/apply_segments.sh`：加列、重建视图、重新导入看板、按新规则重启采集器，并把 `segments.json` 下发到所有节点，过滤器两秒内重读，vLLM 不用重启。新列对旧请求为空（`P2/README.md`「映射规则」）。部署到内网时不手改集群目录里的文件，而是出新包、用更新脚本换包：升级安全检查把 `segments.json` 和包里的校验值比较，手改了就固定报 FAIL（说明书 13.4）。

## 9. 怎么出包

出包只有一条路径：`panel2/tests/t41/build_pack.sh` 打部署包，`panel2/tests/t41/pack_dist.sh` 组装交付目录。demo 目录的 `tools/build_panel2_pack.sh` **废弃**，不在本仓库，不再使用。

| 脚本 | 用法 | 做什么 |
|---|---|---|
| `build_pack.sh` | `build_pack.sh <输出目录> [提交，默认 HEAD]` | 从一个提交 `git archive` 出 `vllm-pd-grafana-panel2/`（工作区里未提交的文件不会进包）；运行一次 `scripts/generate.py`，`segments.json` 有错时在这里失败；去掉 `generated/`、`.gitignore`、`__pycache__`；写 `SHA256SUMS` 和 `MANIFEST.txt`（版本、打包时刻和提交、组件版本、每个文件的字节数和 sha256）；打成属主为 root、不带 macOS 元数据的 `vllm-pd-grafana-panel2.tar.gz`，旁边写 `.sha256` |
| `pack_dist.sh` | `[TAR_FROM=<走查用的 tar 所在目录>] pack_dist.sh <输出目录> [提交]` | 组装交付目录：设了 `TAR_FROM` 时用实验室走查过的那个 tar，并逐个文件核对它就是该提交的包，否则调用 `build_pack.sh` 新打；把 tar 的 sha256 写进两份更新脚本的 `P2_SHA`；填手册里【待打包填】的字节数和 sha256，生成已填路径版；写交付清单；最后做泄漏检查（用户目录只允许出现在两份已填路径版里，tar 和其余文件里没有） |

要点：

- **交付的是走查过的原件。** `MANIFEST.txt` 带打包时刻，重新打包的 sha256 一定不同；所以交付时用 `TAR_FROM` 指向实验室走查用的 tar，Release 里放的也是这个原件（`pack_dist.sh` 开头注释；[`releases/README.md`](../releases/README.md)）。
- **`pack_dist.sh` 是按 v3 的交付目录写的**：它组装的是 v3 的交付目录（`包二-v3/`），读 `docs/v3/` 下的手册和 `docs/v3/fill_guide.py`。`e3885b93` 的 `MANIFEST.txt` 和 `build_pack.sh` 写出的格式相同（`built: 2026-11-19T08:48:35Z from 7ef24eb`）；它所在的 v3.1-extra 交付目录不是由 `pack_dist.sh` 组装的，开发仓库里没有组装它的脚本。
- **在本仓库里运行（按代码看，未在本仓库运行过）：** `build_pack.sh` 用 `git -C panel2 archive … vllm-pd-grafana-panel2`，在子目录里按当前目录取路径，和开发仓库的效果相同；`pack_dist.sh` 用 `git show "<提交>:update/<文件>"` 读更新脚本，这种写法的路径从仓库根目录算起，而本仓库里更新脚本在 `panel2/update/`；它还要读已填路径的更新脚本 `update/vllm_pd_update_pack2_filled.py` 和 `docs/v3/已填路径/` 下的文件，这些不进 git（[`panel2/README.md`](../panel2/README.md)）。
- **出包以后**：核对 sha256，打 tag、建 Release，把 sha256 记进 `releases/<tag>/SHA256SUMS`，做法见 [`releases/README.md`](../releases/README.md)。
