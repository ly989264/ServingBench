# 规则

本文列出维护面板一（服务侧 P/D 看板，Prometheus）和面板二（请求时延 L1/L2/L3：节点过滤 → 监控机拉取 → Vector → ClickHouse → Grafana）时必须遵守的规则。这些规则大多无法从代码推出，来自历次任务中用户的决定和现场、实验室里踩过的坑。

每条写三项：**规则**（要做什么、不做什么）、**原因**（为什么）、**日期与来源**（任务编号；「用户决定」指用户本人定的）。编号前缀：P 产品规则，L 看板版式，T 技术陷阱，M 手册规则，E 实验室操作，X 镜像与内网。

已知问题和待办见 `docs/50-已知问题与待办.md`；面板二的「不要做的事」另见 `docs/面板系统说明书.zh-CN.md` 第 14 节，本文不重复。

## 一、产品规则

### P1 面板二只显示日志里有的内容，不推断

- **规则：** 面板二的每个值都必须能在补丁写出的日志记录里找到。不按补丁代码反推，不分摊，不估算；日志里没有的段留空。不向写日志的同事追问缺段是否有意，也不为补缺向用户要日志。真实 P/D 上出现、但样例日志里没有的记录，在用户提供这样的日志之前不处理。
- **原因：** 用户要求看板如实反映日志。此前按推断补出的段（例如同事脚本里 7 个「（并行）」段）被用户质疑过。
- **日期与来源：** 2026-11-12，T29（接同事第二版 `[PD_DIAG]` 日志），用户决定；T28 同期提出「（并行）」段的问题。

### P2 段严格等于用户的 L1/L2/L3 名单加 T28 各点，不增不减

- **规则：** P、D 两侧的段只能是用户给的 L1/L2/L3 名单（T51 方案统计为 47 段）。名单之外只保留 T28 的几项：P 侧轮次、D 侧总步数、Top-100 的三种排序（总时间、P 侧执行、D 侧执行）、分布统计的内存有上限。日志变细了也不因此加段；名单以外的显示项（例如整请求的 TTFT、客户端侧 TTFT/E2E、proxy 时间线、看板上的段说明文字）都不加，是否增加由用户定。段的口径写进说明书，不写在看板上。
- **原因：** 用户多次拒绝名单以外的指标和显示项。看板只按新的 `segments.json` 重新生成，名单内原来为空的段在补丁到位后开始有值。
- **日期与来源：** 2026-11-12，T29，用户决定；2026-11-16，T40（包二 v3），用户重申「段严格按名单」；2026-11-18 至 11-19，T51，用户决定（撤回概况区客户端 TTFT/E2E、proxy 骨架和看板说明文字）。

### P3 升级只按升级安全设闸，mock 和测试数据的准确性不设闸

- **规则：** 更新脚本的 `check` / `run` 只检查升级安全：版本、配置、容器、看板，以及数据在流入。mock 数据和测试数据是否准确、P/D 是否配得上，放在另外的功能检查（`bin/panel2_cluster.sh quality`）里，只报告、不拦升级。现场被非必要的检查卡住时，先给一个可以手工执行的绕过办法（在副本上试过，附预期 sha256 和恢复命令），再离线查原因。
- **原因：** 2026-11-13 内网升级时，包一的更新被面板二 mock 数据的完整率和配对检查拦了多次，现场来回诊断约八轮；用户明确说不关心 mock 数据，准确性另做检查。按这一原则，包二 v3 起升级和回滚直接删掉该集群的请求数据、从空开始（说明书第 16 节第 20 条）。
- **日期与来源：** 2026-11-13，T32，用户决定；2026-11-16，T40，用户重申「测试数据不拦升级，不设日志流、数据流闸门」。

### P4 补丁必须在检测到的目标环境上验证

- **规则：** 面板和每一份补丁都必须在环境检测得到的目标环境上能正确运行，不得带入其他版本的残留。移植类交付要附：调用图比对（移植前后各方法调用了谁）、对目标基线版本做内部 API 存在性检查、现场每一项事实（版本、调度器、async、MTP、TP/DP、现场本地补丁）与其验证方式的对照。实验室测试尽量用现场的 Python 和包版本；装不上时写明哪个版本、为什么。
- **原因：** T51 中发现 vLLM 移植里有 v0.32 的残留：n>1 时子请求不再经过 `AsyncLLM._add_request`，现场 P 上的长度校验包装对子请求失效。签名检查查不出，只有对 v0.30.0 的调用路径比对查出了这一处。
- **日期与来源：** 2026-11-19，T51，用户决定（同事补丁原本针对 v0.32，用户已提供 glm5.3 环境信息和多轮检测结果，要求整包在 glm5.3 上正确运行）。背景：2026-11-16（T40）时补丁只作参考、面板二升级不管补丁；2026-11-18 起 T51 由用户决定由本项目适配并给出容器内打补丁的做法。

### P5 面板读取的每个数据来源都要有补丁、手册步骤和现场核对

- **规则：** 交付面板相关的包之前，逐一核对面板读取的每个来源（vLLM、vllm-ascend、Mooncake、proxy）：有补丁，有手册步骤，有在目标现场的核对办法。一份手册写「这些值来自另一份手册」时，要确认另一份手册确实产出这些值。
- **原因：** T51 的 glm5.3 打补丁包覆盖了 vLLM、vllm-ascend、Mooncake，但没有 proxy 补丁；面板手册第 17 步却默认 proxy 已打补丁。两段 LB proxy 段和 42 段的覆盖数都以 proxy 已打补丁为前提。用户要求补上 proxy 补丁，输出直接写进节点日志目录，由现有拉取程序收走。
- **日期与来源：** 2026-11-19，T51 / T53，用户决定。

### P6 每次 add / update / rollback 之后执行一次 `arrange_boards.py apply`

- **规则：** Grafana 看板按两层文件夹组织（模型组 / 集群，例如 `GLM-5.3/glm53-1`、`dsv4.1-flash/dsv4.1-flash-1`）。对这些集群做任何 add、update、rollback 之后，执行一次 `tools/arrange_boards.py apply`。
- **原因：** 用户选的方案 A2 让注册表和各 `deploy.env` 的 `MODEL_GROUP` 等于子文件夹名，两个包本身不改。而两个包的 `folder_uid` 只找标题为 `MODEL_GROUP` 的顶层文件夹，找不到就新建，并以覆盖方式导入，所以每次 add、update、段定义下发都会把看板挪回顶层。整理命令把它们移回父文件夹 / 子文件夹，并改 dsv 看板的标题。
- **日期与来源：** 2026-11-17，T45，用户决定（方案 A2）。

### P7 包一 v1.0 的更新脚本写死 GLM-5.3，停用，不再执行

- **规则：** 包一 v1.0 的更新脚本（`vllm_pd_update.py` 及其已填路径版）不再执行；面板二的升级只用包二当前版本的更新脚本。
- **原因：** 包一 v1.0 的更新脚本把模型组写死为 GLM-5.3，看板分层以后再执行会把看板放回错误的文件夹；包二 v3 起的更新脚本从注册表读模型组。另见说明书第 14 节第 7 条（不要用 11-14 以前的备份和 11-13 手改过的旧更新脚本）。
- **日期与来源：** 2026-11-17，T45。

### P8 面板一出包用 `NO_EXPORT=1`

- **规则：** 打面板一的部署包一律执行 `NO_EXPORT=1 tools/build_pack.sh`。看板以 `grafana/dashboards/` 里的合并基线为准，不从演示页重新导出。
- **原因：** T26 起看板是合并基线（重建的基线加上内网已有的改动），不是演示页的导出；默认的导出步骤会覆盖合并后的看板。本仓库的 `panel1/tools/build_pack.sh` 没有导出脚本，不带 `NO_EXPORT=1` 时直接拒绝执行。改了 `names.py` 时要从面板二包重新拷一份再出包。
- **日期与来源：** 2026-11-12，T26。

### P9 面板一的修改只在开发侧做，内网不再手改

- **规则：** 面板一看板的改动只在本仓库里改、出包、交给现场整套部署，现场不在 Grafana 界面或 API 上改。每次整套部署前先用 `tools/panel1/diff_panel1.py` 查现场是否偏离基线（退出码 0 / 1 / 2）。现场出现的新改动走 `diff_panel1.py --decisions-out` → 用户逐条决定 → `--merge`；界面保存产生的噪声没有用户决定不合并。
- **原因：** 用户批准面板一全量替换，并决定此后内网不改、只由开发侧改。现在的 8 套面板一由 `panel1_cluster.sh add` 经 Grafana API 导入（`overwrite: true`），更新一套就是用新包重跑 `add`，界面上的手改会在下一次 `add` 时被覆盖，所以手改本身也留不住。2026-11-12 之前的旧面板一由文件 provider 加载，保存会被文件改回（见 T4）。
- **日期与来源：** 2026-11-12，T26，用户决定；2026-11-11，T23（文件 provider 改回现象）。

### P10 现场值不进 git，示例地址只用 10.1.x.x

- **规则：** 现场值（地址、主机名、用户目录、口令）不进 git；仓库只放占位符版的手册和脚本，已填路径版只放本地（清单见 `docs/50-已知问题与待办.md` 附表）。手册里的示例地址只用手册自己的示例集 10.1.x.x；粘贴实验室输出时把地址换成示例地址并注明。提交前按地址、个人目录、主机名扫一遍。
- **原因：** 本仓库是公开仓库。此前一份说明书的样例输出里带进了实验室地址，被退回重做；已填路径版只在用户明确同意的单个文件上放进过私有仓库。
- **日期与来源：** 2026-11-16，T43（示例地址规则）；2026-11-12，T26（已填路径版只限用户同意的文件）；2026-11-19，T52（仓库公开，用户决定保持公开）。

### P11 段名单和产品范围由用户定，实现上的正确性取舍由维护者定

- **规则：** 段名单的增减、显示项、范围问题交给用户；实现上的正确性取舍（例如取哪个字段、怎样配对）由维护者决定并写进说明书，不交给用户。
- **原因：** 用户在包二 v3 时明确了这一分工，避免把实现细节推给现场。
- **日期与来源：** 2026-11-16，T40，用户决定。

## 二、看板版式

### L1 图例在图的下方

- **规则：** 所有图的图例（各条线的标注）放在图下方，不放右侧。折线图、状态时间线每行一张、宽度占满（T27 起 `w=24`）。
- **原因：** 用户认为右侧图例很难看，整版被否决。
- **日期与来源：** 2026-11-05，T14（v2 被否决），用户决定；2026-11-12，T27（折线图一行一张，D 侧图例移到下方）。

### L2 一个实例下拉框，名称 P0..Pn / D0..Dm 按清单参数计算

- **规则：** 每张看板只有一个实例下拉框，一个 DP 就是一个实例，按清单里的位置连续编号为 P0..Pn、D0..Dm。名称由清单参数（每侧的 API server 列表、每实例进程数）计算，不写死。
- **原因：** 用户不接受实例和 DP 两个下拉框，并明确要求按参数计算（不同集群形态不同：glm5.3 为 P 8 台 × 1 实例、D 4 台共 64 实例；dsv4.1 为 P 4 台 × 2 实例、D 2 台共 16 实例）。
- **日期与来源：** 2026-11-05，T14，用户决定；集群形态 2026-11-18，T51，用户给出。

### L3 P 看板不设 D 过滤，D 看板不设 P 过滤

- **规则：** P 看板上没有 D 一侧的过滤项，D 看板上没有 P 一侧的过滤项。
- **原因：** 为照顾总览而加的对侧过滤器让看板变乱，被用户否决。
- **日期与来源：** 2026-11-05，T14，用户决定。

### L4 一个总览分组

- **规则：** 每张看板只有一个总览分组，不分子组，自上而下依次为资源、请求、吞吐、时延。面板尺寸统一，每行排满。
- **原因：** 同 L1，用户要求版面整齐。
- **日期与来源：** 2026-11-05，T14，用户决定。

### L5 看板上只放真实的面板元素

- **规则：** 看板上不加解释性文字；口径、段的含义写进说明书。
- **原因：** 用户要求展示页只显示真实面板元素；T51 中曾提出的看板段说明被撤回。
- **日期与来源：** 2026-11-04（任务编号未核实），用户决定；2026-11-18，T51，用户重申。

## 三、技术陷阱

前三条必须记住；其余按出处列出。说明书已写的陷阱不在此重复。

### T1 停 Vector 用 `docker stop -t 60`，不能 `docker rm -f`

- **规则：** 停采集器（Vector）一律先 `docker stop -t 60`，等它正常退出；不要直接 `docker rm -f`。
- **原因：** 强制删除时 Vector 来不及把磁盘缓冲和读取位点正常落盘，重启后重放缓冲：实验室实测事件表出现重复行，有一次在 TRUNCATE 之后重放了约 15 分钟的数据。
- **日期与来源：** 2026-11-11，T22（子事情 3 实验室走查）。

### T2 节点过滤器每 2 秒重读一次 `segments.json`

- **规则：** 只改 `segments.json` 不需要重启 vLLM；改过滤器代码（`pd_diag_logfilter.py`）或日志配置（`pd_diag_logging.json`）才需要。判断「vLLM 有没有重启」不能看 `segments.json` 的修改时间。
- **原因：** 过滤器按修改时间每 2 秒重读一次段定义（v2.0 的 `pd_diag_logfilter.py` 第 598–610 行；v3 起所有节点过滤器相同）。更新或回滚下发节点文件后，几秒内按步记录的 `config_id` 就会切换，早于任何 vLLM 重启；只有新的过滤器代码和依赖新补丁的段要等重启。已打开文件的文件头仍是旧版本（说明书第 16 节第 5 条）。v2.0 时期的独立诊断工具按 `segments.json` 的时间判断「没有重启」，每次下发后都误报。
- **日期与来源：** 2026-11-13，T32 / T33；2026-11-19，T51 复核。

### T3 ClickHouse 内存上限不能低于 1500 MB

- **规则：** `CLICKHOUSE_MAX_SERVER_MEMORY_MB` 不低于 1500。
- **原因：** 设为 900 MB 时，看板的 Top-20 查询被 ClickHouse 杀掉。
- **日期与来源：** 2026-11-12，T26。

### T4 文件 provider 会改回 API 和界面上的保存

适用范围：只适用于由文件 provider 加载的看板，即 2026-11-12 之前按部署包 README 步骤 1–31 安装的旧面板一（单集群、文件夹「vLLM P/D」）。现在的 8 套面板一经 API 导入，不受此影响，改法是重跑 `panel1_cluster.sh add`（见 `docs/10-面板一.md`）。

- **规则：** 改由文件 provider 加载的看板，要改 provider 读取的 JSON 文件：先备份，再覆盖，等 30 秒，用 `tools/panel1/diag_panel1.py` 和 `diff_panel1.py` 确认（diag 显示改动后连续读取不变，diff 为 0 处）。识别文件加载的看板时，`provisioned` 和 `provisionedExternalId` 两项都要看。
- **原因：** 内网两张面板一看板由文件 provider `vllm-pd` 加载，`allowUiUpdates=true`，Grafana 显示为 `provisioned=False`、`managedBy classic-file-provisioning`，但仍带 `provisionedExternalId`。T23 中经 API 的每次保存都在 4–22 秒后被「预置加载」改回，比实验室复现更严格（实验室只在改文件或重启时改回）。旧的更新脚本只在 `provisioned=True` 时走文件模式，在内网误走 API 路径。`POST /api/admin/provisioning/dashboards/reload` 不重启即可应用 provider 文件的改动，但需要 Grafana 的 server admin，组织管理员会得到 403。
- **日期与来源：** 2026-11-11，T23；2026-11-12，T26（Grafana 12.4.2 实验室）。

### T5 Grafana 嵌套文件夹与 provisioning 的行为

- **规则：** 按下列行为写整理和安装脚本（Grafana 12.4.2 实测）。
- **原因 / 事实：**
  - 嵌套文件夹开箱可用；`GET /api/folders` 只列顶层文件夹；允许同名文件夹；看板的 `folderTitle` 是它所在的最底层文件夹。
  - 带 `folderUid` 重新保存看板即可移动，uid、URL、收藏不变，版本号加 1；文件夹可以移动、改名；Grafana 重启后看板位置不变。
  - 看板、数据源、文件夹的 UID 不允许带点，标题可以；因此内部名用 `dsv41-flash-N`，显示名 `dsv4.1-flash-N` 只放在文件夹标题里。
  - provider 要同时写 `folder` 和 `folderUid` 才能落到嵌套文件夹；`foldersFromFilesStructure` 只用最底层目录名、且只建在顶层；由 provider 加载的看板不能经 API 保存。
- **日期与来源：** 2026-11-17，T45。

### T6 Vector 按首行校验和识别文件，节点日志的首行必须互不相同

- **规则：** 每个日志文件的第一行必须与其他文件不同；回放同一份样例同时当作 P0 和 D0 时，每侧要单独指定 `--instance`。
- **原因：** Vector 的 file source 按首行校验和去重，首行相同的文件被当作已读过而跳过。
- **日期与来源：** 2026-11-07，T14；2026-11-13，T29。

### T7 rsync 拉取的参数

- **规则：** 拉取用 `--append` 的前提是日志文件名唯一、不改名；有 logrotate 或 RotatingFileHandler 轮转时要用 `--inplace`。
- **原因：** 实验室配合 Vector 的 file source 实测：不带参数的 rsync 每轮生成新 inode，Vector 继续读旧的，会丢行；`--inplace` 不丢行，约每两次轮转多出一行，每轮要对整个活动文件做校验。`--append` 发现不了同名文件被截断或复用。
- **日期与来源：** 2026-11-07，T14。

### T8 ClickHouse 在 INSERT 时就丢弃已过 TTL 的行

- **规则：** 测 TTL 时用两行：一行刚好在保留期外，一行刚好在保留期内。
- **原因：** 已超过 TTL 的行在写入时即被丢弃，不会先写进来再被清理；`engine_full` 里显示为 `toIntervalDay(15)`，不是 `INTERVAL 15 DAY`。
- **日期与来源：** 2026-11-11，T22。

### T9 mock 每次进程启动要换新的 `run_id`；mock 速率按 D 实例数定

- **规则：** mock 每次进程启动生成新的 `run_id`（真实 vLLM 就是这样）。`MOCK_RATE` 是整个模型的请求率，每个 D 实例的负担是 `MOCK_RATE ÷ D 实例总数`；v2.1 起留空即取 D 实例总数（每个 D 1 请求/秒），超过 1.5 请求/秒时报 FAIL。
- **原因：** 不换 `run_id` 时，重启后观测 ID 重复，事件视图把不同请求混在一起。mock 的 D 模型每个实例只在约 1.7–2.3 请求/秒以内稳定，超过后积压持续增长、多数请求结束不了；2026-11-13 内网 2 台机器（P 2 个、D 8 个）按 100 请求/秒运行，每个 D 12.5 请求/秒，完整率从 15.8% 降到 0.1%。积压的 D 进程收到 SIGTERM 后长期不退出（v2.1 改为 10 秒后 SIGKILL）。
- **日期与来源：** 2026-11-11，T22（`run_id`）；2026-11-13，T27 / T32（速率、停不干净）。

### T10 图例排序靠补零的 `a_order` 标签

- **规则：** 生成脚本在抓取目标上加补零的 `a_order` 标签，查询写 `sum by (a_order, pd_instance)`。
- **原因：** 图例按 Prometheus 返回的顺序排列，按字典序会变成 D0、D1、D10……
- **日期与来源：** 2026-11-05，T14。

### T11 过滤器在第一条记录到来之前什么都不写

- **规则：** 判断节点过滤器是否装上，看 vLLM 子进程环境里的 `PD_DIAG_INSTANCE_SOURCE`，不能看有没有自检行。
- **原因：** 过滤器在第一条记录打开文件之前不写任何内容，自检行也不写；vLLM 自重启以来一直空闲时，检查只能看到「没有记录」。未打补丁的 vLLM 上，旧过滤器同样静默。
- **日期与来源：** 2026-11-13，T33；2026-11-19，T51。

### T12 节点上不留原始按步记录；日志描述工具要用原始日志

- **规则：** 用 `pdlog-*` 日志描述工具（不在本仓库，见 `docs/50-已知问题与待办.md` 附表 B）比对日志时，输入要用 vLLM 的原始输出，不能用过滤器写出的文件；不要按这类比对报告去「修」`segments.json`。
- **原因：** 过滤器把三种按步记录（引擎一侧的 lookup/alloc/schedule_other，Worker 一侧的 forward/sampling）按设计累加成每请求一行 `pd_seg_partial`，再进 `phase_line` 的 `acc__*` 列；`pool_task` 只把 save 和 load_submit/submission_returned 原样写进 `pool.*.log`，其余丢弃。过滤器装上后 vLLM 标准输出里的 `[PD_DIAG]` 行被去掉，节点上不留原始按步记录。对过滤后的文件做比对，必然报这些记录「被删除」，工具给出的「把 src 改成 null」会把看板清空。rc1 原始日志回放 22 组累加值全等。
- **日期与来源：** 2026-11-18，T50。

### T13 `panel2_cluster.sh remove` 不删集群自己的 Prometheus

- **规则：** 卸掉一个带独立 Prometheus 的面板二集群（例如 test）时，另外手工删它的 Prometheus 容器、数据卷和目录；不要删文件夹，同一模型文件夹里可能还有别的集群的看板。
- **原因：** `remove` 只处理面板二部分；test 的看板放在 glm53-1 的模型文件夹里。
- **日期与来源：** 2026-11-19，T51（《面板二：删除 test、安装 test-glm53 操作手册》第 7 步）。

### T14 `deploy.env` 里的 `CLICKHOUSE_HTTP_PORT` 是空的

- **规则：** 需要 ClickHouse 端口的命令先执行 `bin/lib.sh` 的 `load_env` 取端口，不要直接读 `deploy.env`。
- **原因：** 集群目录的 `deploy.env` 里这一项留空，由 `PORT_BASE` 派生；直接读得到空值，命令没有输出。
- **日期与来源：** 2026-11-19，T51（新增 test-glm53 说明 10.5 的更正）。

### T15 bash 3.2 下变量名后紧跟全角字符时要加花括号

- **规则：** shell 脚本里变量后面紧跟中文或全角标点时写 `${c}：`，不写 `$c：`。
- **原因：** 没有设置 LANG 的 bash 3.2 会把全角冒号当作变量名的一部分。
- **日期与来源：** 2026-11-12，T26。

## 四、手册规则

### M1 每个目的一份线性手册

- **规则：** 内网手册按操作者要做的事拆分，每个目的一份（例如「面板」和「打补丁」各一份）。格式：
  - 第一页不超过一屏：做什么、做完是什么样子；跨手册的总顺序；要准备的现场值；对服务的影响。
  - 步骤连续编号 1..n，不用嵌套节号，不在手册之间跳转。
  - 每步四块：在哪台机器上；照抄的命令；应当看到什么；不对时怎么办（停下，带回哪段输出）。
  - 要带回的输出在步骤里标出，文末汇总成带回清单。
  - 只写这个现场会走的那条路径；不适用的分支、原因、已知问题、没测过的部分放附录，不混进步骤。
  - 命令从走查过的原文逐字照抄；新写的命令先在实验室走查再进手册。
  - 仓库只放占位符版；已填路径版按 P10 只放本地。
- **原因：** 用户在内网逐步照做。此前几份手册带 7.3、11.6 一类的嵌套节号、单独的分支说明和附录 B/B0，用户认为太乱、难以照做，要求改为两份清晰的手册。现场一次只能带出很短的文本，所以带回内容要短、要事先列明。
- **日期与来源：** 2026-11-19，T51，用户决定；2026-11-12，T26（现场只能带回短文本）。

### M2 每步写明执行后马上看到的现象和对同机服务的影响

- **规则：** 每个内网步骤都写明：执行后马上会看到什么（例如看板短时为空、某项检查在 N 分钟内必然 FAIL）；这台机器或这块磁盘上还有哪些服务，重的步骤（大量删除、重启）会对它们有什么影响。
- **原因：** 2026-11-13 给现场的清数据步骤只写了「等 5 分钟」，没写清完以后看板会空几分钟，也没写在监控机（与 Prometheus、Grafana 同机）上删 156 GB 拉取镜像可能影响面板一。现场看到所有面板都没有数据，以为系统损坏，之后两块面板自行恢复。
- **日期与来源：** 2026-11-13，T32。

## 五、实验室操作

### E1 测试容器用 `--rm` 或 `docker rm -fv`，不执行 prune

- **规则：** 一次性测试容器用 `--rm` 启动，或用 `docker rm -fv` 删除（连同匿名数据卷）；清理后核对时也数 64 位十六进制名字的匿名数据卷。不执行 `docker volume prune`、`docker system prune`。
- **原因：** ClickHouse 镜像声明了 `/var/lib/clickhouse` 数据卷，用 `docker rm -f` 删除的测试容器留下约 106 GB 的匿名数据卷，宿主机只剩约 8 GiB；当时的清理核对只按名字前缀找，误报干净。prune 会删掉不归自己的数据卷，是否删除由用户决定。
- **日期与来源：** 2026-11-07，T14。

### E2 在 Docker 中写入数 GB 之前先查宿主机剩余空间

- **规则：** 在 Docker 中写入超过约 5 GB 之前，查宿主机磁盘（不是容器或 Docker 虚拟机内的 `df`），保留至少「写入量 + 30 GB」的空间；不够时缩小测试规模并记录偏差。
- **原因：** macOS 上 Docker 的磁盘镜像是宿主机上的稀疏文件，容器内的 `df` 看不出宿主机还剩多少。一次测试写入 40 GB 轮转日志，宿主机数据卷只剩 147 MiB，containerd 元数据开始报 I/O 错误，所有容器都无法 exec 或删除，直到重启 Docker；重启 Docker 会停掉所有容器，须由用户决定。
- **日期与来源：** 2026-11-13，T32（测试 T-5）。

### E3 读不受信任的日志用 `python3 -I`

- **规则：** 读取现场带回或同事提供的日志、压缩包时，Python 一律用 `python3 -I` 运行，把路径作为参数传入，不在这些文件所在目录里执行解释器。
- **原因：** 解释器会从脚本目录和当前目录加载模块，目录里的同名 `.py` 文件会被当作模块执行；`-I` 不把这些目录放进 `sys.path`，并忽略 `PYTHON*` 环境变量。
- **日期与来源：** 2026-11-19，T52（交接要求，起始日期未核实）；同类做法：T51 的环境检测脚本要求以 `python3 -I -S -B` 运行，否则拒绝执行（2026-11-19）。

### E4 实验室按内网的形态和速率测

- **规则：** 实验室测试按内网的清单形态和配置（机器数、P/D 实例数、`deploy.env`、请求速率）搭建，不只测正常路径：包括负载、积压下停止、异常状态、清数据后马上检查、中途失败、没有请求的空闲期。
- **原因：** 2026-11-13 内网遇到的问题，实验室都没提前发现：实验室是 5 个 D、每秒 4–8 个请求，内网是 8 个 D、每秒 100 个；只测了正常路径；没有 vLLM，也没有替身；说明由作者从理想起点走查。用户要求以后的包不再踩这些坑。
- **日期与来源：** 2026-11-13，T32，用户决定。

## 六、「镜像 = 内网」

### X1 镜像与内网一致由用户本人保障

- **规则：** 实验室镜像（开发机上的一套监控机加节点容器）与内网一致，目前由用户本人保障，没有程序上的证明，交接时不提供一致性证明。同事如需比对，可以自行编写检测脚本。
- **原因：** 用户决定交接只需把现有实现、部署结构等全部信息交出，不需要证明。背景：2026-11-12 起，镜像只用交付给内网的同一批命令更新，不清理、不另行修改；镜像从未从零重建过。已知与内网不同的地方：Prometheus 保留期镜像为 2h（内网 15d，2026-11-18 决定保留）；glm53-1 面板二节点规模缩小；面板一目标为占位主机名、全部 down；test 的来历不同（镜像用 v3 包直接新装，内网由 v2.1 改名再升 v3）；vLLM 在镜像中是替身进程；数据从空库起，不与内网比较。
- **日期与来源：** 2026-11-19，T52，用户决定；2026-11-12，T26（镜像只用交付命令更新）；2026-11-18，T45（保留期）。
