# 术语表

本仓库和交付文档中自造或有特定含义的叫法。按主题排列。

## 面板与包

| 叫法 | 含义 |
|---|---|
| 面板一 | 服务侧看板：Prefill、Decode 两张（标题「Prefill实例（<集群>）」「Decode实例（<集群>）」，早期文档写作「面板一·P」「面板一·D」），数据来自每个集群自己的 Prometheus |
| 面板二 | 请求时延拆解看板：每个请求按 L1/L2/L3 段显示耗时，数据来自 ClickHouse |
| 包一、包二 | 面板一、面板二的部署包及其更新脚本的统称。「包一 v1.0」「包二 v2.0 / v2.1 / v3 / v3.1-extra」指交付批次 |
| v3、v3.1-extra | 面板二的两个在用版本：glm53-1 用 v3，test-glm53 用 v3.1-extra（加了 glm5.3 的段定义、Mooncake 计时等） |
| config_id | 面板二部署包的配置标识，写进每条入库记录，例如 `pd-diag-v3-2026-11-16`；test-glm53 的后缀为 -19c |
| 更新脚本 | 在监控机上把一个面板二集群从上一版升到这一版、并能回滚的单文件 Python 脚本（`vllm_pd_update_pack2*.py`） |
| 离线包 | 面板二在无外网的监控机上安装所需的第三方原件（ClickHouse、Vector 镜像，Grafana 的 ClickHouse 插件，Python standalone） |
| 合并基线 | 面板一两张看板的真源：用户内网看板的导出，加上各轮修改合并后的结果，放在面板一部署包的 `grafana/dashboards/` |

## 集群与部署

| 叫法 | 含义 |
|---|---|
| 集群 | 监控机上一套面板的安装单位，对应注册表中的一条。名字如 glm53-0、glm53-1、glm53-2、dsv41-flash-1…5、test-glm53 |
| 注册表 | 监控机上的 `~/.vllm-pd-clusters.json`（format `vllm-pd-clusters` version 1），记录每个集群的面板、目录、端口基数、模型文件夹 |
| 模型文件夹、`MODEL_GROUP` | Grafana 中第一层文件夹（GLM-5.3、dsv4.1-flash），第二层为集群文件夹。部署包只认顶层文件夹，整理靠 `arrange_boards.py` |
| 内部名与显示名 | 集群内部名不能带点（部署包和 Grafana UID 都不接受），所以内部名为 `dsv41-flash-N`，文件夹和看板标题显示为 `dsv4.1-flash-N` |
| 端口基数 | 一个集群在监控机上占用的一段端口的起点（如 18100、18120），由 `names.py` 分配 |
| `<ROOT>` | 各集群目录的根，监控机上为 `/data/grafana`；面板一目录为 `<ROOT>/vllm-pd-grafana-panel1/<集群>`，面板二为 `<ROOT>/vllm-pd-grafana-panel2/<集群>` |
| `<用户目录>` | 用户在监控机上的个人目录，存放交付包和工具；现场值不进本仓库 |
| mock 模式、vllm 模式 | 面板二 `NODE_MODE`：mock 为节点上运行 mock 日志写入器（没有接真实 vLLM）；vllm 为读取真实 vLLM 经过滤器写出的日志 |
| 现场值 | 只在内网有意义、不进仓库的值：内网地址、主机名、用户目录、口令 |
| 占位符版、已填路径版 | 同一份手册或脚本的两个版本：占位符版写 `<用户目录>` 等；已填路径版把用户目录等填成现场值，只放本地 |

## 面板二的数据

| 叫法 | 含义 |
|---|---|
| `[PD_DIAG]` | 补丁在 vLLM 日志中写出的诊断记录的行首标记，每行一条 JSON 记录 |
| 记录 | 一条 `[PD_DIAG]` JSON，按 `event` 分种类（如 `api_summary`、`core_summary`、`worker_summary`、`pool_task`、`pd_transfer_summary`），格式由《记录格式约定》规定 |
| 《记录格式约定》 | 补丁与面板二之间的接口文档（glm5.3 版 1.3.3），`contracts/` 下；条款编号 C1、C2…（如 C11–C15）在交付说明中引用 |
| 段 | 请求耗时中的一段，由 `segments.json` 定义：从哪种记录的哪个字段取值、属于 L1/L2/L3 哪一层 |
| L1 / L2 / L3 | 用户给定的三层段名单；L1 为最粗的阶段，L2、L3 逐层细分。包根目录与 dsv4.1 段定义 47 段，glm5.3 段定义 v3.2-extra 起 56 段 |
| 对照行 | glm5.3 段定义里 vLLM 自己的统计值（`queued_time`、`prefill_time`、`decode_time`），放在对应的段旁边比较，不是段，不算占比、不进合计（v3.2-extra 起） |
| else 行 | v3.4-extra 起 P、D 分布表合计正上方的一行：本侧合计减各一级段，小于 0 记 0 |
| `PD_DIAG_LEVEL` | 补丁的记录粒度（1、2、3，缺省 3），T58 起；段定义里每段的 `from_level` 说明从第几级起记 |
| T28 各点 | 任务 T28 中用户另加的几个时间点，与段名单一起构成面板二的全部显示内容 |
| 过滤器 | 节点上随 vLLM 日志配置加载的 `pd_diag_logfilter.py`：只把段要读的记录写到节点日志目录，每 2 秒重读一次 `segments.json` |
| 拉取 | 监控机上的拉取进程（`puller.py`）经 SSH 用 rsync 把各节点日志目录镜像到监控机，供 Vector 读取 |
| 替身 | 实验室中代替真实 vLLM 进程、按相同方式写日志的小程序 |

## 开发与交付

| 叫法 | 含义 |
|---|---|
| T 编号 | 开发侧的任务编号（如 T26 多集群、T45 看板分层、T51 glm5.3 接入），文档中用来标注规则和决定的来源 |
| 交付 | 把包、更新脚本和手册放进私有交付仓库（Caching 仓库 ServingBench 分支），由用户带进内网执行 |
| 带回 | 用户在内网执行手册后，把手册要求的输出（RESULT 行、检查结果）发回开发侧 |
| 实验室 | 开发机上用 Docker 搭的「内网形态」环境：监控机容器（自带 dockerd）、节点容器、mock exporter。一次性实验室每次测试新建、测完删除 |
| 实验室镜像 | 开发机上长期保留的那套实验室（容器名前缀 `t14p2-`），只用交付给内网的同一批命令更新；它与内网的一致目前由用户本人保障 |
| 走查 | 在实验室里按手册原文逐步执行一遍，记录每步输出；交付的 tar 是走查用过的那一份 |
| 线性手册 | 内网手册的格式：每个目的一份，第一页一屏，步骤 1..n，每步写「哪台机器、命令、应看到、不对怎么办」，最后是带回清单 |
| 升级安全设闸 | 更新脚本只在影响升级安全的项目（版本、配置、容器、看板、数据在流入）不满足时停下，不因 mock 或测试数据的准确性停下 |
