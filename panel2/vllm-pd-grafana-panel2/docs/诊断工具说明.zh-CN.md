# 面板二诊断工具说明

`bin/diag.sh` 诊断一个已经装好的面板二集群，mock 模式和 vllm 模式都适用。它回答「环境哪里不对、怎么修」，不判断数据准不准（那是 `bin/panel2_cluster.sh quality`），也不拦升级（那是 `bin/panel2_cluster.sh check`）。

**只读：** 除 `pair` 以外，各子命令只读：

- 不写集群目录（包括 `generated/`），不调用 `verify.sh`；
- 不重启、不停止、不修改任何服务。

报告写在集群目录以外的 `~/vllm-pd-diag-reports/<集群>/`。`pair` 会经 proxy 发 3 个短请求，见第 8 节。

**和 `check` 的关系：** 节点文件的 sha256、mock 进程数、过滤器版本的期望值、「这次启动以后有没有记录」、日志量估算、链路的阈值，这几项判据由 `scripts/criteria.py` 提供，`check` 和 `diag.sh` 共用同一个函数，所以同一时刻对同一个集群给出相同的判断。

## 概要

以下命令都在监控机上、集群目录里执行（集群目录就是 `bin/panel2_cluster.sh add` 建的那个目录，比如 `/data/grafana/vllm-pd-grafana-panel2/<集群>`）。

| 情况 | 命令 | 看哪一行 |
| --- | --- | --- |
| 看板空了、数据断了、升级前自查 | `bin/diag.sh all` | 最后一行 `RESULT`；`FAIL` 行 `→` 后面是修法 |
| vllm 模式下 `[PD_DIAG]` 仍在标准输出，或日志目录没有文件；切到 vllm 模式、重启 vLLM 以后确认 | `bin/diag.sh vllm` | 每个容器的「结论」一行 |
| 看板上请求只有 P 或只有 D | `bin/diag.sh pair <proxy 地址:端口>` | `OK` / `FAIL` 一行 |
| 事后查某一段时间断没断 | `bin/diag.sh history "2026-11-13 10:30" "2026-11-13 12:00"` | 各台、各 job 的 `WARN` |
| 拿到一份新的 vLLM 日志，要知道格式变没变 | `bin/diag.sh log <日志文件>` | `FAIL` 和「和已知样本不同」几行 |

样例输出来自实验室，地址 `10.97.1.1`（P 机器，P0、P1）、`10.97.2.1`（D 机器，D0–D7）、`10.97.0.10`（proxy）都是实验室地址，集群名 `glm53-1`。

## 1. 准备

### 1.1 在哪里执行

- **机器：** 监控机，用平时执行 `bin/panel2_cluster.sh` 的那个用户。
- **目录：** 集群目录。`bin/diag.sh` 只诊断它所在的那个集群，不需要也不接受指定别的集群目录。
- **Python：** 和包里别的脚本相同：先用 `deploy.env` 的 `PYTHON`，再找 `PATH` 里 3.9 及以上的，都没有时用包里自带的。不需要装别的包，不生成 `__pycache__`。

```bash
cd /data/grafana/vllm-pd-grafana-panel2/<集群> && bin/diag.sh -h
```

### 1.2 配置

诊断工具没有单独的配置文件，只读集群目录里的 `deploy.env`、`inventory.json`、`segments.json`。和诊断有关的两项：

| `deploy.env` 的项 | 填什么 | 留空时 |
| --- | --- | --- |
| `NODE_VLLM_CONTAINERS` | 每台节点上 vLLM 的容器名，`地址=容器名,地址=容器名`；一台有几个容器时，容器名之间用分号 | 在每台节点上自己找，见下 |
| `NODE_VLLM_STDOUT_FILES` | 启动脚本把 vLLM 的标准输出 `tee` 进文件、`docker logs` 看不到时，填 `地址=文件路径,…` | 标准输出看 `docker logs` |

**容器名自己找：** 某台没有写进 `NODE_VLLM_CONTAINERS` 时，按下面的顺序在那台上找，前一步找到就停。找法和 `bin/nodes.sh selfcheck` 相同。

1. `docker ps` 里命令含 `vllm` 的容器；
2. 宿主机上 `vllm serve` 进程所在的容器（按进程的 cgroup 对回容器）；
3. 运行中的容器里有 vLLM 启动形态的进程（`docker top` 里有 `vllm serve` 或 `vllm.entrypoints`）。

找到的容器名写在输出里：

```text
INFO 10.97.2.1 找到 vLLM 容器 <容器名>（容器里有 vllm 进程）；不对时填 deploy.env 的 NODE_VLLM_CONTAINERS
```

找得不对时，把正确的名字填进 `NODE_VLLM_CONTAINERS`。一台节点上跑着几个集群的 vLLM 时，也要填这一项。

**命令行优先：** 临时换一组容器或标准输出文件时，在子命令前加：

```bash
bin/diag.sh --containers 10.97.1.1=<P 的容器名>,10.97.2.1=<D 的容器名> vllm
```

```bash
bin/diag.sh --stdout-file 10.97.2.1=<D 的标准输出文件> vllm
```

### 1.3 权限

- **监控机：**
  - 读集群目录里的 `deploy.env`、`inventory.json`、`segments.json`；
  - 能执行 `docker exec` 进 ClickHouse 容器，查询时都加 `--readonly=1`；
  - 能访问本机的 Prometheus、Grafana 和拉取程序的端口。
- **节点：**
  - SSH 用户、端口、密钥和 `bin/nodes.sh` 相同，取自 `deploy.env`；
  - 查容器时，SSH 用户要能执行 `docker`：在 docker 组里，或能免密 `sudo docker`。不能时写 `WARN`，改用宿主机能看到的进程判断；
  - 读 vLLM 进程的环境变量时，`docker exec` 进容器的默认用户要能读 `/proc/<pid>/environ`（默认用户是 root 时可以）；
  - 查内存耗尽和磁盘满时，要能读系统日志：root 或 `adm` 组。

## 2. 子命令一览

| 子命令 | 查什么 | 什么时候用 |
| --- | --- | --- |
| `all` | 依次执行 `nodes`、`vllm`（vllm 模式，或填了容器名时）、`chain`、`monitor`；屏幕上最多 40 行，`FAIL`、`WARN` 优先 | 第一步；升级前自查 |
| `nodes` | 每台节点：<br>· 开机时间、时钟差、内存；<br>· 日志盘空闲，按拉取字节数估 `keep_hours` 小时的日志量；<br>· mock 模式：速率、mock 进程数、主循环卡没卡；<br>· 三个节点文件的 sha256 和监控机比；<br>· 系统日志里的内存耗尽和磁盘满；<br>· 各台的 `/data` 是不是同一块盘 | mock 不写、节点重启过、怀疑磁盘满 |
| `vllm` | 每个 vLLM 容器：<br>· 挂载；<br>· 标准输出在不在 `docker logs` 里；<br>· 主进程和子进程的环境变量；<br>· 变量指向的目录里有没有三个文件；<br>· 过滤器创建了没有；<br>· 标准输出里这次启动以后还有没有 `[PD_DIAG]`；<br>· 启动时的 logging 报错；<br>· 过滤器文件在 vLLM 启动以后换没换过内容。<br>最后给一行「结论」，见第 5 节；再按实例判过滤器版本 | 切到 vllm 模式以后；重启 vLLM 以后；看板在 vllm 模式下没有数据 |
| `chain` | 数据经过的每一段：<br>· 节点日志的最新一行；<br>· 拉取程序；<br>· 监控机上的镜像；<br>· ClickHouse 每个实例的最新一行；<br>· 采集器的缓冲积压、解析失败；<br>· 过滤器出错数；<br>· 过滤器丢掉的空键记录数（取键字段为空的记录，各进程从启动累计）。<br>vllm 模式下，先按实例判「这次启动以后有没有记录」，见 4.4 | 看板有一部分实例空 |
| `monitor` | 监控机：<br>· 镜像盘，按拉取字节数估日志量；<br>· ClickHouse 和 Prometheus 的数据盘；<br>· 各容器的状态、重启次数、内存耗尽；<br>· 拉取程序；<br>· Prometheus 的目标、Grafana 的健康状态；<br>· 内存 | 看板整个打不开、某个面板没有数 |
| `history "<起>" "<止>"` | 一段时间里：<br>· 每台拉到的字节数什么时候降到 0；<br>· 每个 Prometheus job 什么时候 `up` 为 0、抓取耗时；<br>· 解析失败。<br>时间是监控机的本地时间，6 小时以内每 60 秒一个点，更长每 300 秒一个点 | 事后查「昨晚几点断的」 |
| `log <文件> [--save-profile]` | 一份 vLLM 日志：<br>· 格式校验（`tools/check_pd_diag_format.py`）；<br>· 面板二读的 9 种记录在不在：原有的 7 种缺一种就是 FAIL；新补丁的 `pool_task[task]` 只在 P 侧有，`pd_transfer_summary[request_generation]` 只在 D 侧有，两种都没有时是 WARN（这份日志不是补丁 01、02 写的）；<br>· 共用缓存池任务（多个请求共用、只带 `request_ids` 的 `pool_task`）的条数；<br>· 和已知样本（`samples/profiles/` 里 11-12 的 `server.log`、11-16 rc1 的 `P.log` 和 `D.log` 的统计，取记录种类最接近的一份）比，多了或少了哪些记录类型、进程类型、字段 | 同事给了新日志；vLLM 或补丁升级以后 |
| `pair <proxy 地址:端口> [--model M] [--wait 秒]` | 经 proxy 发 3 个请求，看同一个请求在 P、D 两侧能不能配上 | 看板上请求只有 P 或只有 D；最多等 `--wait` 秒（默认 180） |

## 3. 命令写法

以下命令都在监控机上、集群目录里执行。

```bash
bin/diag.sh all
```

```bash
bin/diag.sh nodes
```

```bash
bin/diag.sh vllm
```

```bash
bin/diag.sh chain
```

```bash
bin/diag.sh monitor
```

```bash
bin/diag.sh history "2026-11-13 10:30" "2026-11-13 12:00"
```

`log` 的日志文件先拷到监控机，比如 `/data/logs/prefill_v32.log`：

```bash
bin/diag.sh log /data/logs/prefill_v32.log --save-profile
```

`--save-profile` 把这份日志的统计存成 `~/vllm-pd-diag-reports/<集群>/profiles/prefill_v32.log.json`。文件里只有计数和字段名，不含日志内容，可以发回。

```bash
bin/diag.sh pair <proxy 地址:端口>
```

模型名默认取 `inventory.json` 里的 `model`；proxy 要求别的名字时加 `--model <模型名>`。

## 4. 摘要怎么看

### 4.1 格式

- **第一行：** 集群、集群目录、模式，以及「只读」或「会发 3 个请求」。
- **每段的标题：** 以 `==` 开头。
- **每一行：** 级别加内容。

| 级别 | 意思 |
| --- | --- |
| `OK` | 这一项正常 |
| `WARN` | 可能有问题，或者没法核对，比如没有权限、vLLM 重启以后还没有请求；不影响别的项 |
| `FAIL` | 这一项不对；`→` 后面是修法 |
| `INFO` | 只是记录，比如路径、版本、请求数、找到的容器名 |

- **最后两行：**
  - `报告：<路径>`：完整报告，在 `~/vllm-pd-diag-reports/<集群>/` 下，权限 0600，里面有每条远程命令的原始输出，诊断时把它发回；
  - `RESULT: OK`、`RESULT: WARN（n 项）`或 `RESULT: FAIL（n 项）`。
- **退出码：** 有 `FAIL` 时为 1，否则为 0。
- **报告里有什么：**
  - 有：进程命令行、挂载、文件的 sha256，以及 7 个变量的值（`VLLM_LOGGING_CONFIG_PATH`、`PYTHONPATH`、`VLLM_CONFIGURE_LOGGING`、`PD_DIAG_INSTANCE`、`PD_DIAG_INSTANCE_SOURCE`、`PD_DIAG_MAPPING`、`PD_DIAG_LOG_DIR`）；
  - 没有：密码、别的环境变量、请求内容。

### 4.3 样例：vllm 模式的 `vllm`，一切正常

实验室真实输出。P 是 2 个 `vllm serve`、18 个子进程；D 是 8 个 `vllm serve`、72 个子进程（TP8）。P 那台的各行同 D，样例里省略了：

```text
OK   10.97.2.1 t33b-vllm-d：子进程带 PD_DIAG_INSTANCE_SOURCE=argv，主进程在起子进程之前已经加载了过滤器

OK   过滤器版本：10 个实例 12 个进程都是 pd-diag-v2-2026-11-13@10dc8087

RESULT: OK
```

「不是直接挂进来的」：

- 实验室的节点本身是容器，`/data` 来自 docker 卷，不是宿主机目录的直接映射，所以工具改用证据判断：
  - 容器里三个文件的 sha256 和下发的相同；
  - 过滤器写的文件出现在宿主机的日志目录里。
- 现场若是 `-v /data:/data` 直接映射，这两行是 `OK … 在容器里同样是 …`。

**标准输出里有重启以前的旧行时：** `docker logs` 会一直保留修好以前写进标准输出的行，不算问题。判「以后」用的时间是 vLLM 主进程的启动时间加 10 秒，因为 `docker logs` 给重启前最后几行打的时间会晚 1 秒左右。实验室里的样子：

```text
OK   10.97.2.1 t33b-vllm-d：标准输出里的 5980 行 [PD_DIAG] 都是 vLLM 这次启动（11-13 08:58:45）以前的（最后一行 2026-11-13 08:58:45 UTC），启动以后没有
OK   10.97.2.1 t33b-vllm-d 结论：日志配置生效，过滤器在写，标准输出里没有新的 [PD_DIAG]（5980 行是这次启动以前的）
```

### 4.4 vllm 模式下，重启以后还没有请求

过滤器要等第一条记录才建文件，之后才每 60 秒写一行自检。所以 vLLM 重启以后、第一个请求以前，ClickHouse 里没有这次启动的任何一行。`vllm` 和 `chain` 这时按实例判，规则和 `bin/panel2_cluster.sh check` 相同：

| 这个实例（主进程和它的子进程）这次启动以后 | 级别 |
| --- | --- |
| 任一进程在 ClickHouse 里有行 | 照常判新旧 |
| 都没有行，节点上它的日志目录这次启动以后写过文件 | 照常判：行该到而没到，`chain` 会指出是哪一段 |
| 都没有行，子进程带 `PD_DIAG_INSTANCE_SOURCE`（过滤器已经创建） | `WARN`「这次启动以后还没有记录，有请求后再查」 |
| 都没有行，读不了进程环境变量 | `WARN`「分不清过滤器有没有创建」 |
| 都没有行，过滤器也没有创建 | `FAIL`，看 `bin/diag.sh vllm` 的结论 |

这样判过的实例不进节点、镜像、ClickHouse 的新旧判断。实验室真实输出，替身重启后不发请求：

```text
bin/diag.sh chain：集群 glm53-1（/data/grafana/vllm-pd-grafana-panel2/glm53-1，vllm 模式），只读
== chain（节点日志 → 镜像 → 采集器 → ClickHouse）
INFO 阈值：节点 65 秒、镜像 75 秒、ClickHouse 135 秒以内算 OK，3 倍以内 WARN（自检每 60 秒、flush 5 秒、拉取每 10 秒）
WARN 10.97.1.1 链路通：P0 P1 这次启动以后还没有记录，有请求后再查
WARN 10.97.2.1 链路通：D0 D1 D2 D3 D4 D5 D6 D7 这次启动以后还没有记录，有请求后再查
OK   拉取：2 台，最久的 3 秒前成功
INFO 镜像 10.97.1.1：这台的实例这次启动以后都还没有记录，没有判镜像的新旧
INFO 镜像 10.97.2.1：这台的实例这次启动以后都还没有记录，没有判镜像的新旧
OK   采集器缓冲：5 个输出共 0 条积压
OK   解析失败：最近 10 分钟 0 行；dead-letter 0 行
OK   过滤器：48 个进程的出错数都是 0
INFO 最近 15 分钟 97 个请求
报告：/root/vllm-pd-diag-reports/glm53-1/diag-chain-20261113-091124.txt
RESULT: WARN（2 项）
```

同一时刻 `vllm` 的结论一行：

```text
WARN 10.97.2.1 t33b-vllm-d 结论：日志配置加载了、过滤器已经创建（子进程带 PD_DIAG_INSTANCE_SOURCE），这次启动以后还没有 [PD_DIAG] 记录（日志目录里没有新文件，标准输出里也没有新行）：多半是还没有请求 → 有请求以后再跑一次 bin/diag.sh vllm
WARN 10.97.2.1 版本：D0 D1 D2 D3 D4 D5 D6 D7 这次启动以后还没有记录，有请求后再查
```

- 「最近 15 分钟 97 个请求」是重启以前的请求。
- 读不到 vLLM 进程（SSH 用户不能执行 docker、找不到容器）时分不出这种情况，`chain` 写一行 `INFO` 说明，之后的几行仍会因为没有数据给 `FAIL`，以 `vllm` 的结论为准。

## 5. `vllm` 的结论

每个容器最后一行是「结论」。结论按下表从上到下取第一条成立的：

| 级别 | 结论（原文开头） | 意思 | 怎么修 |
| --- | --- | --- | --- |
| `FAIL` | vLLM 没有重启，新下发的节点文件没生效 | `pd_diag_logfilter.py` 或 `pd_diag_logging.json` 在 vLLM 启动以后换过（ctime 晚于启动），而且内容和 vLLM 启动时可能用的那一份都不同。`segments.json` 变了不算：过滤器自己重读 | 重启 vLLM |
| `FAIL` | 日志配置被关掉（`VLLM_CONFIGURE_LOGGING=0`） | 进程里有 `VLLM_CONFIGURE_LOGGING=0`，没有 `VLLM_LOGGING_CONFIG_PATH` | 去掉这个变量，加上两行 `export`，重启 vLLM |
| `FAIL` | 变量没有进到 vLLM 进程 | 主进程没有 `VLLM_LOGGING_CONFIG_PATH`，这次启动以后过滤器也没写过文件；多半是 `export` 写在了宿主机上，或者不在起 vLLM 的那个 shell 里 | 两行 `export` 放在容器里执行 `vllm serve` 的那个脚本里、`vllm serve` 之前（或用 `docker run/exec -e` 传进去）；写在宿主机的 shell 或别的脚本里不生效。改完重启 vLLM |
| `FAIL` | 子进程没有继承变量 | 主进程有变量，子进程（EngineCore、Worker）没有 | 变量要在 `vllm serve` 启动前就设在它的环境里，不要在进程里改环境变量后再起子进程；重启 vLLM |
| `FAIL` | 变量指向的目录里没有三个文件 | `VLLM_LOGGING_CONFIG_PATH` 所在目录里缺 `pd_diag_logging.json`、`pd_diag_logfilter.py`、`segments.json` 之一 | `export` 改成容器里的 `NODE_CONF_DIR_IN_CONTAINER`，重启 vLLM |
| `FAIL` | 日志配置加载了、过滤器已经创建，但 `[PD_DIAG]` 仍在标准输出 | 过滤器在，记录却没有经过它：发这些记录的 logger 不在 `vllm` 之下 | 查补丁 `pd_diagnostics.py` 用的 logger 名，把它加进 `pd_diag_logging.json` 的 `loggers` |
| `OK` | 日志配置生效，过滤器在写，标准输出里没有新的 `[PD_DIAG]` | 正常 | — |
| `WARN` | 日志配置加载了、过滤器已经创建，这次启动以后还没有 `[PD_DIAG]` 记录 | vLLM 重启以后还没有请求。过滤器要等第一条记录才建文件，之后每 60 秒写一行自检 | 有请求以后再跑一次 `bin/diag.sh vllm` |
| `WARN` | vLLM 启动不到 70 秒 | 刚启动，分不清 | 1 分钟后再跑一次 |
| `FAIL` | 变量和文件都对，但这次启动以后日志目录里没有新文件 | 过滤器没有起来 | 看 vLLM 的启动日志里有没有 logging 的报错 |
| `WARN` | 组合没见过，原样写下 | 以上都不成立；后面跟着五个原始信号（S1 环境变量、S2 启动与下发时间、S3 文件、S4 启动后写过的文件、S5 标准输出） | 把报告发回 |

**「没有重启」怎么判：**

- vLLM 只在启动时加载过滤器程序和日志配置，所以只有这两个文件换了内容才需要重启。
- 「vLLM 启动时可能用的那一份」取自集群目录的 `SHA256SUMS`，加上 v2.0 的两个值。v2.0 和 v2.1 的这两个文件相同，所以 v2.0、v2.1 之间来回升级、回滚、多次 `bin/nodes.sh push` 都不报。
- 以后哪一版改了这两个文件，那一版的说明会写明要重启 vLLM。

结论之外还有两种 `FAIL` 行，出现时 vLLM 多半没有起来，结论一行不出现：

- **「vLLM 启动时的报错：…」：** 原样摘自容器的标准输出，比如路径不存在：`RuntimeError: Could not load logging config. File does not exist: …`。
- **「容器里没有找到 vLLM 进程」：** 容器在，但里面没有命令行含 `vllm` 的进程。

## 6. 其他子命令的 `FAIL` 和修法

`→` 后面已经写了修法的，照做即可。下表列常见的几种，命令都在集群目录里执行：

| 子命令 | `FAIL` 行（开头） | 原因 | 怎么修 |
| --- | --- | --- | --- |
| `nodes` | `<地址> SSH 连不上` | 网络、密钥、SSH 用户 | 在监控机上用 `deploy.env` 里的用户 `ssh <地址>` 试 |
| `nodes` | `MOCK_RATE=…，每个 D … 请求/秒，超过 1.5` | mock 速率太大，D 会积压 | 按 `→` 后的值改 `deploy.env` 的 `MOCK_RATE`（留空即每个 D 1 请求/秒），再 `bin/nodes.sh start` |
| `nodes` | `mock 进程 n 个，应为 m 个` | 少了：mock 停了，停着的不会自己起来；多了：旧进程没停干净 | 少了：`bin/nodes.sh start`；多了：`bin/nodes.sh stop` 后再 `bin/nodes.sh start` |
| `nodes` | `vllm 模式下还有 n 个 mock 进程` | 从 mock 切到 vllm 时没有停干净 | 在那台节点上执行 `pkill -9 -f '[p]d032_mock.py'` |
| `nodes` | `mock 的主循环卡住` | `MOCK_RATE` 太大，每个 D 超过约 1.7 请求/秒会积压 | 调小 `MOCK_RATE`，再 `bin/nodes.sh start` |
| `nodes` | `节点文件和监控机不同或缺` | 下发以后节点上的文件被改过或删了 | `bin/nodes.sh push`；vllm 模式下，`pd_diag_logfilter.py`、`pd_diag_logging.json` 变了要重启 vLLM |
| `nodes` | `日志盘 …：按最近 30 分钟估 … 空闲只有 …` | 按现在的写入速率，`keep_hours` 小时的日志放不下 | 调小 `MOCK_RATE` 或 `segments.json` 的 `line.keep_hours`，或清理这块盘 |
| `nodes` | `内存耗尽杀过进程`、`系统日志里有磁盘满` | 系统日志里的原文 | 按原文处理；磁盘满时先看 `nodes` 的日志盘一行 |
| `vllm` | `宿主机的 … 在容器里是 …，不是 …` | 挂载的容器内路径和 `deploy.env` 写的不一样 | 改挂载，或改 `deploy.env` 的 `NODE_CONF_DIR_IN_CONTAINER`、`NODE_LOG_DIR_IN_CONTAINER` |
| `vllm` | `过滤器版本：…，期望 …` | 有记录的进程在 `push` 以后 2 分钟还是旧版本，或者两个以上版本同时在写 | 按 `→` 后的命令处理 |
| `vllm`、`chain` | `…：D0 D1 这次启动以后没有记录，过滤器也没有创建` | vLLM 这次启动以后一条记录都没有，子进程里也没有 `PD_DIAG_INSTANCE_SOURCE` | 看 `bin/diag.sh vllm` 的结论一行 |
| `chain` | `拉取程序没有运行` | 监控机重启以后拉取程序不会自己起来 | `bin/puller.sh start` |
| `chain` | `拉取：这些机器超过 2 分钟没有拉取成功` | SSH 不通，或者节点上日志目录读不了 | 看括号里的报错 |
| `chain` | `节点上各实例最新一行落后` | 节点上没有在写 | mock 模式看 `nodes`，vllm 模式看 `vllm` |
| `chain` | `镜像 … 最新文件 n 秒前改过`、`ClickHouse：这些实例最近 60 分钟没有行` | 上一段没有数据过来 | 往上一段找第一行 `FAIL` |
| `chain` | WARN `ClickHouse：最新一行最多落后 n 秒…最近没有请求` | vllm 模式下各实例这次启动以后都写过记录、拉取正常、各实例的自检行还在写，只是最近没有请求，汇总表没有新行 | 不用处理；有请求以后再查 |
| `chain` | `解析失败` | 日志格式和包二不符 | 把报告发回；同时用 `log` 查一份节点上的日志 |
| `chain` | `过滤器出错` | 过滤器在处理记录时出错 | 把报告发回 |
| `monitor` | `容器 … 不存在`、`容器 … <状态>`（不在运行）、`被内存耗尽杀过` | 监控机上的服务停了 | `bin/panel2_cluster.sh check <集群>` 看是哪个，再按包二说明处理 |
| `monitor` | `镜像盘 …：按最近 30 分钟估 … 空闲只有 …` | 各节点的日志在镜像盘上放不下 | 调小写入速率或 `line.keep_hours` |
| `monitor` | `Prometheus 访问不了` | Prometheus 容器停了或端口变了 | 同上 |
| `log` | `包二读的 9 种记录：原有的 7 种缺 …` | 这份日志里没有面板二要的记录 | 确认补丁版本；把统计文件发回 |
| `log` | `包二读的 9 种记录：新的 2 种（…）都没有` | 日志不是补丁 01、02 写的，v3 新加的 8 个段会是空的 | 确认节点上换了补丁 01、02 |
| `pair` | `诊断请求只在 P 侧有` | proxy 没有把 id 传给 D | 现场改 proxy：同一个请求发给 P、D 时带相同的 `X-Request-Id`（或请求体里相同的 `request_id`） |
| `pair` | `两侧都没有诊断请求的键，但 … P 新增、D 新增` | proxy 对两侧都没有传 id | 同上 |
| `pair` | `发请求以后只有 P 侧新增请求` | 请求没到 D，或 D 侧过滤器没生效 | `bin/diag.sh vllm` 看 D 那台 |
| `pair` | `n 秒内两侧都没有新增请求` | 请求没到 vLLM，或过滤器没生效 | 先跑 `bin/diag.sh chain`、`bin/diag.sh vllm` |

`pair` 的样例（实验室真实输出）：proxy 正常转发时：

```text
OK   3 个请求返回 200，请求键 diag-20261113090634-1 … diag-20261113090634-3（头部和请求体都带）
OK   3 个请求两侧都有：P、D 能配上
INFO 这几个请求会出现在看板上，请求键以 diag- 开头，是诊断发的，可以忽略
```

proxy 头部和请求体里的 id 都不传时：

```text
OK   3 个请求返回 200，请求键 diag-20261113090714-1 … diag-20261113090714-3（头部和请求体都带）
FAIL 两侧都没有诊断请求的键，但发请求以后 P 新增 48 个、D 新增 56 个请求：proxy 对两侧都没有传 id（头部和请求体都没有）→ 要现场改 proxy
```

## 7. 现场要提供的信息

| 编号 | 要提供什么 | 写到哪里 | 没有时 |
| --- | --- | --- | --- |
| U1 | 每台节点上 vLLM 的容器名 | 不用写，工具自己找；找得不对时写进 `deploy.env` 的 `NODE_VLLM_CONTAINERS`，或命令行 `--containers` | 找不到时写 `WARN`「没有找到 vLLM 容器，没有核对真实容器」，改用宿主机能看到的进程判断 |
| U2 | SSH 用户能不能执行 `docker`（docker 组，或免密 `sudo docker`） | 不用写，工具自己判断 | 写 `WARN`「SSH 用户不能执行 docker（…），没有核对真实容器」 |
| U3 | `docker exec` 进容器的默认用户能不能读 vLLM 进程的 `/proc/<pid>/environ`（默认用户是 root 时可以） | 不用写 | 写 `WARN`「读不了 vLLM 进程的环境变量，结论只靠文件和标准输出判断」 |
| U4 | 各台节点的 `/data` 是不是同一块共享盘 | 不用写，`nodes` 用 `findmnt` 判断 | 来源相同时写 `INFO`「看起来是同一块盘」 |

| U6 | SSH 用户能不能读系统日志（root 或 `adm` 组） | 不用写 | `nodes` 写 `WARN`「读不了系统日志」，附一条可以用有权限的用户手工执行的命令 |
| U7 | proxy 的地址、端口和模型名 | `pair` 的命令行 | 不能跑 `pair` |
| U8 | 真实 P 侧日志的统计 | 执行 `bin/diag.sh log <日志> --save-profile`，只发回 `~/vllm-pd-diag-reports/<集群>/profiles/` 下生成的统计文件 | `log` 只能和 11-12 的 `server.log` 统计比 |

## 8. 只读范围和 `pair` 的例外

- **集群目录：** 只读。读 `deploy.env` 时，在一个干净的子 shell 里执行 `bin/lib.sh` 的 `load_env`，并设 `PYTHONDONTWRITEBYTECODE=1`，不在 `scripts/` 下生成 `__pycache__`。
- **ClickHouse：** 每条查询都带 `--readonly=1`。
- **节点：** SSH 上去只执行读的命令：`ls`、`stat`、`df`、`findmnt`、`sha256sum`、`journalctl`、`pgrep`、`docker version`、`docker ps`、`docker inspect`、`docker top`、`docker logs`。
- **vLLM 容器：** `docker exec` 进容器只做两件事：
  - 读 `/proc/<pid>` 下的命令行、启动时间和上面 7 个变量；
  - 用 vLLM 进程的 uid 执行 `test -w` 判断日志目录能不能写。`test -w` 只判断，不写文件。
- **写的地方：** 只有 `~/vllm-pd-diag-reports/<集群>/`。
- **`pair`：**
  - 经 proxy 发 3 个 `max_tokens` 为 8 的请求，请求键是 `diag-<时间>-1` 到 `-3`；
  - 这几个请求会进看板，以 `diag-` 开头的请求是诊断发的，可以忽略；
  - 除此以外 `pair` 也只读。

## 9. 已知限制

- **vLLM 加载 logging 配置的方式：**
  - 工具对它的判断按 vLLM 的 `vllm/logger.py`：
    - `VLLM_CONFIGURE_LOGGING=0` 又设了路径时，启动报错；
    - 路径不存在时，启动报错；
    - 路径存在时，整份 `dictConfig`。
  - 实验室用的是按这个行为写的替身，不是真实 vLLM；
  - vllm-ascend 若在这一层另有处理，「启动时的报错」一行的原文可能不同。
- **「logger 不在 vllm 之下」是推断：** 依据是过滤器已经创建（子进程带 `PD_DIAG_INSTANCE_SOURCE`），而 `[PD_DIAG]` 仍在标准输出。工具不读补丁的源码，logger 名要现场看。
- **重启以后、第一个请求以前：** 过滤器一行也不写，自检行也不写。`vllm` 和 `chain` 按实例判：这次启动以后没有记录、子进程带 `PD_DIAG_INSTANCE_SOURCE` 的实例记 `WARN`，不记 `FAIL`。读不到 vLLM 进程（没有 docker 权限、找不到容器）时分不出这种情况，`chain` 仍会因为没有数据给 `FAIL`，以 `vllm` 的结论为准。
- **读不到进程环境变量时：** 容器的默认用户不是 root、读不了 vLLM 进程的 `environ` 时，变量各项写 `WARN`，结论只能靠文件和标准输出判断；按实例判时记「分不清过滤器有没有创建」（`WARN`）。
- **自己找容器：** 一台节点上跑着几个集群的 vLLM 时，自己找会把它们都列出来，这时要填 `NODE_VLLM_CONTAINERS`。
- **`history` 只看字节数和 `up`：** 拉到的字节数为 0 超过 10 分钟才算断，记为 `WARN`；短于 10 分钟的记 `INFO`。
- **只诊断，不修复：** `→` 后面的修法要人工执行。
