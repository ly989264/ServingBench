## 0. 读法和约定

- **两类机器：** 监控机（<监控机地址>，运行 Grafana、Prometheus、ClickHouse、采集器和拉取程序）和节点（运行 vLLM 或 mock 的 P、D 机器）。除另行说明外，命令都在监控机上执行，节点上不需要手工操作。
- **执行账号：** 在监控机上安装面板、执行更新脚本的账号。注册表、更新脚本的备份、诊断报告都在它的家目录下，文中的 `~` 指这个家目录。
- **命令标记：** 命令块前标【只读】（不改变任何东西）或【会改】（改变配置、进程或数据）；删除数据的另外写明「删数据」「不可恢复」。
- **命令的来源：** 命令只取自两处：已在实验室走通的文档（包一、包二的 README，《内网升级总说明》，《面板一二新装操作单》，《面板二改名和新增集群使用说明》），写明出处；或这次在实验室按内网状态实际执行过的命令。两者都不是的标「未验证」。附录 B 汇总了出处。
- **正常输出：** 第三部分的输出取自实验室，具体换算方法见第三部分开头。
- **待确认：** 第二部分有几项内网事实没有直接核对过，标「待确认」，用附录 C 的只读命令核对。
- **尖括号：** 命令里的 `<…>` 要换成现场的值；输出里的 `<…>` 是每次不同的部分。
- **密码：** 文中不出现任何密码。需要密码的命令从集群目录的 `deploy.env` 里读，写法是 `(set -a; . ./deploy.env; 命令)`，括号让这些变量只在这一条命令里有效。

# 第一部分 原理

第一部分说明系统由哪些部分组成、数据怎样流动，第二到第四部分都以这里的概念为基础。

## 1. 系统总览

本节给出全书的总体框架：系统由哪两个面板组成，按什么层次组织，部署在哪些机器上。后面各节都在图 1 中定位所讲的对象。

### 1.1 两个面板

**面板**是 Grafana 里一组用途相同的看板，连同为它采集、存储数据的全部程序。本系统有两个面板，回答两类不同的问题：

| | 面板一：服务侧指标 | 面板二：请求时延拆解 |
|---|---|---|
| 回答的问题 | 每个 vLLM 实例和每台机器现在运行得怎样：请求数、吞吐、时延分布、调度、KV cache、NPU 和主机资源 | 一个请求的时间花在哪一段：在 P、D 两侧各经过哪些阶段，每段多长 |
| 数据的形态 | 指标：随时间变化的数值序列，每 15 秒取一个点 | 逐请求的记录：每个请求一行汇总，另有请求级事件 |
| 数据来源 | 节点上各程序开放的指标端口（vLLM、npu-exporter、node_exporter、Mooncake） | vLLM 进程写出的 `[PD_DIAG]` 日志行；内网没有推理模型时由 mock 写入程序生成同样格式的日志 |
| 存储 | Prometheus（时序数据库），保留 15 天 | ClickHouse（列式数据库），汇总表保留 30 天，事件表保留 15 天 |
| 看板 | 两个：「vLLM 服务侧监控面板 - Prefill实例」和「… - Decode实例」，下文简称面板一·P、面板一·D | 一个：「面板二：请求时延拆解（P / D）」 |
| 部署包 | 包一（v1.0），面板一的部分 | 包二 v2.1 |

两个面板共用同一个 Grafana。面板二还借用面板一的 Prometheus 监视自己的采集链路（见 3.5），所以同一个集群里面板一和面板二并不完全独立。

### 1.2 模型组、集群和面板三层

系统按三层组织，从大到小：

- **模型组**：同一个模型的若干集群，在 Grafana 里是一个文件夹。内网目前只有一个模型组 `GLM-5.3`，对应 Grafana 文件夹「GLM-5.3」。
- **集群**：一组一起提供服务的 P、D 机器和实例，有一个只用小写字母、数字和 `-` 的名字，例如 `glm53-1`。同一台监控机上集群名不能重复，一台节点机器只能属于一个集群。集群名决定了这个集群全部容器、端口、目录和 Grafana 对象的名字（规则见第 4 节）。
- **面板**：一个集群可以装面板一、面板二，或者只装其中一个。

内网目前的两个集群（详见第二部分）：

```
模型组 GLM-5.3（Grafana 文件夹「GLM-5.3」）
├── 集群 glm53-1：12 台机器（P 8 台、D 4 台）
│   ├── 面板一：面板一·P、面板一·D（glm53-1）
│   └── 面板二：mock 模式（这 12 台的 vLLM 接入面板二以前，用模拟日志）
└── 集群 test：2 台测试机
    └── 面板二：vllm 模式（读真实 vLLM 的日志），没有面板一
```

### 1.3 机器和推理服务的结构

推理服务采用 **P/D 分离**：一个请求先由 **P 实例**（prefill，处理输入、生成第一个 token）处理，再交给 **D 实例**（decode，逐个生成后续 token）。几个相关概念：

- **vLLM 实例**：一组共同完成推理的 vLLM 进程，对外有一个 **API server**（HTTP 端口，形如 `IP:端口`）。实例按在列表中的顺序命名为 `P0`、`P1`… 和 `D0`、`D1`…。
- **DP、TP**：DP（数据并行）是实例的个数，TP（张量并行）是一个实例占用的 NPU 卡数，也是它的进程数。glm53-1 的 P 侧 DP=8、每个实例 TP16，一台机器一个实例；D 侧 DP=64、TP1，一台机器 16 个实例。
- **proxy**：请求的入口，把请求依次转给某个 P 和某个 D。两个面板都不采集 proxy 的数据。
- **节点**：运行 vLLM（或 mock 写入程序）的 P、D 机器。
- **监控机**：运行 Grafana、Prometheus、ClickHouse、采集器和拉取程序的机器，内网是 <监控机地址>。所有部署和运维命令都在监控机上执行，节点上不需要手工操作（只有从 mock 切到 vllm 时要改 vLLM 的启动脚本，见 10.3）。

图 1 是全书的核心对象：两个面板的组成部分、所在机器和数据流向。

```

面板一
  [节点]   vLLM API server、npu-exporter、node_exporter、Mooncake master
     │ (1) Prometheus 定时抓取各指标端口
     ▼
  [监控机] Prometheus（每个集群一个）
     │ (2) Grafana 数据源「Prometheus（<集群>）」
     ▼
  [监控机] Grafana：面板一·P、面板一·D

面板二
  [节点]   vLLM 的每个进程里的过滤器（mock 模式下是 mock 进程里的过滤器）
     │ (3) 写日志文件
     ▼
  [节点]   日志目录 NODE_LOG_DIR
     │ (4) 拉取程序经 SSH + rsync 复制

  [监控机] 镜像目录 <数据目录>/pull
     │ (5) 采集器读新行、解析
     ▼
  [监控机] ClickHouse（每个集群一个）
     │ (6) Grafana 数据源「vLLM ClickHouse（<集群>）」
     ▼
  [监控机] Grafana：面板二

交点
  (7) 面板一的 Prometheus 也抓取面板二的拉取程序和采集器的状态，用于告警
```

| 编号 | 从 → 到 | 方式 | 频率 |
|---|---|---|---|
| (1) | 节点的指标端口 → Prometheus | Prometheus 主动发 HTTP GET 读 `/metrics` | 每 15 秒 |
| (2) | Prometheus → Grafana | 打开或刷新看板时发 PromQL 查询 | 看板刷新时 |
| (3) | 过滤器 → 日志目录 | 写本地文件 | 请求级记录随到随写，累计行每 5 秒，自检行每 60 秒 |
| (4) | 节点日志目录 → 监控机镜像目录 | 监控机上的拉取程序经 SSH 执行 rsync，只传新增部分 | 每 10 秒 |
| (5) | 镜像目录 → ClickHouse | 采集器读文件里新增的行，解析后经 HTTP 写入（账号 `vllm_writer`） | 连续，攒批最多 5 秒 |
| (6) | ClickHouse → Grafana | 打开或刷新看板时发 SQL 查询（账号 `vllm_reader`） | 看板刷新时 |

图 1 中面板一的数据由 Prometheus 主动到节点上取（步骤 1），面板二的数据由拉取程序经 SSH 把节点上的日志文件复制回监控机（步骤 4）。两条数据流在节点上互不相干，只在监控机上共用 Grafana，并由面板一的 Prometheus 监视面板二的拉取程序和采集器。

两个面板分工不同：面板一用 Prometheus 显示实例和机器的运行指标，面板二用 ClickHouse 显示逐请求的时延拆解，二者共用 Grafana，按「模型组 → 集群 → 面板」三层组织。

## 2. 面板一：服务侧指标

本节对应图 1 的上半部分：数据从哪些端口来，怎样由 Prometheus 存起来，又怎样显示在两个看板上。

### 2.1 看板上有什么

面板一有两个看板，P 一个、D 一个，每个看板顶部有「模型」「实例」两个下拉框和时间范围。看板按分组（Grafana 里叫 row）排列：

| 看板 | 分组 |
|---|---|
| 面板一·P（Prefill 实例） | 实时总览、时延、调度与批处理、所选时间段统计、KV Cache、Mooncake Client、Mooncake Master、NPU 与主机、API Server |
| 面板一·D（Decode 实例） | 实时总览、时延、调度与批处理、所选时间段统计、KV Cache、P→D KV 传输、NPU 与主机、API Server |

「实例」下拉框选一个实例时，时延和调度分组只显示这个实例的曲线；选 All 时显示全部（D 侧 64 条线，图例可滚动）。部分 panel 需要 vllm-ascend 打了补丁才有数据（Mooncake client、Transfer Engine 的每进程指标），没打补丁时显示 No data，名单见包一 README「不打补丁时缺什么」。

### 2.2 数据流

```
图 2  面板一的数据流

  [监控机] 清单 inventory.json
     │ (a) panel1_cluster.sh add 里的生成脚本
     ▼
  [监控机] prometheus.yml（抓取目标清单，挂进 Prometheus 容器）
     │ (b) 热加载
     ▼
  [监控机] Prometheus 容器 vllm-pd-prometheus-<集群>
     ▲ (c) 每 15 秒抓取一次
     │
  [节点]   vLLM API server   <IP>:<端口>/metrics
           npu-exporter      <IP>:npu_exporter_port
           node_exporter     <IP>:node_exporter_port
           Mooncake master   mooncake_master.address

  [监控机] Prometheus 的数据卷 vllm-pd-prometheus-data-<集群>（保留 15 天）
     │ (d) PromQL 查询
     ▼
  [监控机] Grafana 数据源「Prometheus（<集群>）」→ 面板一·P、面板一·D
```

| 编号 | 方式 |
|---|---|
| (a) | `panel1_cluster.sh add` 执行包一的生成脚本，按清单写出 `prometheus.yml`（面板二写入的两段原样保留） |
| (b) | `prometheus.yml` 以只读方式挂进容器；写完以后向 Prometheus 的 `/-/reload` 发 POST，不重启容器 |
| (c) | Prometheus 主动访问每个指标端口（HTTP GET），间隔为清单的 `scrape_interval` |
| (d) | Grafana 打开或刷新看板时向 Prometheus 发 PromQL 查询 |

几个术语：

- **指标端口**：程序在一个 HTTP 端口上以文本形式列出自己当前的计数和测量值（路径通常是 `/metrics`）。vLLM 的每个 API server、npu-exporter（NPU 卡的指标）、node_exporter（主机 CPU、内存、磁盘、网络）、Mooncake master 各开一个。
- **抓取**：Prometheus 按固定间隔访问每个指标端口，把读到的值连同时间存下来。每个被抓的端口叫一个**抓取目标**（target），状态为 up（抓到）或 down（抓不到）。
- **prometheus.yml**：Prometheus 的配置文件，列出全部抓取目标。它由包一的生成脚本按 `inventory.json` 算出来，不手写。面板二也往这个文件里加一段带标记的内容（见 3.5），面板一重新生成时原样保留这一段。
- **热加载**：让运行中的 Prometheus 重新读取 `prometheus.yml`，不重启容器、不中断数据。命令是向它的 `/-/reload` 端点发 POST（13.5）。

### 2.3 清单 inventory.json

**清单**（`inventory.json`）是一个 JSON 文件，写明一个集群有哪些实例、在哪里。面板一和面板二都以它为准。最重要的字段：

| 字段 | 含义 |
|---|---|
| `prefill.api_servers`、`decode.api_servers` | 每个实例 API server 的 `IP:端口`，按 vLLM 的 `--data-parallel-rank` 排。第 n 项（从 0 数）是实例 `P<n>` / `D<n>` |
| `prefill.procs_per_instance`、`decode.procs_per_instance` | 每个实例的进程数，等于 TP × PP × prefill-CP |
| `vllm_ascend_patched` | vllm-ascend 是否打了包一的补丁；`false` 时不抓 Mooncake client 和 Transfer Engine 的每进程端口 |
| `npu_exporter_port`、`node_exporter_port` | 两个 exporter 在每台机器上的端口 |
| `mooncake_master` | Mooncake master 的指标地址和显示用的节点名 |
| `scrape_interval`、`scrape_timeout`、`retention` | 抓取间隔、超时（默认 15s、10s）和 Prometheus 的保留时长（默认 15d） |

机器列表不单独写：清单里出现过的不同 IP 即这个集群的机器。全部字段见包一 README「附录 A：清单字段」。改清单以后要重新生成 `prometheus.yml` 并热加载，操作见 11.1。

面板一的全部数据都来自节点上已有的指标端口，由 Prometheus 按 `inventory.json` 生成的抓取目标定时取回；看板只是对 Prometheus 的查询。

## 3. 面板二：请求时延拆解

本节对应图 1 的中间一行：一个请求的时延记录怎样从 vLLM 进程里产生，经过哪些程序到达看板。

### 3.1 看板上有什么

面板二只有一个看板「面板二：请求时延拆解（P / D）（<集群>）」，顶部有模型、实例、排序依据、请求 ID 四个选择项和到面板一·P、面板一·D 的跳转按钮。看板分四个区域：

| 区域 | 内容 |
|---|---|
| 所选时间段概况 | 请求数；官方 E2E（P / D）；官方 TTFT（P / D）；TPOT；P 合计 / D 合计；P 侧轮次、D 侧总步数；P 侧、D 侧分段时延分布（p50、p90、p99、均值、均值占比） |
| 最慢请求 | 按「排序依据」取最慢的 100 个请求，带每侧最大的段；最慢 20 个请求的分段条形图；P、D 两侧的子段明细 |
| 单请求拆解 | 选定一个请求 ID 后，它的官方 E2E、TTFT、TPOT、token 数、P / D 时间线和两侧分段明细 |
| 单请求事件 | 这个请求两侧的请求级记录，按时间排列 |

**段**是一个请求在某一侧经过的一个阶段，例如 P 侧的 tokenizer、schedule、forward，D 侧的 add_request、第二步起的 forward。段有层级：L1 是阶段，L2 是阶段下的子段，L3 是子段下的子段；有下级段的叫**父段**，父段没有自己的数据来源时显示子段之和。每个段取自哪种记录的哪个字段、哪些段为空，见 3.6。

P、D 两侧靠请求头 `X-Request-Id` 配对。proxy 没有给同一个请求的 P、D 发相同的 `X-Request-Id` 时，单请求拆解里另一侧和「P 末到 D 首」为空。

### 3.2 数据流

```

  [节点]   vLLM 的每个进程（或 mock 进程）加载 NODE_CONF_DIR 里的三个文件

     ▼

     │ (3) 采集器（容器 vllm-pd-vector-<集群>）读新行、解析
     ▼
  [监控机] 采集器的磁盘缓冲 <数据目录>/vector（ClickHouse 写不进时暂存）

     ▼
  [监控机] Grafana 数据源「vLLM ClickHouse（<集群>）」→ 面板二看板

  旁路：面板一的 Prometheus 抓取拉取程序（端口基数+1）和采集器的状态

  v3.1-extra 的两个可选来源（deploy.env 打开时才有）：
  [proxy 机器] PROXY_LOG_DIR/proxy-<端口>/proxy.*.log ──拉取程序 rsync──▶ PULL_DIR/_proxy ──采集器──▶ 表 proxy_line
  [节点] vLLM 的标准错误 ──拉取程序只取 [BatchPutTiming] 行──▶ PULL_DIR/_mooncake
         ──拉取程序和缓存池保存记录配对──▶ PULL_DIR/_native ──采集器──▶ 表 phase_line
```

各环节的作用：

- **过滤器**（`pd_diag_logfilter.py`）：一个 Python 模块，由 vLLM 的日志配置加载进 vLLM 的每个进程（API server、EngineCore、Worker）。它从 vLLM 的日志里挑出 `[PD_DIAG]` 行：请求级记录原样写盘；每一步的记录不逐条写，在进程里按请求累加，每 5 秒写一行累计值；按步记录和缓存池记录只保留 TP rank 0 的。日志按实例、进程分文件写进 `NODE_LOG_DIR`，单个文件写满 256 MiB 换新文件，超过保留时长的旧文件自己删掉。保留时长是集群 `deploy.env` 的 `NODE_LOG_KEEP_HOURS`，留空时 12 小时（9.5）。进程写过第一行之后，过滤器每 60 秒另写一行**自检行**，报告自己的版本和计数。
- **拉取程序**：监控机上的一个后台进程（不是容器），用 SSH 和 rsync 把每台节点的 `NODE_LOG_DIR` 复制到监控机的**镜像目录**。节点上删掉的旧文件，镜像里也跟着删，所以镜像的大小约等于各节点保留的日志之和。它在端口基数 +1 上开一个状态端口（`/status`、`/metrics`）。
- **采集器**：Vector 程序，运行在容器里，持续读镜像目录里新增的行，解析成表的行，攒批写进 ClickHouse。
- **ClickHouse**：存放面板二全部数据的数据库，每个集群一个容器。看板只读视图 `vllm_pd.phase_line_cur`，即当前 `segments.json` 版本写出的行。
- **数据源**：Grafana 里指向这个 ClickHouse 的连接，用只读账号 `vllm_reader` 访问。
- **proxy 的一行（v3.1-extra）**：打了 proxy 补丁、设 `PD_PROXY_DIAG=1` 的 proxy，在每个请求结束时写一行，记 6 个时刻、重试次数和 P、D 地址。`deploy.env` 的 `PROXY_COLLECT=1` 时，拉取程序连 `PROXY_MACHINE`，把 `PROXY_LOG_DIR` 复制到 `PULL_DIR/_proxy`，采集器写进表 `proxy_line`；看板按请求号把它和 P、D 的行对上（3.6.4）。
- **Mooncake 的计时行（v3.1-extra）**：打了补丁 04 的 Mooncake 每次批量写入打印一行 `[BatchPutTiming]` 到 vLLM 的标准错误，过滤器收不到。`MOONCAKE_LOG_COLLECT=1` 时：
  - 拉取程序按 `MOONCAKE_LOG_FILES` 在节点上从上次停下的位置只取这种行，放进 `PULL_DIR/_mooncake`；
  - 再按机器、线程号、key 数、字节数和时间，把每行配给缓存池保存记录（`pool_task[save]`）里的一次调用；
  - 一个保存任务的调用都配上以后，拉取程序写一条记录到 `PULL_DIR/_native`，采集器照常读。

从节点写下一行日志到看板上查得到，实验室实测中位数约 10 秒、最长约 16 秒，主要是拉取间隔（10 秒）加采集器的攒批（最多 5 秒）（出处：包二 README「开始之前」）。

### 3.3 节点文件和版本串

**节点文件**是监控机下发到每台节点 `NODE_CONF_DIR` 的三个文件，节点上只有这三个文件属于面板二：

| 文件 | 作用 |
|---|---|
| `pd_diag_logging.json` | vLLM 的日志配置。vLLM 通过环境变量 `VLLM_LOGGING_CONFIG_PATH` 读它，它把过滤器挂到 vLLM 的日志上 |
| `pd_diag_logfilter.py` | 过滤器本身。vLLM 通过 `PYTHONPATH` 找到它 |
| `segments.json` | **映射规则**：日志里哪条记录的哪个字段对应看板上的哪一段，以及写盘目录（`line.log_dir`）、轮转大小、保留小时数（`line.keep_hours`）等参数。`line.log_dir`、`line.keep_hours` 两个值由 `deploy.env` 的 `NODE_LOG_DIR_IN_CONTAINER`、`NODE_LOG_KEEP_HOURS` 写入，其余内容和部署包里的相同 |

`segments.json` 是面板二的中心配置：节点上的过滤器、监控机上采集器的解析规则、ClickHouse 的表和视图都由它决定。监控机上集群目录里有一份，下发到节点的是同一份。

**版本串**是 `segments.json` 的 `config_id` 加上文件内容的 SHA-1 前 8 位，形如 `pd-diag-v3-2026-11-16@<8 位十六进制>`（v2.1 是 `pd-diag-v2-2026-11-13@10dc8087`）。`deploy.env` 里的两个值写进文件以后，SHA-1 跟着变，所以同一版的两个集群版本串可以不同。过滤器把它写进每一行自检行，`check` 和 `diag` 用它判断节点上运行的是不是监控机上的那一份规则。

**段定义按集群选（v3.1-extra）。** 部署包的根目录有一份 `segments.json`，`profiles/` 下另有按环境写的段定义（`profiles/dsv41/segments.json`、`profiles/glm53/segments.json`）。集群 `deploy.env` 的 `SEGMENTS_PROFILE` 留空时用根目录那份，和 v3 的内容相同；填 `dsv41` 时，`bin/panel2_cluster.sh add` 把 `profiles/dsv41/segments.json` 拷成集群目录的 `segments.json`，`config_id` 是 `pd-diag-v3.1-extra-dsv41-2026-11-19`。填 `glm53` 时同理，用 `profiles/glm53/segments.json`，`config_id` 是 `pd-diag-v3.1-extra-glm53-2026-11-19b`（3.6.5）。几种环境的差别只放在各自的段定义里，代码相同。

两条规则决定改动节点文件以后要不要重启 vLLM：

- 只改了 `segments.json`（换新版本时由脚本下发）：不用重启。写过记录的进程每 2 秒查看一次它的修改时间，变了就重新读取；还没写过记录的进程在它的第一条记录以后 2 秒内重读。
- 改了 `pd_diag_logfilter.py` 或 `pd_diag_logging.json`：要重启 vLLM 才生效。

### 3.4 两种模式：mock 和 vllm

**模式**写在集群 `deploy.env` 的 `NODE_MODE` 里，决定节点上由谁写日志：

| | mock 模式 | vllm 模式 |
|---|---|---|
| 用途 | 机器上还没有推理模型时，先把整条链路跑起来 | 读真实 vLLM 的日志 |
| 节点上写日志的 | **mock 写入程序**（`pd032_mock.py`）：每个实例一个进程，按当前时间生成请求，写出和打了补丁 01、02 的 vLLM 同格式的日志，经同一个过滤器写盘 | 打了插桩补丁 01、02、写 `[PD_DIAG]` version 2 记录的 vLLM（3.6） |
| 节点文件怎样加载 | mock 进程自己加载 | vLLM 启动时通过 `VLLM_LOGGING_CONFIG_PATH`、`PYTHONPATH` 加载，节点目录要挂进 vLLM 容器 |
| 请求速率 | `MOCK_RATE`（全集群每秒请求数），每个 D 实例不超过 1.5 请求/秒 | 真实流量 |
| 节点上的进程 | 每个实例一个 mock 进程（`nice 19`）；拉取时短暂多一个 rsync 和 sshd | 不新增进程，过滤器在 vLLM 自己的进程里 |
| 启停 | 监控机上 `bin/nodes.sh start` / `stop` | 随 vLLM |

从 mock 切到 vllm 的步骤见 10.3。

### 3.6 段的来源

本节对应图 1 中间一行最上面的一格：节点上的 vLLM 进程写出哪些记录，`segments.json` 从中取哪个字段给哪个段。

**结论：** 面板二的段共 47 个（P、D 两侧合计，同名的段在两侧各算一个）。用包里的 `segments.json` 时，情况和 v3 相同：

- 33 个有数据来源，其中 25 个从 v2.0 起就有，8 个是 v3 新加的；
- 5 个是父段，显示子段之和；
- 9 个为空，因为日志里没有对应的计时。

8 个 v3 新段全部来自插桩补丁 02 写的两种记录，原有 25 个段来自补丁 01。节点上没有换补丁时，原有 25 个段照常显示，8 个新段为空。用 dsv4.1 的段定义（`SEGMENTS_PROFILE=dsv41`，3.6.4）时，这 9 个空段里 8 个接上了来源，47 段里 46 段有数据，只有网关为空。

**插桩补丁**是给 vLLM 和它的插件加 `[PD_DIAG]` 日志的补丁，同事 2026-11-16 给了四个：

| 补丁 | 改什么 | 面板二要不要 |
|---|---|---|
| 01 | vLLM：写 API server、EngineCore、Worker 的三种记录 `api_summary`、`core_summary`、`worker_summary` | 要。原有 25 个段和 queue_time 的口径都来自它 |
| 02 | Ascend 插件：写缓存池任务 `pool_task` 和 KV 传输 `pd_transfer_summary` 两种记录 | 要。8 个新段都来自它；01 和 02 要一起部署 |
| 03 | KV 传输的业务修复，不是日志补丁 | 不要。面板二不读它的任何东西 |
| 04 | Mooncake 原生的计时日志 `[BatchPutTiming]`，写到标准错误 | 不要。这种行不是 `[PD_DIAG]`，过滤器收不到，v3 不采 |

**缓存池**是 P 侧存放 KV 的共享存储：P 把算好的 KV 存进去叫**保存**，遇到相同前缀时取回叫**加载**。`pool_task` 每个保存或加载任务一条；`pd_transfer_summary` 记 D 从 P 读取 KV 的传输。

#### 3.6.1 v3 新加的 8 个段

| 侧 | 段 | 记录和条件 | 字段 | 说明 |
|---|---|---|---|---|
| P | start_load_kv/submit | `pool_task`，`scope` 为 `task`、`operation` 为 `load_submit`、`status` 为 `submission_returned` | `duration_ns` | 缓存池加载的提交耗时，只在命中缓存池的请求上有值 |

| P | wait_for_save/build_key | 同上 | `stages.build_key.duration_ns` | |
| P | wait_for_save/lookup | 同上 | `stages.lookup.duration_ns` | 在缓存池里查 key，和 schedule 下的 lookup 不是一回事 |
| P | wait_for_save/prepare | 同上 | `stages.prepare.duration_ns` | 全部命中、不需要保存时为空 |
| P | wait_for_save/sync | 同上 | `stages.sync.duration_ns` | 同上 |

#### 3.6.3 补丁 01 带来的口径变化

下面两处变化来自补丁，不是 v3 的改动，看板上的段名不变：

- **queue_time（排队）只算到第一次被调度器挑中。** 补丁 01 的排队从进入队列算到调度器第一次挑中这个请求（日志里 `timing_scope` 为 `enqueue_to_first_candidate`），等 KV 的时间不再算在里面，改由 D 侧的 start_load_kv/wait_for_transfer 显示。没有换补丁的节点，排队包含等 KV 的时间，数值明显更大。
- **add_request 包含输入处理。** 补丁 01 从分词器返回算到请求经 ZMQ 发给引擎，中间的 token 构造、渲染、校验、注册和序列化都算在这一段；这些时间在更早的补丁下落在「未归属」里。它和 tokenizer 段交叠几十微秒，照日志显示，不扣。

**首次候选**是调度器第一次挑中一个请求的那一步。要先等 KV 的请求（P 侧命中缓存池、D 侧从 P 读 KV）在这一步不执行，只发起 KV 加载；这一步的 lookup、alloc、other 和 D 的提交记在一条不带请求号的步骤记录里，过滤器按空键丢掉并计数。v3 不做按步骤编号的关联，接受这个缺口：P 侧命中缓存池的请求 lookup 为空，alloc、other 只有执行那一步的值；D 侧的「第一步」是 KV 到了以后第一次执行的那一步。`bin/diag.sh chain` 报出各实例过滤器丢掉的空键记录数。

段的来源全部写在 `segments.json` 里：8 个新段来自补丁 02 的 `pool_task` 和 `pd_transfer_summary`，9 个空段是日志里没有计时，两处口径变化随补丁 01 而来，看板和过滤器的代码都不用跟着改。上面这一段说的是包里的 `segments.json`；dsv4.1 的段定义把首次候选那一步归到请求上，见 3.6.4 的 C2。

#### 3.6.4 v3.1-extra：dsv4.1 的段定义

本节描述的是交付时的 dsv4.1 段定义，C12、细化后的 C2、C15 和缺 `execution_id` 的规则只在 glm5.3 的段定义里生效（3.6.5）。

`profiles/dsv41/segments.json` 在包里 `segments.json` 的基础上，给 9 个空段里的 8 个接上来源，另外按 C2 把首次候选那一步的 lookup、alloc、other 计入请求。它要求 dsv4.1 的节点打了新的 vLLM、vllm-ascend 补丁和 Mooncake 补丁 04，proxy 换成打了 proxy 补丁的文件（这三件的部署见内网操作说明 A）。新补丁没装上时，对应的段为空，其余照常。

| 侧 | 段 | 来源 | 口径 |
|---|---|---|---|
| P | proxy/lb_proxy | proxy 行的 `proxy_to_p_ms` | proxy 进入请求处理 → 发给 P 之前，proxy 自己的单调时钟 |
| D | proxy/lb_proxy | proxy 行的 `proxy_to_d_ms` | 收到 P 的响应 → 发给 D 之前 |
| P | ttft/wait_for_put（等 put 完成） | Worker 每步记录 `worker_summary[execute]` 的 `stages.wait_for_put.duration_ns`，按请求累加（C3） | 这一步 forward 之前，等前面已释放请求的保存做完的时间，记给这一步的请求；只取 TP rank 0。这一段是本步因为别的请求的 put 而等待的时间，不是本请求自己的 put 完成时间 |
| P | start_load_kv/wait_for_transfer | `pool_task[load]` 的 `counters.queue_wait_ns` 加 `duration_ns`（C1） | 加载请求进入加载线程的队列 → get 返回。记录里没有排队时间时只算处理时间 |
| P | put/submit、put/wait_for_transfer、put/finalize | Mooncake 计时行的 phase2、phase3、phase4，按保存任务的每次调用相加（C4） | 一个保存任务可能调用 Mooncake 不止一次，三段各是这些调用对应阶段之和 |
| D | start_load_kv/submit | 首次候选那一步 Worker 记录的 `stages.submit.duration_ns`（C2） | D 发起从 P 读 KV 的调用：start_load_kv 进入 → 返回，只入队 |

**取舍（统筹已定）：**

- **C1** P 的 wait_for_transfer 取加载任务的排队时间加执行时间；没有排队时间时只取执行时间。采集器把同一条加载任务记录的排队时间和执行时间先相加，写成一个值；一个请求有几条加载任务记录时，和其他缓存池段一样，取相加以后最大的一条。
- **C2** 首次候选那一步归到请求上，同一步的 lookup、alloc、other 也随之计入：
  - P 侧命中缓存池的请求，lookup、alloc、other 包含首次候选那一步；
  - D 侧第一步的 alloc、other 包含首次候选那一步，第二步起不变（glm5.3 的段定义改成只取 submit，3.6.5）。
  - 换了 `config_id`，数值和 v3 已有的数据不可比。
  - 做法在过滤器里，每个进程自己做：有几种记录会写明「请求号 R、步骤编号 X」（记录格式约定 v2 第 3 节）：
    - EngineCore 里 D 的 `pd_transfer_summary[link]`（`transfer_role` 为 `consumer`）和 P 的同种记录（`transfer_role` 为 `pool_load`，vllm-ascend 补丁新加）；
    - Worker 里 D 的 `pd_transfer_summary[task]` 和 P 的 `pool_task[load_submit]`。
  - 过滤器把 X 这一步的值加给 R，写进 R 的累计行；这一步自己的记录已经带着 R 时不再加。
  - 这一步里同时有别的请求在执行时也成立。TP 大于 1 时 Worker 和 EngineCore 是两个进程，各自配对。
  - 过滤器把最近的步骤值暂存起来，等映射记录到来（D 读 KV 慢时映射记录可能晚到几秒）。条数和时长上限是段定义 `candidate` 的 `hold_steps`（8192）和 `hold_seconds`（120），可调。过滤器自检行里有四个计数：
    - `cand_maps`：配上的（请求、步骤）对数；
    - `cand_applied`：加给请求的值的个数；
    - `cand_unpaired`：写明了请求、但离开暂存时还有值没加上的步骤数；
    - `cand_evicted_full`：没到时长就因条数满了被挤出的步骤数。
    
    它们写进 `vllm_pd.filter_selfcheck` 的同名列。
  - 首次候选的值不分 P、D 两侧计算，所以 P 的累计行也有 `cand_submit`，D 的累计行也有 `cand_lookup`。多出的这些 `cand_*` 列没有段读它，不影响数值。
- **C3** 等 put 完成取 rank 0，和 forward、sampling 一致。
- **C4** put 下 3 段分别对应 Mooncake 的第 2、3、4 阶段；第 1 阶段（`StartBatchPut`）不显示。`prefer_alloc_in_same_node` 打开时计时行的 `timing_scope` 是 `prefer_same_node_full`，3 段只含这三个阶段。3 段相加不等于 put：put 是 Python 一侧整个调用的时间。
- **C5** P 合计、D 合计保持 API server 的口径，不含 proxy 段。看板上 proxy 段那一行「占比」一列为空；proxy 量到的 TTFT、E2E 只进单请求 JSON 的 `latency_ms.ttft`、`latency_ms.e2e`（这时 `latency_ms.starts_at` 是 `proxy`）。
- **C6** D 的 wait_for_transfer 不变，是第一次读开始到最后一次读结束（`transfer_envelope_ns`）。
- **C9** 多个请求共用的缓存池任务计整份。记录不带单个请求号、请求列在 `members[]` 里时，整份时长计给每个成员，和共用的步骤（forward 等）一样。适用于 `pool_task[load]`、`pool_task[save]`，以及由保存任务配出的 Mooncake 3 段。只在 dsv4.1 的段定义里生效（`shared_members`，13.4）；用包里的 `segments.json` 时照 v3，这类任务不归到任何请求上（已知问题第 16 条）。看板对缓存池段的取法和 v3 相同：一个请求有几条任务记录时，每一列取最大的一条。
  - 这些段表示的是请求等了多久，不是这个请求独占了多少工作量：同一个共用任务的时长会出现在每个成员上，所以不能把各请求的值相加来估算工作量。
  - 补丁作者说的「共用工作不能当作每个成员独占的工作」，针对的是工作量的统计，这里没有这样用。
  - 不这样计的话，有并发时共用任务可能是常态，P 的 submit、wait_for_transfer、后台 wait_for_save 和它的子段、put 下 3 段在真实负载下会大量为空。
  - 一个请求有几条缓存池任务记录时，看板对每一列取最大的一条。共用任务的时长通常比请求自己那条任务长，可能盖过请求自己的值，所以这几段可能比只看请求自己的任务时大。其中 P 的 start_load_kv/submit、start_load_kv/wait_for_transfer 在 TTFT 路径上，看板「占比」一列是它们除以 P 合计，值偏大时占比也跟着偏大（P 合计是 API server 量的，不随它们变）。
  - `bin/coverage.sh` 报出 P 的这几段里，值来自共用任务（`members[]` 不止一个请求）的请求有多少、占几成。这一项只在命令行输出里，不进看板。
- **C10** Mooncake 计时行配给保存任务的一次调用，必要条件是同一台机器、同一个线程（线程号对不上时见已知问题第 27 条）、时间落在调用区间内、key 数相等。字节数只在有几行都符合时用来区分，区分完要正好剩一行。配上的行字节数和 `submitted_bytes` 不相等时，计入拉取程序 `/status` 里 `mooncake` 那一行的 `bytes_mismatch`：约定认为两者相等，不相等说明约定这一处和现场不符。
- **C8** D 关了 `enforce_eager`（图模式）时，forward 先沿用同事补丁的定义，只计 host 侧耗时，不加设备同步。test 集群第一批数据出来后核对：forward 明显小于每步实际耗时时，改用不阻塞的设备事件计时，改的是补丁，看板不变。glm5.3 的段定义已按 C15 只用设备计时（3.6.5）；dsv4.1 的段定义仍是 host 侧耗时。

**口径说明（C13，段定义不变）：**

- **req_resolve** 的段定义是「ASGI 入口 → 进入 typed handler」，另外把模板渲染（`stages.render`）也算进这一段；不算的话，渲染就不落在任何一段里。包里的 `segments.json` 和 dsv4.1、glm5.3 的段定义都是这样。
- **P 的 start_load_kv/submit**（glm5.3）和 **D 的 start_load_kv/submit**（glm5.3）的口径和核对方法见 3.6.5。

**两个开关。** proxy 段要 `deploy.env` 的 `PROXY_COLLECT=1`，Mooncake 3 段要 `MOONCAKE_LOG_COLLECT=1`（13.2）。关着时对应的段为空，其余照常。

#### 3.6.5 v3.1-extra：glm5.3 的段定义

`profiles/glm53/segments.json` 给新增的 glm5.3 测试集群用（集群 `test-glm53`，`SEGMENTS_PROFILE=glm53`）。glm5.3 的环境：vLLM v0.30.0，vllm-ascend `d4ad49796`（有本地修改），P、D 都是 MooncakeConnectorV1 加 AscendStoreConnector，两边都是 `kv_both`；P `load_async=false`（同步加载），D `load_async=true`；`kv_load_failure_policy=fail`；deepseek_mtp（P k=1，D k=5）；P 是 eager，D 是图模式（`enforce_eager=false`）；V1 runner；P 每实例 TP16，D 每实例 TP1。记录格式以《glm5.3 记录格式约定》（glm5.3 版 1.3.1）为准。

段树和 dsv4.1 相同，仍是 L1/L2/L3 的 47 段，列名、看板都相同。和 dsv4.1 的段定义（交付时的那一份，3.6.4）有以下不同：

| 项 | dsv4.1 | glm5.3 | 原因 |
|---|---|---|---|
| `config_id` | `pd-diag-v3.1-extra-dsv41-2026-11-19` | `pd-diag-v3.1-extra-glm53-2026-11-19c` | 两种环境的数据不混在一起；末尾的字母把口径不同的各版分开：`…-19`（包 `76dec56e`），`…-19b`（包 `52b8824b`，forward、sampling 取不到设备值时退回 host），`…-19c`（这一版，只取设备值，C15） |
| P 的 start_load_kv/submit | `pool_task[operation=load_submit]`、`status=submission_returned` 的 `duration_ns`：异步加载的提交 | `pool_task[operation=load]` 的 `duration_ns`，只取 4 种终态（C11，见下） | P 同步加载，不写 `load_submit`，每个请求的加载记在它自己的 `load` 记录里 |
| P 的 start_load_kv/wait_for_transfer | 缓存池加载任务的排队时间加执行时间（C1） | 没有来源，为空 | 同步加载没有后台阶段，P 没有任何「等加载完成」的记录 |
| P 后台 wait_for_save | 保存任务的 `duration_ns` | 加上排队时间 `counters.queue_wait_ns`（C12，见下） | 段定义从保存批次进入保存线程算起 |
| D 第一步的 schedule/alloc、schedule/other | 含首次候选那一步的 alloc、other（C2） | 只取第一步自己的值，首次候选那一步只取 submit（C2 细化，见下） | 首次候选那一步的 alloc 是为接收 KV 分块，不是第一步的调度 |
| forward、sampling | host 侧耗时 `duration_ns` | 只取设备时间 `device_duration_ns`，没有时这一步留空（C15，见下） | host 侧的计时和设备时间不是同一个量（见 C15），退回 host 会让同一段在不同记录之间换含义 |
| 记录缺 `execution_id` | 拿 `record_id` 当步骤编号 | 每条算一步，这一项的第一步为空（`missing_execution_id`，见下） | 日志里没有的就留空，不推算 |

**从上一版换过来（已装 `76dec56e` 的 test-glm53）。** 用更新脚本 `run --cluster test-glm53 --profile glm53` 换包（新增集群操作说明附录 B）。换包以后、vLLM 重启以前，节点上还是上一版的过滤器程序，读不了这一版的段定义，照旧按上一版写按步累加的行；这些行带上一版的 `config_id`，看板不读，所以新口径的几段对新请求为空，重启后恢复（实验室：换包后约 2 分钟 47 段里 17 段有值，重启后 41 段，和新装相同）。回滚到 `76dec56e` 时不一样：节点上运行的是这一版的过滤器程序，它读得了上一版的段定义，回滚以后不等重启大多就有值（实验室：回滚后约 1 分钟 37 段，重启后 41 段）。

**C11（P 同步加载时的 submit）。**

- **来源：** `pool_task[operation=load]` 的 `duration_ns`。同步加载时，`start_load_kv` 对这一步的每个请求单独写一条记录（`member_count` 为 1，`request_id`、`execution_id` 是这个请求和这一步；`queue_enter_ns` 为空，没有排队计数）。
- **口径：** 同步加载，从开始处理到处理完，含同步 get 和拷到设备。每个请求一条，只含这一步的加载循环里属于这个请求的那一份，不含循环外的开销。
- **只取终态为 `succeeded`、`backend_failure`、`unknown_result`、`exception` 的记录**，这几种是实际花了时间的。过滤条件只支持等值，所以段定义里写成 4 条来源，一条记录只会对上其中一条。`all_hit`、`no_task`、`skipped`、`missing_load_spec` 不取：没命中缓存池的请求也会写一条只有几微秒的记录，不取它们，这一段对没命中的请求为空，不会显示成约 0。
- **`backend_failure` 照记录显示：** 加载失败时花掉的时间也在这一段里。
- **`exception` 的时长只算到异常抛出为止**，异常发生在 get 之前时，这个值接近 0。同步路径上的异常会一路抛到 Worker，这个进程多半随即退出，所以这种记录极少；看到 submit 状态为 `exception` 的请求时，先查 Worker 有没有重启过。
- **只取 TP rank 0 的记录**，和 C3 相同。
- **每个请求只有一个成员，C9 用不上。**
- **不取 Worker 整步的 `worker_summary[phase=execute].stages.submit`。** 有同步加载时，这个阶段包含这一步所有请求的同步加载，按 `request_ids` 会计到这一步的所有请求上，没命中缓存池的请求也算在内。反过来，同一步里各请求的 submit 加起来，约等于这一步的 `stages.submit`（差的是不取的那几种记录的几微秒）；第一批真实数据出来后核对这一项。

**C12（P 后台 wait_for_save 的起点）。** P 后台 wait_for_save 取保存任务的排队时间加处理时间，和 C1 同理：段定义从保存批次进入保存线程算起，要把排队时间算进来。glm5.3 的保存任务记了排队时间（`counters.queue_wait_ns`）。取法和 C1 相同：采集器把同一条保存任务记录的排队时间和处理时间先相加，一个请求有几条保存任务记录时取相加以后最大的一条。父段因此比 5 个子段之和多出排队时间和各段之间的间隙；5 个子段不变。出处：端到端测试 `tests/t51/e2e_v31.py` 的 glm53 一套，冷、热两个请求各有自己的一条保存任务和一条共用的保存任务（C9），看板显示 9.050 ms，是共用任务那一条的处理时间 9.000 ms 加排队时间 0.050 ms。

**C2 细化（D 第一步的 alloc、other）。** D 侧只取首次候选那一步的 submit，即 D 的 start_load_kv/submit。D 第一步的 alloc、other 不加上这一步的值，第二步起不变。段定义里 D 的「第一步」是 KV 到了以后第一次执行的那一步；首次候选那一步给这个请求做的 alloc 是为接收 KV 分块，不是第一步的调度。因此这一步的 alloc、other（毫秒以下）不落在 D 的任何段里。出处：端到端测试的 glm53 一套，D 上有首次候选那一步的请求 9 个，这一步的 alloc 是 0.031–0.062 ms、other 是 0.047–0.482 ms，D 第一步的 alloc、other 都只含执行那一步的值，和看板一致。

**C15（forward、sampling 的计时口径，取代 C14）。** glm5.3 的 forward、sampling 只取设备计时。段定义里这两段的来源只有一个路径 `stages.<段>.device_duration_ns`。一步的记录里没有设备值时，这一步不加值，这一段对这一步留空，不退回 host 侧耗时；一个请求的记录都没有设备值时，这两段为空。两段的定义因此是：**设备上执行这一步的时长**，forward 只计目标模型（`run_model`），sampling 只计采样器。设备值由补丁在 V1 runner 上用设备事件计得，只在 TP rank 0 记。用包里的 `segments.json` 和 dsv4.1 的段定义时照 v3，只取 host 侧耗时。

- **为什么不退回 host。** host 侧的计时和设备时间量的不是同一样东西：D 上 host 侧的 forward 只量到下发命令的开销；host 侧的 sampling 包住整个 `sample_tokens`，含 MTP 草稿的下发；设备事件只包住采样器和 `run_model`。退回 host 的话，同一段在不同记录之间会换含义，看板上看不出来。C14（包 `52b8824b`，`config_id` `…-19b`）取不到设备值时退回 host，这一版改掉。
- **补丁没写设备值时**（没换补丁，或者事件没读到），这两段为空。
- **留空次数。** 过滤器自检行里的 `acc_fallback`（列名沿用）在 glm5.3 的段定义下是这两段的留空次数：按段数出有这一段、但没有设备值的记录条数（一条记录是一步，进程启动以来累计；整条记录连这一段都没有的不算），写进 `vllm_pd.filter_selfcheck` 的 `acc_fallback` 列。
  - 要计数，段定义里这两段的来源必须写成只有一项的列表（`["stages.forward.device_duration_ns"]`），不能写成字符串：写成字符串时过滤器按单个路径处理，这两段不进自检行的 `acc_fallback`，留空也不计数，不报错。
  - 「这一段的对象在」靠补丁照旧写 host 侧的 `duration_ns`：补丁在一步没有设备值时，`stages.forward` 里仍有 `duration_ns`，这一步才计入留空次数。
  - 图模式按批大小分桶捕获图，服务中第一次遇到某个桶的那一步在捕获，没有设备值，所以留空次数不会一直是 0。操作说明 A 第 7 步按比例判：重启 10 分钟以后到判的时候这一段里，D 上留空的步占全部步的比例（按请求的步数加权：1 − 有设备时间的 forward 步数 ÷ 调度器的 alloc 步数，sampling 同理）超过 1%，而且留空次数在这一段里增加了，才算这一批失败；四种情况见操作说明 A 7.3。P 只记录。明显偏多时，加大补丁的推迟步数 K，或者排查设备计时。
- **步数。** D「第二步起」的步数只数有设备时间的 forward 步，留空的步不计（看板的步数取自 forward 这一段）。有留空的步时，「第二步起」的步数偏少，第二步起各段的「每步平均」按留空步所占的比例偏大，和设备时间无关的 schedule、alloc、other、detokenizer 也在内（已知问题第 34 条）。forward、sampling 自己的每步平均不受影响。
- **推迟写出。** 补丁在 rank 0 把这一步的 `worker_summary[execute]`、`[sample]` 推迟到读到设备值以后再写出，最多推迟 K 步（K=4），写出顺序按步骤先后。这两种记录的 `timestamp_ns`、`native_tid` 是写出的时刻和写出的线程，不是这一步结束的时刻和执行这一步的线程；记录里各阶段的开始、结束时刻不变。
- 推迟写出不改变各段的值和请求的第一步：
  - 过滤器按 `execution_id` 和请求号把值归到请求和步骤上，不按 `timestamp_ns`；`timestamp_ns` 只用来记分片第一条记录的时刻 `first_mono_ns`。
  - 过滤器每 5 秒写一次的是累计值，晚到的记录落进下一次写出，数值不变；请求的暂存因为空闲被清掉以后才到的记录另起一个分片，视图把各分片相加。
  - 视图在一个请求有几个分片时按 `first_mono_ns` 取最早的分片来定第一步和第一步的值，同一个请求各分片的第一步相同，取哪个都一样。
  - 看板按行的写入时刻 `ts` 开窗（窗口前多留 5 分钟、后多留 1 小时），请求按 API 到达时刻归窗口，晚几步写出的行仍在窗口里。
  - 出处：单元测试 `tests/t51/test_filter_device.py`，在 rc1 日志上（forward、sampling 补上和 host 时间相同的设备时间，现场的补丁两样都写）把 Worker 记录推迟 1–2 步写出，一个进程和 TP2 两种，另加两种情况：每一步后都写一次累计行；每批晚到的记录之前都清掉所有请求的暂存（D 的请求最多拆成 26 个分片）。三种段定义下，每个请求的各段之和、步数、第一步的值和第一步都和不推迟时相同。端到端测试 `tests/t51/e2e_v31.py` 的 shift 一套走完采集器和 ClickHouse，单请求 JSON 和不推迟时相同。
- **进程被强制终止时**（kill -9、崩溃），最多丢失最后 K 步的 Worker 记录；正常退出时补丁把剩下的写出。

**缺 `execution_id` 的记录（`missing_execution_id`）。** 段定义的 `missing_execution_id` 为 `own_step_first_null`。补丁 01 已装上、但移植时漏掉或改名了 `SchedulerOutput.pd_execution_id` 时，步骤记录不带 `execution_id`。包里的 `segments.json` 和 dsv4.1 的段定义拿 `record_id` 当步骤编号，D 第一步的 forward、sampling、alloc 会显示成 0，第二步起会把整个请求的值都算进去，看板上分不出是错数。glm5.3 的段定义改成：

- 累加规则读到的一条记录没有 `execution_id` 时，这条记录算一步，步数加一，合计照加。
- 这个请求这一项的第一步值记为未知：累计行写 `first_ns: null`。只要有一条缺，这一项的第一步就整体为空，不用其余几步拼一个值。
- 这个请求在这个进程里的第一条记录就缺 `execution_id` 时，请求的第一步未知：`first_exec` 写 null，这个请求的每一项第一步都为空。
- 看板上，第一步为空时，这一项的「第一步」「第二步起」两段都为空，不用「合计减第一步」去推；`first_exec` 为空时，D 的 detokenizer 第一步、第二步起也为空。合计、步数照记录。
- 过滤器自检行的 `exec_missing` 数出累加规则读到的、没有 `execution_id` 的记录条数（一条记录只数一次，进程启动以来累计），写进 `vllm_pd.filter_selfcheck` 的 `exec_missing` 列。第一批数据进来时它应当是 0；不是 0 时，先查 vLLM 移植版里 `SchedulerOutput.pd_execution_id` 有没有漏。
- 出处：单元测试 `tests/t51/test_filter_device.py`（合成记录：后面某一步缺、第一条就缺、两条规则读同一条记录只数一次；包里的和 dsv4.1 的段定义照 v3）；端到端测试 glm53 一套里直连请求的两个副本，见本节末尾。

其余照 dsv4.1：

- **C2（首次候选那一步）。** `candidate.map` 和 dsv4.1 相同的 4 条；D 侧只取这一步的 submit（见上面的 C2 细化）。glm5.3 只有 D 有首次候选那一步：D 从 P 读 KV 时用 consumer 映射记录和读任务记录（MooncakeConnectorV1 写的记录和 hybrid 连接器的字段逐一相同，过滤器不区分）；D 异步命中缓存池时用 `pool_load` 映射记录和 `load_submit` 记录（MultiConnector 对每个请求只用第一个报出可取 token 的子连接器，MooncakeConnectorV1 排在前面，所以这种情况很少）。P 同步加载，没有这一步，也不写 `pool_load`、`load_submit`，这几条在 P 上不起作用。

**被 D 退回 P 重算过的请求（读法，段定义不变）。** glm5.3 的 D 用 RecomputeScheduler，KV 块不够时会把请求退回 P 重算。proxy 重试时，客户端的请求号不变，vLLM 内部换一个新后缀，采集器把它解析成另一次尝试。看板按请求号把几次尝试合成一行：

- **第一步的各段和请求级的各段，取最早一次有值的尝试。** 取法是 ClickHouse 的 `argMin`，它跳过空值（用包里的 ClickHouse 26.8.36.3 实测：`argMin(a, b)` 对 `(NULL, 1), (5, 2)` 返回 5）。被退回的那次在 D 上只写了请求级记录，所以 D 的 queue_time 和 API server 的几段（req_resolve、tokenizer、add_request）是被退回那次的；D 第一步的 forward、sampling、alloc、other、detokenizer，被退回那次没有，是重试那次的。
- **第二步起的几段是各次之和。** 被退回的那次没有步骤，实际就是重试那次的值和步数。
- **D 合计取各次里最大的那次**，一般是重试那次。
- 单请求 JSON 的 `attempts` 大于 1，就是这种请求。

出处：端到端测试 glm53 一套的 retry 请求。同一请求号两次尝试：第一次在 D 上只有请求级记录，早 5 秒，排队 0.777 ms，只用了 5 ms；第二次照直连请求。看板这一行：attempts 2；D 第一步的 forward 44.264 ms、alloc 0.067 ms、detokenizer 0.289 ms，第二步起 forward 1169.46 ms、步数 47，都是第二次的；queue_time 0.777 ms、req_resolve 是第一次的；D 合计 1728.854 ms 是第二次的。

**被抢占过的请求（读法，段定义不变）。** glm5.3 的 D 用 RecomputeScheduler，请求会被抢占（重算型：放掉这个请求已有的 KV，重新排队，再从头算一次 prefill）。看板上的数值没有错，读的时候注意两点：

- **queue_time 只算从入队到第一次被选中。** 被抢占后重新排队的那段等待不计入任何段，所以被抢占过的请求，D 的合计（API server 口径）会大于各段之和。
- **D 的「第二步起 每步」会偏大。** 重算型抢占把一次完整的 prefill 放进「第二步起」，看板这一行是按步数平均的。「第二步起」的总值和步数都是对的，偏大的只是「每步」这个平均值。

**怎么确认一个请求被抢占过：** 看这个请求 `core_summary[scope=request]` 记录里的 `preemptions`（在 `members[]` 里，不是顶层字段；`diag_event` 的 `event` 列写成 `core_summary[request]`）。这种记录在 glm5.3 和 dsv4.1 两份段定义的 passthrough 里，采集器把整条原文存进 ClickHouse 的 `vllm_pd.diag_event` 的 `raw` 列，保留 `EVENT_TTL_DAYS` 天（缺省 15 天）；节点上的日志只留 12 小时，所以到监控机上查。`<请求号>` 是看板上「单请求拆解」用的那个请求号：

### 3.5 面板二和面板一的交点

面板二在三处用到面板一：

1. **Prometheus**：面板二往这个集群面板一的 `prometheus.yml` 里加一段标记为 `# BEGIN vllm-timing (面板二 <集群>)` 的内容（两个抓取任务、一个规则文件），用来发现拉取程序和采集器的故障并告警。没有面板一的集群（如 test）要另起一个 Prometheus。
2. **看板跳转**：面板二看板顶部的「面板一·P」「面板一·D」按钮跳到同一集群的面板一看板；没有面板一时不放这两个按钮。
3. **Grafana**：共用同一个 Grafana 和容器网络。面板二第一次装到一个 Grafana 上时要装 ClickHouse 插件并重启 Grafana 一次，以后的集群不再重启。

面板二的数据从 vLLM 进程里的过滤器开始，经节点日志、拉取程序、镜像目录、采集器进入 ClickHouse，再由看板查询；`segments.json` 决定每一环怎样处理这些记录，版本串用来核对各环用的是不是同一份规则。

### 4.2 注册表

**注册表**是监控机上执行账号家目录下的文件 `~/.vllm-pd-clusters.json`，记录这台监控机上每个集群登记的名字、端口、目录、UID 和机器，按面板（面板一、面板二）分别登记，不记密码。

- `add` 在建任何东西之前，按注册表查重：容器、端口、目录、UID、Prometheus 配置文件和机器都不能和别的集群相同，主机端口还要空闲。有冲突时报 `FAIL` 并停下。
- 一台节点机器只能属于一个集群：节点上的工作目录、mock 进程都按机器划分，两个集群共用一台机器会互相干扰。
- 一个 Prometheus（容器和配置文件）只能属于一个集群（v2.1 的限制，见第 16 节）。
- `bin/panel2_cluster.sh list` 和面板一的 `bin/panel1_cluster.sh list` 列出注册表的内容（9.1）。

集群名经固定规则派生出全部容器、端口、目录和 Grafana 对象的名字，注册表记录这些名字并在安装前查重，因此同一台监控机上的几个集群互不干扰。

# 第三部分 操作和接口

第二部分说明了每样东西在哪里；第三部分说明怎样操作它们。每条操作按同一格式写：

- **在哪：** 哪台机器、哪个目录。除另行说明外都在监控机上、用执行账号操作。
- **命令：** 完整命令，路径已填好。命令块前标【只读】或【会改】。
- **正常输出：** 实验室按内网状态（glm53-1 为 mock 模式、test 为 vllm 模式，两个集群都用 v2.1）执行得到的输出。实验室的机器少，台数、实例数和速率换成了内网的（12 台、每台 D 机器 16 个实例、`MOCK_RATE=64`），机器地址写作 `<地址>`；文件数、秒数随现场变化。
- **执行后：** 马上能看到的变化。
- **影响：** 对同一台机器上其他服务（另一个集群、面板一、Grafana、Prometheus）的影响。
- **前提、撤回：** 会改东西的操作另写两行：先要成立什么；做错了怎样回到原样，做不到的写「不可撤回」。

**第 2 步：按需要腾出空间。** 从上往下，影响越来越大：

| 措施 | 怎样做 | 能腾出多少 | 影响 | 撤回 |
|---|---|---|---|---|
| 降低 glm53-1 的 mock 速率 | 9.5 改 `MOCK_RATE` | 不腾出现有空间，增长按比例变慢（数据量和请求率成正比） | 看板上的请求变少 | 改回原值 |
| 缩短保留天数 | 9.5 改 `EVENT_TTL_DAYS`、`SUMMARY_TTL_DAYS` | ClickHouse 数据按天数成比例减少，几分钟到几小时内在后台删除 | 超出天数的旧请求查不到了 | 不可撤回（已删的数据） |
| 清空某个集群的请求数据 | 9.7 | 这个集群 ClickHouse 里的请求数据全部 | 看板上清空时刻以前的请求全部没有了 | 不可撤回 |
| 删早先部署留下的目录 | 见 5.4，逐个确认不再使用以后删 | 视目录而定，未测 | 先用附录 C 第 ② 行确认 Grafana 没有挂着它 | 不可撤回 |
| 删旧面板一 Prometheus 的数据卷 | 《停用旧面板一操作单》最后一节 | 未测 | 旧面板一的历史数据没有了 | 不可撤回 |

镜像目录的大小由节点保留的 12 小时日志决定，v2.1 里不能手工缩小（9.5）。

**磁盘已经满了时【会改】** 先停两个集群的拉取程序，让镜像目录不再增长（数据还在节点上，保留 12 小时）：

```bash
cd <总目录>/vllm-pd-grafana-panel2/glm53-1 && bin/puller.sh stop && cd <总目录>/vllm-pd-grafana-panel2/test && bin/puller.sh stop
```

腾出空间以后再 `bin/puller.sh start`（9.3），停止期间的日志会补拉回来，超过 12 小时的部分丢失。ClickHouse 写不进时，采集器先把数据存进磁盘缓冲（最多约 1.3 GB），缓冲满了就暂停读镜像，不丢数据。

**前提：** 第 1 步确认了是哪块盘。
**撤回：** 停拉取程序可以撤回（`bin/puller.sh start`）；删数据、删目录不可撤回。

不要手工删 ClickHouse 数据目录下的文件，也不要用 `docker system prune` 一类的批量清理（第 14 节第 5、6 条）。

磁盘快满时，先看清是哪个集群的哪个目录，再按影响从小到大选择：降速、缩短保留天数、清数据；已经满了时先停拉取程序止住镜像的增长。

面板二的日常操作都在集群目录里用 `bin/` 下的脚本完成：`check`、`status` 类命令只读，随时可以执行；启停和改参数只作用于这一个集群，其中只有清数据和缩短保留天数会删除数据。

## 10. 面板二集群的增减、切换和升级

本节的操作改变集群本身：新加一个集群，卸掉一个集群，从 mock 切到 vllm，用更新脚本升级或回滚，以及出问题时用的诊断工具。

### 10.1 加一个集群

**在哪：** v3 部署包目录 `<用户目录>/vllm-pd-panel2-update-v3/pack/vllm-pd-grafana-panel2`（更新脚本第一次 `run` 时解开）。出处：包二 README「装一个集群（一条命令）」；11-14 内网用 v2.1 部署包里的同一条命令装了 glm53-1 的面板二（《面板二改名和新增集群使用说明》C5b）。

前提：新集群的机器不属于任何已有集群（4.2）；监控机能免密 SSH 到这些机器；有面板一的集群直接用面板一的清单。

**【会改】** mock 模式、已有面板一的集群（以 glm53-1 为例，`N` 为 D 实例数）：

```bash
cd <用户目录>/vllm-pd-panel2-update-v3/pack/vllm-pd-grafana-panel2 && bin/panel2_cluster.sh add <集群名> --model-group GLM-5.3 --mode mock --inventory <总目录>/vllm-pd-grafana-panel1/<集群名>/prometheus/inventory.json --env-from <总目录>/vllm-pd-grafana-panel2/glm53-1/deploy.env --set MOCK_RATE=<N> --set CLICKHOUSE_MIN_DISK_GB=<10N+5> --set PULL_MIN_DISK_GB=<2N> --set CLICKHOUSE_DATA_DIR=<大盘上的目录，每个集群不同>
```

- `--env-from` 复制共用值（Grafana 账号、容器网络、监控机地址），不复制端口和名字。
- 节点上的 SSH 账号和已有集群不同时加 `--set SSH_USER=<账号>`。
- 两个磁盘门槛按 mock 速率估算（《面板二改名和新增集群使用说明》「磁盘预检值」）；默认值 1000 GB、200 GB 按 100 请求/秒估，速率低时可以按比例调低。

正常输出：`已写 <总目录>/vllm-pd-grafana-panel2/<集群名>/deploy.env：集群 …，模型文件夹 GLM-5.3，端口基数 …`；`==== 集群 …：查注册表、端口和清单` 下是 `RESULT: OK`；接着步骤 3–18 各自的输出；最后一行 `RESULT: OK（集群 … 装好了：看板在 Grafana 的「GLM-5.3」文件夹里）`。约 1–3 分钟。

失败时：命令停在哪一步就报哪一步，按 FAIL 行的提示改好以后重跑同一条命令，做完的步骤内容不变时会跳过。常见的几种见第 15 节最后几行。

执行后：GLM-5.3 文件夹里多一个面板二看板，几分钟内有数据。

影响：
- 监控机：新建这个集群的 ClickHouse、采集器两个容器和一个拉取进程，占用端口基数起的两个端口。
- Grafana：新加一个数据源和一个看板。第一次装面板二时还要装插件并重启 Grafana 一次，以后不再重启。
- Prometheus：往这个集群面板一的 `prometheus.yml` 加面板二的两段，热加载一次，面板一的数据不断。
- 节点：下发三个文件；mock 模式下启动 mock（开销见 6.3）。

没有面板一的集群（像 test），`add` 会停在步骤 6，要先起一个 Prometheus，再逐条执行其余步骤，做法见《面板二改名和新增集群使用说明》C4a–C4d。

**前提：** 机器不属于别的集群；监控机能免密 SSH 到这些机器；数据目录所在盘的剩余空间够两个磁盘门槛。
**撤回：** mock 模式的集群用 10.2 的 `remove` 卸掉（删数据；是最后一个面板二集群时会重启 Grafana）。中途失败时重跑同一条命令，或按 10.2 卸掉。

### 10.2 卸掉一个集群

卸集群分两种情况，做法不同。

**mock 模式的集群【会改，删数据】**（出处：包二 README「停止和卸载」）：

```bash
cd <用户目录>/vllm-pd-panel2-update-v3/pack/vllm-pd-grafana-panel2 && bin/panel2_cluster.sh remove <集群名>
```

它停 mock、删节点上本包的文件、删监控机上的容器、ClickHouse 数据、镜像、看板、数据源和 Prometheus 里的面板二段，最后注销并删掉集群目录。**两个限制：**这台监控机上只剩这一个面板二集群时，它会顺带删除 ClickHouse 插件并重启 Grafana（面板一跟着中断几秒）；它删除 ClickHouse 数据，不可恢复。

**vllm 模式的集群：**v3 的 `remove` 在「删数据」一步不再删掉过滤器正在写的日志：每个进程只删序号较小的旧文件，留下序号最大、正在写的那一个，输出写明删了几个、留下几个（第 16 节第 11 条；v3 的改动）。实验室走查（vllm 集群 test，有请求时执行 `remove`，再 `add` 回来）：
- 节点上的文件 SSH 账号能删时：删了 648 个、留下 310 个，和节点上剩下的文件数一致；正在写的 50 个文件都在，`remove` 以后 vLLM 照常往里写。留下的 310 个里，另外 260 个是之前已经退出的进程各自序号最大的文件，输出把它们也算成「正在写的」。
- 节点上的文件 SSH 账号删不掉时（实例目录属于 vLLM 的账号、SSH 账号没有写权限）：一个文件也没删，这一行仍记 OK，写成「删了 0 个」。
- 两次重新 `add`，各约 20 秒做完，做完 5 秒内看板有数：节点上留着的日志重新导入，新请求接着进来。

留下的文件要等维护 vLLM 的人去掉两行 export、重启 vLLM 以后再手工删。`remove` 的另一个限制仍在：这台监控机上只剩这一个面板二集群时，它会删除 ClickHouse 插件并重启 Grafana。要避开这一点，或者要节点上的日志一个都不删，按《面板二改名和新增集群使用说明》C3a–C3e 逐条执行：`uninstall_old.sh plan` → `uninstall_old.sh remove`（不带 `--remove-plugin`）→ 删监控机上的 ClickHouse 数据卷或数据目录、镜像和拉取状态（不碰节点）→ `uninstall_old.sh check` → `names.py unregister` → 删集群目录。11-14 内网按这个顺序卸掉了旧的 glm53-1 面板二（当时接的是 test 的两台机器），实验室核对过：节点文件、日志、vLLM 都没动。vLLM 启动脚本里的两行 export 和挂载要由维护 vLLM 的人去掉并重启 vLLM，面板二才和这些机器完全脱开。

影响（两种都是）：这个集群的看板从 Grafana 消失；面板一的看板、Prometheus 的数据和其他集群不受影响（`remove` 删插件的情况除外）。

**前提：** 确认这个集群的面板二数据不再需要；vllm 模式按逐条做法。
**撤回：** 不可撤回：ClickHouse 数据被删除，重新 `add` 得到的是空集群。vllm 模式的逐条做法保留节点日志，重新装回后最近 12 小时的日志会重新导入。

### 10.3 从 mock 切到 vllm

glm53-1 以后接入真实 vLLM 时用。出处：包二 README「从内网切到模型推理环境」和「模型推理环境」一节、v2.1 版《内网升级总说明》第 4 节（实验室走通，内网的旧 glm53-1 11-13 按它切过；v3 版的总说明只讲升级，没有这一节）。v3 没有改切换的做法。步骤要按下面的顺序：先在 mock 模式下用 `bin/nodes.sh clean` 停 mock、删节点上 mock 的文件，切到 vllm 模式以后再清数据。`bin/clear_data.sh --yes`（不带 `--all`）在 mock 模式下会重新启动 mock，所以不要在切换以前执行它。步骤：

1. **先向现场确认：** vLLM 容器里日志目录和节点文件目录的宿主机路径和容器内路径、容器用户的 uid、启动脚本能否修改、每个实例的 `vllm serve --port`（包二 README「先向现场确认的事」表）。
2. **【会改】备份并停 mock：** 在集群目录里 `cp -p deploy.env deploy.env.mock-backup && cp -p inventory.json inventory.json.mock-backup`，然后 `bin/nodes.sh clean`（停 mock，删节点上 mock 的文件和日志）。
3. **【会改】以 vllm 模式重跑 add**（在部署包目录）：`bin/panel2_cluster.sh add glm53-1 --model-group GLM-5.3 --inventory <清单> --mode vllm --set NODE_CONF_DIR=<宿主机目录> --set NODE_LOG_DIR=<宿主机目录>`（容器里路径不同时再加两个 `…_IN_CONTAINER`）。内容不变的步骤跳过，不启动 mock。
4. **【会改】清空 mock 留下的全部数据：** `bin/clear_data.sh --yes --all`。
5. **改 vLLM：** 在集群目录执行 `bin/nodes.sh paths`，按每台的输出给 vLLM 启动脚本加两行 export、给容器加两个挂载（7.3），重启 vLLM（由维护 vLLM 的人做）。
6. **确认：** `bin/diag.sh vllm`，每台结论为 OK；有请求以后 `bin/panel2_cluster.sh check glm53-1`。

退回 mock 的做法见 v2.1 版《内网升级总说明》4.8。

**前提：** 第 1 步要确认的各项都已清楚；维护 vLLM 的人能修改启动脚本并重启 vLLM。
**撤回：** 按 v2.1 版《内网升级总说明》4.8 退回 mock（用第 2 步备份的 `deploy.env`、`inventory.json`）；第 4 步清掉的 mock 数据不可撤回。

### 10.4 用更新脚本升级和回滚

**更新脚本**（v3 是 `<用户目录>/vllm-pd-update-v3/vllm_pd_update_pack2_filled.py`）把一个集群的面板二从 v2.1 升到 v3，或者回滚到 v2.1。v3 起加了 `--cluster <集群名>`，不写时是 glm53-1；没有面板一的集群（test）也能用，面板一那几项不做。它写死了总目录 `<总目录>` 和 `<用户目录>` 下的包路径；集群由 `--cluster` 选，一次只做一个集群。出处：v2.1 版《内网升级总说明》2.2、2.3、第 5 节；v3 的步骤见 v3 版《内网升级总说明》第 2–9 步。

| 子命令 | 作用 | 只读 / 会改 |
|---|---|---|
| `check` | 迁移预览、升级前的安全检查、升级前比对（哪些「不变」会跳过），不改集群 | 只读（会把包解到 `pack/`） |
| `run` | 备份 → 迁移 → 更新 → 升级安全检查；备份在 `~/vllm-pd-update-backup/<时间>/` | 会改 |
| `rollback <备份目录>` | 恢复到那份备份记录的状态 | 会改 |

```bash
cd <用户目录>/vllm-pd-update-v3 && python3 vllm_pd_update_pack2_filled.py check
```

正常输出：9 项检查和三段预览，最后 `RESULT:` 一行；摘要第一行写着「包二 v3，集群 glm53-1」。

v3 的更新脚本只接受 v2.1 和 v3 的集群目录。`run` 和 `rollback` 不看数据流（链路通不通、过滤器版本、有没有数据进来、mock 在不在跑都不拦它们），只查保护机器和别的服务的几项：两个包和 sha256、解包要的磁盘空间、集群目录、ClickHouse 容器、Grafana 账号和注册表。`run` 备份、把手改过的节点日志保留时长迁移进 `deploy.env`（9.5）以后，先列出这个集群库 `vllm_pd` 里请求数据的行数，删掉两张表 `phase_line`、`diag_event` 和三个视图，更新以后从空表开始；过滤器自己的三张记录表 `filter_file`、`filter_selfcheck`、`filter_other` 保留，和 `bin/clear_data.sh` 一样（vLLM 不重启时过滤器不会重写文件头，删了以后检查会一直报缺进程的文件）。`rollback` 同样先删，再由 v2.1 建成空表。删掉的数据不进备份，不能恢复。最后核对不变的项时，面板一的 check 和升级前比，不算本集群面板二挂在面板一 Prometheus 上的两个抓取任务（`vllm-timing-puller-<集群>`、`vllm-timing-central-<集群>`）：它们刚被重启，Prometheus 还没重新抓到。`check` 是可选的核对，只读，结果不影响 `run`。具体步骤、每一步看到什么、对同机其他服务的影响，见 v3 版《内网升级总说明》。11-14 以前的备份记的是 test 的配置，不要用它回滚 glm53-1；《面板二改名和新增集群使用说明》C6 把它们挪到 `~/vllm-pd-update-backup-before-1114/`，还没做 C6 时先做这一步再执行 `run`。

影响：`run` 和 `rollback` 只动 glm53-1 的面板二；Prometheus 的面板二段不变时不重载，Grafana、vLLM、面板一都不重启（《内网升级总说明》「对同机其他服务的影响」）。

**前提：** 用执行账号；`<用户目录>` 至少空出 500 MB；`check` 没有不能忽略的 FAIL；集群目录里的 `segments.json` 没有手改过（9.5）。
**撤回：** `run` 用 `rollback <run 摘要里的备份目录>` 撤回；`rollback` 本身不可再撤回，要回到新版就重新 `run`。

**v3.1-extra 的更新脚本**（`<用户目录>/vllm-pd-update-v3.1-extra/vllm_pd_update_pack2_v31extra_filled.py`）把指定的一个集群从 v3 升到 v3.1-extra，或者回滚到 v3；`--cluster` 不写时是 test。和 v3 的脚本相比：

- 只接受 v3 和 v3.1-extra 的集群目录，v2.1 及更早的先用 v3 的脚本升到 v3。
- `--profile <段定义>` 把 `SEGMENTS_PROFILE` 写进这个集群的 `deploy.env`，`run` 用包里 `profiles/<段定义>/segments.json` 作它的段定义。迁移预览这时只报一行「段定义换成新包的 profiles/…」，不逐键列出差别。
- `run` 的摘要多一行，写明段定义和两个来源开没开。两个来源默认不开，打开的方法是改 `deploy.env` 再 `bin/puller.sh restart`（内网操作说明 B）。
- `rollback` 在恢复目录以前先停拉取程序，删掉 `PULL_DIR` 下 v3.1-extra 多出来的 `_proxy`、`_mooncake`、`_native` 三个目录和配对状态。v3 的采集器读不懂这三个目录里的文件。`apply_segments.sh` 之后再用 v3 的脚本启动拉取程序。
- 删数据和 v3 相同：库 `vllm_pd` 里除过滤器三张记录表以外的表和视图都删，`proxy_line`、`proxy_selfcheck` 也在内。其他集群不动。

vllm 模式下，过滤器程序 `pd_diag_logfilter.py` 换了，升级和回滚以后都要重启 vLLM 才用上，和内网操作说明 A 的重启合在一次做。

### 10.5 诊断工具

**【只读】** 看板空了、数据断了，或者切到 vllm 以后，在集群目录里执行：

```bash
cd <总目录>/vllm-pd-grafana-panel2/glm53-1 && bin/diag.sh all
```

它依次查节点、vLLM（vllm 模式）、链路、监控机，每项一行，FAIL、WARN 排在前面，`→` 后面是修法；报告写在 `~/vllm-pd-diag-reports/<集群>/`。子命令和含义见 13.1，结论的读法见集群目录里的 `docs/诊断工具说明.zh-CN.md`。正常输出的结尾（mock 模式，节选）：

```
== chain（节点日志 → 镜像 → 采集器 → ClickHouse）
OK   拉取：12 台，最久的 5 秒前成功
OK   ClickHouse：… 个实例，最新一行最多落后 19 秒（vllm_pd.phase_line_cur）
OK   采集器缓冲：5 个输出共 0 条积压
OK   解析失败：最近 10 分钟 0 行；dead-letter 0 行
== monitor（监控机）
OK   ClickHouse 数据（<glm53-1 的数据目录>/data）：已用 …%，空闲 … GB
OK   拉取程序在运行
OK   Grafana 正常
报告：<家目录>/vllm-pd-diag-reports/glm53-1/diag-all-<时间>.txt
RESULT: OK
```

glm53-1 的 12 台目前没有 vLLM 和 exporter 在面板一的端口上应答时，`monitor` 一段会有一行 `WARN Prometheus：… 个目标，… 个 down`，这是面板一的抓取目标，不影响面板二。test 用 `bin/diag.sh vllm` 看每台 vLLM 的变量、挂载和过滤器，结论行是 `OK   <地址> <容器> 结论：日志配置生效，过滤器在写，标准输出里没有新的 [PD_DIAG]`。

影响：只读。除 `pair`（经 proxy 发 3 个请求）以外，ClickHouse 查询带只读参数，节点上只执行读的命令。

### 13.2 deploy.env 的键

`deploy.env` 是面板二集群目录里的参数文件（面板一目录里也有一份，只含面板一的名字和端口）。改完以后要执行对应的命令才生效：

| 键 | 含义 | 改了以后执行 |
|---|---|---|
| `MOCK_RATE` | mock 模式全集群每秒请求数。每个 D 实例不超过 1.5 请求/秒，即不超过 D 实例数 × 1.5；留空时等于 D 实例数 | `bin/nodes.sh start` |
| `EVENT_TTL_DAYS`、`SUMMARY_TTL_DAYS` | 事件表、汇总表的保留天数（默认 15、30） | `bin/apply_segments.sh` |
| `NODE_LOG_KEEP_HOURS` | 节点上的过滤器保留日志文件的小时数，留空时 12（v3 新增，9.5） | `bin/apply_segments.sh` |
| `GRAFANA_BOARD_TITLE`、`GRAFANA_DS_NAME` | 看板标题、数据源名字（留空时按集群名派生） | 见 9.6 |
| `NODE_MODE` | `mock` 或 `vllm` | 不单独改，按 10.3 切换 |
| `NODE_CONF_DIR`、`NODE_LOG_DIR` | 节点上放三个文件、写日志的目录（宿主机路径） | 重跑 `add`（vllm 模式还要改 vLLM 启动脚本） |
| `NODE_CONF_DIR_IN_CONTAINER`、`NODE_LOG_DIR_IN_CONTAINER` | vllm 模式下上面两个目录在 vLLM 容器里的路径，留空时与宿主机相同 | 同上 |
| `NODE_VLLM_CONTAINERS`、`NODE_VLLM_STDOUT_FILES`、`NODE_CONTAINER_UID` | vllm 模式下诊断和自检用的容器名、标准输出文件、容器用户 uid | 下次执行 `diag.sh`、`nodes.sh selfcheck` 时生效 |
| `PULL_INTERVAL_S`、`PULL_CONCURRENCY`、`PULL_TIMEOUT_S` | 拉取间隔（秒）、同时拉几台、单台超时 | `bin/puller.sh restart` |
| `SSH_USER`、`SSH_OPTS` | 拉取和 `nodes.sh` 用的 SSH 账号和参数 | `bin/puller.sh restart` |
| `CLICKHOUSE_MAX_SERVER_MEMORY_MB` | ClickHouse 的内存上限（MiB），留空不限 | `bin/clickhouse_up.sh` |
| `SEGMENTS_PROFILE` | v3.1-extra：段定义，留空用包里的 `segments.json`；`dsv41` 用 `profiles/dsv41/segments.json`，`glm53` 用 `profiles/glm53/segments.json`（3.3） | 重跑 `add`，或用更新脚本的 `--profile` |
| `PROXY_COLLECT`、`PROXY_MACHINE`、`PROXY_LOG_DIR` | v3.1-extra：是否采 proxy 的行（`1` 采，留空或 `0` 不采）；proxy 所在机器（SSH 地址）；它在那台机器上的日志目录 | `bin/puller.sh restart` |
| `MOONCAKE_LOG_COLLECT`、`MOONCAKE_LOG_FILES` | v3.1-extra：是否采 Mooncake 的计时行；vLLM 标准错误的去处，`地址=来源`，来源写宿主机路径（可用通配符）、`exec:容器名:/容器里的路径` 或 `logs:容器名`，几个用分号分开，各台之间用逗号；后两种来源要求 `SSH_USER` 在节点上有 docker 权限 | `bin/puller.sh restart` |
| `MOONCAKE_TID_FALLBACK` | v3.1-extra：Mooncake 计时行的线程号对不上时是否兜底；默认 `0` 只按线程号配，环境检测结果的 `glog=` 是 0.7 及以上时设 `1`（已知问题第 27 条） | `bin/puller.sh restart` |

下列键在安装时确定，装好以后不要改：`CLUSTER`、`MODEL_GROUP`、`PORT_BASE`、`VLLM_PD_ROOT`、`CLICKHOUSE_DATA_DIR`、`PULL_DIR`、三个 `CH_*_PASSWORD`、容器名和 UID 一类的派生项。共用的 `GRAFANA_URL`、`GRAFANA_USER`、`GRAFANA_PASSWORD`、`GRAFANA_CONTAINER`、`DOCKER_NETWORK`、`MONITOR_HOST` 在每个集群的 `deploy.env` 里各有一份，Grafana 密码改了要每个集群都改。全部键的说明见集群目录里的 `deploy.env.example`。

### 13.3 inventory.json

字段见 2.3。面板二只用其中的 `prefill`、`decode` 两段（`api_servers` 和 `procs_per_instance`），按 `api_servers` 的顺序给实例编号，按「机器地址:端口」认出每个实例。面板一用全部字段。

改面板二清单（加减实例或机器）以后，在集群目录里依次执行（出处：包二 README「改拓扑和速率」）：`bin/nodes.sh paths`、`bin/nodes.sh push`，mock 模式再执行 `bin/nodes.sh start`；然后 `bin/puller.sh restart`、`bin/central_up.sh`。改面板一清单见 11.1。新加的机器不能已经属于别的集群（4.2）。

### 13.4 segments.json

`segments.json` 是 JSON 文件，顶层各键的作用：

| 键 | 作用 | 人工改不改 |
|---|---|---|
| `version`、`config_id` | 规则格式的版本和这份规则的名字；`config_id` 进入版本串和视图的筛选条件 | 不改 |
| `line` | 过滤器写盘的参数：`log_dir`（容器里的日志目录，由 `NODE_LOG_DIR_IN_CONTAINER` 写入）、`rotate_mib`（256）、`keep_hours`（由 `NODE_LOG_KEEP_HOURS` 写入，留空时 12）、`flush_seconds`（5）、`selfcheck_seconds`（60）等 | 不改；`log_dir`、`keep_hours` 改 `deploy.env` |
| `roles` | 怎样从进程名认出 api、engine、worker，`pool_task` 归 pool；worker 和 pool 保留哪些 TP rank（`keep_tp_rank`，默认 `[0]`） | 一般不改 |
| `passthrough` | 哪些记录原样写盘（`api_summary`、`core_summary` 的请求级记录） | 不改 |
| `accumulate` | 哪些逐步记录在进程里按请求累加，取哪个字段。v3.1-extra：字段可以写成路径列表，取第一个不为空的；只有一项的列表取不到时这一步留空，自检行计入留空次数（glm5.3 的 forward、sampling，C15） | 不改 |
| `missing_execution_id` | v3.1-extra，只在 glm5.3 的段定义里：`own_step_first_null`，累加规则读到的记录没有 `execution_id` 时算一步、这一项的第一步为空（3.6.5）；没有这个键时照 v3 拿 `record_id` 当步骤编号 | 不改 |
| `shared_members` | v3.1-extra，只在 dsv4.1、glm5.3 的段定义里：事件名列表（`pool_task`、`pd_native_put`）。这些记录不带单个请求号时，按 `members[]` 计给每个成员（C9，3.6.4）；没有这个键时照 v3 | 不改 |
| `candidate` | v3.1-extra，只在 dsv4.1、glm5.3 的段定义里：`map` 列出写明「请求号、步骤编号」的记录，`accumulate` 列出首次候选那一步要计给请求的值，`hold_steps`、`hold_seconds` 是过滤器暂存步骤值的上限（C2，3.6.4） | 不改 |
| `sides`、`request` | P、D 两侧的段和请求级字段各取自哪条记录的哪个字段，看板的段由它决定。v3.1-extra 里 proxy 下的段可以写 `{"proxy": "<proxy 行的字段>"}`，Mooncake 3 段的来源是拉取程序写的 `pd_native_put` 记录 | 不改 |

`segments.json` 整份不手改：升级安全检查把它和包里的校验值比较，只放过由 `deploy.env` 写入的 `line.log_dir` 和 `line.keep_hours`；改了任何其他键，`check` 的「版本和文件」一项就固定报 FAIL 并拦住升级。它随新版本的部署包更新；日志格式变了时由维护者改，方法见包二 README「映射规则：日志变了怎么改」。

## 14. 不要做的事

本节集中列出会造成数据损失、服务中断或误导判断的操作。每条写后果和应该怎样做；前三部分相应的位置也有提示。

| 不要做的事 | 后果 | 应该怎样做 |
|---|---|---|
| 1. 对 vllm 模式的集群（test）执行 `panel2_cluster.sh remove` 或 `uninstall_old.sh purge-data` | v2.1 的 `remove` 会删掉过滤器正在写的日志；v3 只删旧序号的文件，留下正在写的那一个（第 16 节第 11 条），SSH 账号没有写权限时一个也删不掉、却仍记 OK（已知问题）。卸的是最后一个面板二集群时，还会删插件并重启 Grafana | 按 10.2 的逐条做法卸 |
| 2. 在 vLLM 运行时删节点 `NODE_LOG_DIR` 里的文件 | 同第 1 条，新数据到不了看板，要等换文件或重启 vLLM | 清数据用 `bin/clear_data.sh --yes`（9.7），它在 vllm 模式下不动节点 |
| 3. 手改集群目录里的 `segments.json`（包括 `keep_hours`） | 此后每次 `check` 的「版本和文件」都报 FAIL，更新脚本的 `run` 被拦住 | 不改；保留时长等下一版做成 `deploy.env` 的键（9.5） |
| 4. 不是换环境时执行 `bin/clear_data.sh --yes --all` | 连过滤器的文件记录一起清，清完以后检查报「没有过滤器写的文件」，要重启 mock 或 vLLM 才恢复 | 只清请求数据用 `--yes`（9.7）；`--all` 只在 10.3 切换模式时用 |
| 5. 执行 `docker system prune`、`docker volume prune` 一类的批量清理 | 没在运行的容器的数据卷被删除，不可恢复：旧面板一 Prometheus 的数据卷，以及停着的 Prometheus、ClickHouse 的数据卷 | 删容器时指名删：`docker rm -fv <容器名>`；数据卷是否保留逐个决定 |
| 6. 手工删 ClickHouse 数据目录下的 `data`、`vector`、`pull` 里的文件 | 删 `data`：面板二的数据全部丢失，ClickHouse 可能起不来；删 `vector`：丢掉还没写进 ClickHouse 的行；删 `pull`：节点上还在的文件会被拉取程序原样拉回 | 清数据用 9.7，空间不够按 9.8 |
| 7. 用 11-14 以前的更新备份回滚 glm53-1，或执行 11-13 手改过的旧更新脚本（`<用户目录>/vllm-pd-update-v1.0/`、`…-v2.0/`） | 把 test 的配置写回 glm53-1 名下，或用旧版脚本改坏 v2.1 的集群 | 只用 `<用户目录>/vllm-pd-update-v3/` 的更新脚本和它 `run` 时做的备份（10.4） |
| 8. 在 Grafana 界面上改看板，并以为改动会保留 | 下一次 `add`、`apply_segments.sh` 或更新脚本按模板重新导入看板，界面上的改动被覆盖 | 需要长期保留的改动交给维护者改模板 |
| 9. 把一台机器同时放进两个集群，或让两个集群共用 `CLICKHOUSE_DATA_DIR`、Prometheus | `add` 会报 FAIL；绕过注册表手工配置时，两个集群的 mock、日志目录和数据互相覆盖 | 一台机器只属于一个集群，每个集群用自己的数据目录和 Prometheus（4.2） |
| 10. 改 `deploy.env` 里安装时确定的键（`CLUSTER`、`PORT_BASE`、`VLLM_PD_ROOT`、`CLICKHOUSE_DATA_DIR`、`PULL_DIR`、三个 ClickHouse 密码） | 脚本找不到原来的容器、目录和数据；改密码以后 ClickHouse 里的账号、采集器配置和 Grafana 数据源不同步，写入或查询失败 | 只改 13.2 表里列出的键 |
| 11. 换一个账号执行命令 | 找不到注册表和更新备份，`add` 把这台监控机当成没有别的集群，可能分配冲突的端口 | 一律用执行账号（5.2） |
| 12. 删 `<用户目录>` 下早先部署的目录，尤其是旧面板一目录 | Grafana 容器可能仍挂着旧面板一目录里的文件（待确认），删了以后 Grafana 重启时可能起不来 | 先用附录 C 第 ② 行看 Grafana 容器的挂载，再决定 |

这些操作的共同点是绕过了包里的脚本或注册表：用脚本做的操作会先检查、只动一个集群，手工删除、批量清理和改装好以后不该改的参数则没有这层保护。

## 15. 现象、检查和修法对照表

本节按现象列出检查命令和修法。命令都在监控机上执行；「集群目录」指 `<总目录>/vllm-pd-grafana-panel2/<集群>`。不知道问题出在哪一环时，先在集群目录里执行 `bin/diag.sh all`（10.5），它逐段报出哪一段不对、怎样修；看板没有新数据时按 15.1 沿数据流逐站查。

### 15.1 数据在哪一步断了

看板没有新数据时，沿图 3 的数据流从节点往看板一站一站查，第一个不正常的站就是断点。下表的命令都是只读的，在集群目录里执行；以 glm53-1 为例，test 把目录、容器名、数据源 UID 和端口换成 test 的（端口 18110，数据目录 `<test 的数据目录>`）。

| 站 | 查什么 | 命令 | 正常 | 不正常时 |
|---|---|---|---|---|
| 1. 节点在写日志 | mock 进程在不在；vllm 模式下过滤器在不在写 | mock：`bin/nodes.sh status`；vllm：`bin/diag.sh vllm` | mock 每台 `OK … mock 进程 16 个，应为 16 个`；vllm 每台结论行 `日志配置生效，过滤器在写` | mock：`bin/nodes.sh start`（9.2）；vllm：按结论行 `→` 后面的修法 |

| 3. 镜像目录 | 最近 1 分钟有没有文件更新 | `find <glm53-1 的数据目录>/pull -name '*.log' -mmin -1 \| wc -l` | 大于 0（实验室 27） | 0：回到第 2 站 |
| 4. 采集器 | 容器在不在运行；积压和解析失败 | `docker ps --filter name=vllm-pd-vector-glm53-1 --format '{{.Names}} {{.Status}}'`，再看 `bin/diag.sh chain` 的「采集器缓冲」「解析失败」两行 | `Up …`；积压不持续增长；解析失败 0 行 | 容器停了：`bin/central_up.sh`（9.4）；解析失败：15.3 |
| 5. ClickHouse | 最新一行落后多少秒 | `(set -a; . ./deploy.env; curl -s -u "vllm_reader:$CH_READER_PASSWORD" http://localhost:18100/ --data-binary "SELECT max(ts) AS latest, dateDiff('second', max(ts), now64(3)) AS lag_s FROM vllm_pd.phase_line_cur FORMAT TSVWithNames")` | 第二行的 `lag_s` 小于 135（节点在跑时，应当在拉取间隔附近）。实验室镜像里节点没在跑，`lag_s` 很大（实测 115078），不代表正常值 | 远大于 135：看第 4 站；连不上：ClickHouse 容器停了，`bin/clickhouse_up.sh`（9.4） |
| 6. 数据源 | Grafana 能不能连上 ClickHouse | `(set -a; . ./deploy.env; curl -s -u "$GRAFANA_USER:$GRAFANA_PASSWORD" "$GRAFANA_URL/api/datasources/uid/vllm-pd-clickhouse-glm53-1/health")` | `{"message":"Data source is working","status":"OK"}` | 数据源不在：`bin/grafana_board.sh`（15.2） |
| 7. 看板 | 时间范围和地址栏 | 看浏览器 | 所选时间范围内有数据 | 地址栏带着 `var-clickhouse=&`：15.2 第 1 行；时间范围内没有请求：放大范围 |

`bin/diag.sh chain` 一次查完第 1–5 站，每站一行，阈值是节点 65 秒、镜像 75 秒、ClickHouse 135 秒以内算 OK。实验室按内网状态执行的输出（mock 模式，节选）：

```

OK   拉取：12 台，最久的 5 秒前成功
OK   镜像 <地址>：最新文件 6 秒前改过
OK   ClickHouse：… 个实例，最新一行最多落后 17 秒（vllm_pd.phase_line_cur）
OK   采集器缓冲：5 个输出共 1010 条积压
```

采集器的日志里常有 `Currently ignoring file too small to fingerprint` 一类的 WARN，是新文件刚创建时的正常提示，不表示故障。

## 16. 已知问题

本节先列 v2.1 的 14 条已知问题在 v3 的状态，再列 v3 新的已知问题。**结论：** v2.1 的第 7、8、9、10、14 条和第 11 条的第 ③ 点在 v3 修了，第 11 条第 ① 点改了一部分，修法都有单元测试；其中第 8、9、10 条的原因只查清了一部分，修法要在实验室或内网验证后才能确认生效。其余各条不修，仍按每条后面的人工办法处理。v3 新的已知问题主要是新日志带来的缺口和没有在硬件上验收过的情况，都不影响原有 25 个段的数据。

### 16.1 v2.1 的 14 条在 v3 的状态

条号沿用 v2.1，方便和《内网升级总说明》、设计文档对照。

1. **mock 和拉取程序开机不会自己起来。**（不修）机器重启以后执行 `bin/nodes.sh start`、`bin/puller.sh start`（第 12 节）。
2. **`bin/nodes.sh status` 不显示 mock 的积压数。**（不修）用 `bin/diag.sh nodes` 看「主循环卡没卡」一行。
3. **mock 写状态文件遇到磁盘满时直接退出。**（不修）`check` 的「日志量和空闲空间」一项事先报出来。
4. **回滚以后，独立诊断工具会报「没有重启」。**（不修）诊断一律用集群目录里的 `bin/diag.sh`，它不受影响。
5. **`segments.json` 重读以后，已打开文件的文件头仍是旧版本。**（不修）检查按行判，不受影响。
6. **vllm 模式只清请求数据以后，仍有约 30 秒的旧行。**（不修）清空前约 30 秒内在途的行会在清完以后写进来；没有请求时为 0。
7. **重启 mock 或下发了内容不同的 `segments.json` 以后约 2 分钟内，`check` 误报「两个以上版本同时在写」。**（v3 修了）原因是检查把已经退出的旧进程留在窗口里的最后一行自检也算了进去，新进程又要约 80 秒才写出第一行自检。v3 的检查先在节点上列出还在运行的过滤器进程（mock 模式查 mock 进程，vllm 模式查 vLLM 进程），只数它们的自检行；重启以后才启动、还没有自检行的实例记 `INFO`；`segments.json` 下发以后 120 秒内，还有进程是旧版本时记 `INFO`，两种模式都是。真的有旧进程在运行时，过了这 120 秒仍记 `FAIL`。读不到节点上的进程时，退回 v2.1 的判法。实验室核对：修前，v2.1 下发 `segments.json` 以后，check 的「过滤器版本」报 FAIL；修后，新装、`run` 和回滚以后约 2 分钟内记 INFO（刚启动），之后变 OK，没有再报 FAIL。
8. **看板沿用旧 UID 重建以后，可能报「Datasource was not found」。**（v3 修了）v3 给数据源变量加了 `skipUrlSync`，看板不再从地址栏读这个变量。实验室在 Grafana 12.4.2 上打开带空 `var-clickhouse=` 参数的看板地址核对：修前，v2.1 的看板报「Datasource was not found」，全部面板 No data；修后，v3 的看板照常出数，没有报错。不生效时仍按 v2.1 的办法：不带参数打开一次看板地址。
9. **`diag.sh vllm` 可能误报「主进程没有 VLLM_LOGGING_CONFIG_PATH」「PYTHONPATH 里没有 …/conf」。**（v3 修了，内网原因待确认）诊断读进程命令行时，把换行、制表符也换成空格，命令行里有多行 JSON 时不再把一行拆断；比较 PYTHONPATH 时去掉末尾的斜杠。集群目录里的 `bin/diag.sh` 和独立诊断工具同时改了。单元测试用带换行的命令行核对过修法；内网的误报是不是这个原因，要在内网执行 `bin/diag.sh vllm` 才能确认。
10. **vllm 模式下空闲时，`check` 的「链路通」报 FAIL，`--wait` 一直等到超时。**（v3 修了，空闲时为什么窗口里没有行待确认）每个实例这次启动以后都写过记录、拉取程序最近 2 分钟成功过、窗口内却没有这一版的行时，v3 看每个实例最新的自检行：都在阈值（默认 135 秒）的 3 倍以内时记 `WARN 链路通：…最近没有请求`，`--wait` 不再等这一项；有实例超过 3 倍或没有自检行时仍记 `FAIL`，写明是哪几个实例。`bin/diag.sh chain` 的 ClickHouse 一行同样处理。代价是：过滤器的自检停了但拉取正常的情况，在 3 倍阈值以内也只记 `WARN`。实验室核对：修前的现象实验室复现不了，v2.1 的 vllm 集群让替身空闲 4 分钟、只在有请求时写记录，check 的「链路通」仍是 OK；修后在过滤器写不进文件的情况下核对，最新自检行在 405 秒（阈值的 3 倍）以内时记 `WARN`「最近没有请求」，超过 405 秒记 `FAIL`「过滤器停了，看 bin/diag.sh vllm」，和设计一致。
11. **注册和卸载的四个限制：**① `add` 在没有面板一的集群上停在步骤 6；② 两个集群不能共用一个 Prometheus；③ vllm 模式下 `remove` 会删掉过滤器正在写的日志；④ 卸最后一个面板二集群时 `remove` 会删 ClickHouse 插件并重启 Grafana（面板一跟着中断）。v3 修了第 ③ 点：每个进程留下序号最大、正在写的那个文件，只删更早的；留下的文件在去掉过滤器、重启 vLLM 以后手工删（10.2）。v3 也改了第 ① 点中「找不到面板一看板」那一项：它只影响看板顶部的跳转，步骤 6 改记 INFO，不再拦住 `add`，所以 test 这样没有面板一的集群也能用更新脚本升级；没有 Prometheus 的新集群仍要先像 test 那样起一个自己的 Prometheus。两点的实验室核对：① 修前，v2.1 在没有面板一的 test 上 `add`，停在步骤 6（「面板一·P看板 … 没找到」「面板一·D看板 … 没找到」两行 FAIL）；修后，v3 的 `add` 把这两行记 INFO，一次做完。③ 见 10.2 的走查记录：SSH 账号能删时只删旧文件，正在写的都留下；删不掉时一个也没删，输出仍记 OK。②④ 不修，vllm 模式的集群要避开 ④ 时仍按 10.2 的逐条做法卸。
12. **容器的日志驱动是 none 时，`diag.sh vllm` 关于标准输出的那一行不可信。**（不修）看不到标准输出时，在 `deploy.env` 里填 `NODE_VLLM_STDOUT_FILES`。
13. **采集器没在运行时，diag 报出的「解析失败」行数没有意义。**（不修）先按「容器」一行的提示启动采集器，再看。
14. **节点日志的保留时长不能手改。**（v3 修了）保留时长改成 `deploy.env` 的 `NODE_LOG_KEEP_HOURS`，留空时 12；生成 `segments.json` 时写进去，检查比对文件前换回包里的值，所以改它不再让「版本和文件」报 FAIL（9.5）。更新脚本把 v2.1 下手改过的 `line.keep_hours` 迁移进 `deploy.env`。实验室核对：修前，v2.1 下把 `keep_hours` 手改成 24 以后，check 的「版本和文件」报 FAIL；修后，升级前的 check 记 INFO「将迁移 keep_hours=24」，`run` 摘要写「已迁移：segments.json 的 keep_hours=24 → deploy.env 的 NODE_LOG_KEEP_HOURS」，升级后 check OK；回滚以后 `keep_hours` 回到 24，`deploy.env` 里没有这个键。

### 16.2 v3 新的已知问题

15. **首次候选那一步的值不显示。** 要先等 KV 的请求，这一步的 lookup、alloc、other 和 D 的提交没有归到请求上（3.6.3）。P 侧命中缓存池的请求 lookup 为空；D 侧 start_load_kv/submit 为空。`bin/diag.sh chain` 报出过滤器丢掉的空键记录数，可以看出这类记录有多少。
16. **用包里的 `segments.json` 时，多个请求共用的缓存池任务不归到任何请求上。** 补丁规定共用的工作不能全算给每个成员，所以这种任务的耗时不在看板上（3.6.1）。dsv4.1 的段定义不在此列，它按 C9 把整份时长计给每个成员（3.6.4）。`bin/diag.sh log <日志文件>` 报出一份日志里这种任务的条数；rc1 里为 0。
17. **9 个段为空。** 原因见 3.6.2：网关和 proxy 没有计时日志，日志里没有等保存完成和 P 侧等传输的计时，put 下三段只在补丁 04 的原生日志里有。
18. **没有换补丁 01、02 的节点，新段为空，排队时间是旧口径。** 原有 25 个段照常显示；排队包含等 KV 的时间，和换了补丁的节点混在同一张分布图里时没有区分。补丁由维护 vLLM 的人换，面板二的升级不管补丁。
19. **几种情况没有在硬件上验收。** 补丁只在小模型、同机两卡上验收过（rc1）。TP 大于 1 时缓存池记录只留 rank 0 的取法、一个请求有几个传输任务时取最长的一条、并发、跨节点 RoCE 和长期稳定性都没有日志可测。内网第一次升级以后，用 `bin/diag.sh vllm`、`bin/diag.sh log` 和 `check` 核对。
20. **用更新脚本升级、回滚都会删掉这个集群的旧数据。** `run`、`rollback` 先列出库 `vllm_pd` 里请求数据的行数，再删掉两张表和三个视图（过滤器的三张记录表保留），看板从空开始，只显示之后的请求；删掉的数据不进备份，不能恢复。这是 11-16 定的做法：现场的测试数据和日志流不拦升级。要留数据时，升级前自己用 ClickHouse 导出。

21. **装完、升级或回滚以后约 3 分钟内跑 `quality`，部署后核验报 FAIL。** `bin/panel2_cluster.sh quality` 的部署后核验（`bin/postdeploy_check.sh`）一段报 `FAIL 最近 2 分钟没有过滤器的自检行`，「节点 … 换到这一版 segments.json」一行的切换时间显示成 `1970-01-01 00:00:00`：切换时间取这一版的第一行自检，还没有时就显示这个值。3 分钟后重跑就是 OK。v3 实验室走查看到，v2.1 也是这样。`quality` 只报告，不拦升级、`check` 和 `run`；处理办法是等 3 分钟重跑。

22. **更新脚本的迁移预览把 v3 有意改的键也报成 WARN。** 从 v2.1 升级时，`check` 和 `run` 的「迁移预览」有 6 行 `WARN 升级后会变成包里的值：…`，键是 `config_id`、`roles.by_event_prefix`、`roles.ranked_roles`、`sides.decode.ttft`、`sides.prefill.background`、`sides.prefill.ttft`，都是 v3 本来就要改的；后三行是整棵段树的 JSON，每行几千个字符。原因是预览拿集群目录里的 `segments.json` 和新包的比，分不出哪些差别是现场手改的。这 6 行是正常的，除此之外的 WARN 才是手改（《内网升级总说明》v3 版第 2 步列出了这 6 行）。下一版改成和 v2.1 包里原样的文件比，只报现场改过的键。
23. **回滚以后 1–2 分钟内马上再 `run`，摘要里「节点文件不变：segments.json 是 pd-diag-v3-…」一行不对。** 这一行按 ClickHouse 里各过滤器进程最近的自检版本算；回滚刚下发 v2.1 的 `segments.json`，过滤器还没写出新版本的自检行，那里仍是 v3 的值，所以显示成「不变」。实际下发的结果是对的：`run` 照常下发 v3 的 `segments.json`，结尾的升级安全检查和之后的 `check` 按节点上的文件判。处理办法：不看这一行，以 `check` 里「过滤器版本」2 分钟后的结果为准；或者回滚以后等 2 分钟再 `run`。

24. **vllm 模式的集群升级以后约 10 分钟内跑 `quality`，部署后核验报「白名单以外的事件」。** 报的是 `pool_task` 和 `pd_transfer_summary`。升级不重启 vLLM，同一批 vLLM 进程在 v2.1 时期把这两种记录当作白名单以外的事件写进了 `filter_other`；更新脚本升级时保留这张表（和 `bin/clear_data.sh` 一样），而这一项只看最近 10 分钟、还在运行的进程写的行，所以升级前的那批行要过 10 分钟才移出窗口。10 分钟后重跑就是 OK（实验室第二轮走查实测）。mock 模式的集群升级时 mock 重启、换成新进程，不会出现。处理办法：vllm 模式的集群升级以后等 10 分钟再跑 `quality`；10 分钟后仍报，或者报的不是这两种事件，才按那一行的修法查。

这些问题都不影响原有段的数据正确性，影响的是新段的覆盖面、检查结果的可信度和卸载时的副作用，每条都有对应的人工处理办法或核对办法。

### 16.3 v3.1-extra 的已知问题

用 dsv4.1 的段定义时，第 15 条、第 17 条改为下面第 25 条和 3.6.4 所说；用包里的 `segments.json` 时，16.1、16.2 照旧。

25. **P 的 EngineCore 靠 vllm-ascend 补丁新加的 `pool_load` 映射记录。** TP 大于 1 时 `pool_task[load_submit]` 在 Worker 进程里，P 的 EngineCore 要靠 `pd_transfer_summary[link]`（`transfer_role` 为 `pool_load`）才能把首次候选那一步的 lookup、alloc、other 计给命中缓存池的请求。节点上的 vllm-ascend 没有这条记录时（补丁没装上，或 `load_async=false`），这三项在首次候选那一步不计入。它们不是 46 段里新增的目标段；P 的 submit 照常取 `pool_task`，D 侧不受影响。
26. **最近写的 proxy 行，可能要等下一行 proxy 行来了才写进 ClickHouse。** 实验室端到端测试里多次看到：采集器把行交给 `proxy_line` 的出口以后，这些行要等这个出口收到下一条才发出去；卡住的有时是启动后第一秒读到的几行，有时是最后写的一行。原因没有查明（可能和 Vector 0.61 的磁盘缓冲有关）。在线时 proxy 每个请求写一行，延迟只到下一个请求为止；没有新请求时，最后一两行暂时查不到。
27. **Mooncake 计时行从打开开关以后算起。** 每个来源的第一轮从文件末尾开始（docker logs 从当时开始），开关打开之前写的行不取。TP 大于 1 时其他 rank 的保存线程写的行配不上 rank 0 的记录，算在「没有认领的行」里，拉取程序 `/status` 的 `mooncake` 一行列出各项计数。glog 0.7 起前缀里的线程号不等于 `native_tid`（记录格式约定 v2 第 4 节），这时怎么配由 `deploy.env` 的 `MOONCAKE_TID_FALLBACK` 决定（13.2）：
    - 默认 `0`：只按线程号配，不兜底。线程号对不上的行算在「没有认领的行」里，put 下 3 段为空。TP 大于 1 时几个 rank 的行先后到达，兜底会在 rank 0 的行到达之前把别的 rank 的行配给 rank 0 的调用，所以默认不兜底。
    - 环境检测结果的 `glog=` 一项是 0.7 及以上时设为 `1`：一次调用所在的线程一行都没有时，同一台机器上时间、key 数对得上的行里，按 C10 正好剩一行才算配上，计在 `matched_without_tid`。**TP 大于 1 又遇上 glog 0.7 时，几个 rank 的保存线程同时写、key 数相同，几乎总是剩不止一行，put 下 3 段配不上。**
    - 现场的 Mooncake 大概率自带 glog 0.4.0（约定 v2 第 4 节），以环境检测结果为准。

    同一台机器上几个容器的线程号可能重复，要线程号、时间、key 数都对上才算，对不上的不计入。`logs:` 来源每轮执行一次 `docker logs --since`，日志很大时在节点上的开销没有测过。
28. **proxy 打开以后，vLLM 日志和面板二里的请求号是 proxy 生成的。** 客户端带来的号只记在 proxy 行的 `client_request_id`，单请求 JSON 的 `client_request_id` 一项读它。按客户端的号查 vLLM 日志的人要先在 proxy 行里查到对应的请求号。客户端收到的响应 `id` 也会变：客户端带了 `X-Request-Id` 时，原来响应 `id` 是 `chatcmpl-<客户端的号>`，打开开关后是 `chatcmpl-<proxy 生成的号>`；靠响应 `id` 对账的客户端会受影响。
29. **等 put 完成的记录格式按约定稿取。** 段定义读 `worker_summary[execute]` 的 `stages.wait_for_put.duration_ns`；vllm-ascend 补丁最终的字段名如果不同，只改 `profiles/dsv41/segments.json` 的那一条累加规则。
30. **D 图模式下 forward 的口径待核对（C8）。** test 集群第一批数据出来以前，forward 是 host 侧耗时，可能明显小于每步实际耗时。glm5.3 的段定义只用设备计时（C15，3.6.5），没有设备值的步留空，条数见过滤器自检行的 `acc_fallback`（留空次数）；dsv4.1 的段定义仍是 host 侧耗时。
31. **一个请求有几次尝试、各次的状态不同时，看板上的状态取到哪一次不固定。** 被 D 退回 P 重算的请求有几次尝试（3.6.5），看板按请求号合成一行时，状态（`status`）用的是 ClickHouse 的 `anyIf`，取其中任意一次的非空值，不一定是最后一次。这一条只读过代码（`scripts/generate.py` 的 `api_anchor`），没有实测；要确认某个请求最后是否成功，看「单请求事件」里各次的记录。
32. **P eager 下的设备事件没有在卡上测过。** 现场的设备事件探针只跑过图模式（aclgraph replay，3.6.5 引的 vllm-ascend 说明第 8 节）。glm5.3 的 P 是 eager，P 的 forward、sampling 的设备值要等第一批数据核对：看过滤器自检行 P 实例的留空次数，以及 P 的 forward、sampling 是否有值、量级是否合理。
33. **TPOT 下面几段加起来比 TPOT 小。** 设备口径下，MTP 草稿的前向（P 每步 1 次，D 每步最多 5 次）不算在 47 段的任何一段里：forward 只计目标模型，sampling 只计采样器；other 是调度器自己测出来的，不是从总时长里减出来的余数。所以 D 上「第二步起」各段之和比 TPOT 小，草稿数 k 越大差得越多，P 上差得少。这是按定义的结果，看板不为草稿另加指标。
34. **有留空的步时，D「第二步起」的每步平均偏大（C15）。** D 第二步起的每步平均，除数取自 forward 的步数，而 forward 只数有设备时间的步。留空的步占 forward 步数的比例为 f 时，schedule、alloc、other、detokenizer 这些和设备时间无关的段，每步平均会放大到 1/(1−f) 倍；forward、sampling 自己的每步平均不受影响。面板上「步数」一列明显偏小时，同一行的每步平均就是按这个倍数偏大。现场开着 MTP，一步可能出好几个 token，不能拿输出 token 数去核对步数。留空的比例看过滤器自检行的 `acc_fallback`（留空次数），操作说明 A 第 7 步把它作为每批的判据。以后的解法：每条累加规则本来就各自带步数（`scripts/generate.py` 视图里的 `b_<段>_steps`，第 283、296 行），可以让每段除以自己的步数；这一版不改，因为要改视图，默认段定义和 dsv4.1 的视图也会跟着变。
35. **留空比例的分子分母来自两侧，两侧的步数可能本身有偏差。** 操作说明 A 7.3 的留空比例是 1 − Worker 一侧有设备时间的 forward 步数 ÷ 调度器一侧的 alloc 步数。真实 vLLM 每一步两侧各写一条记录，按结构没有偏差：rc1 的真实日志逐请求核对，两侧的步数完全相同（P 2 个请求、D 3 个请求共 144 步，0 差）。实验室的替身有 ±0.9% 的假偏差：替身的引擎、Worker 两个进程各自循环回放同一份样本，互不同步（`tests/t33/fake/fake_vllm.py` 的 `emit_loop`），每个请求差 −2 到 +1 步，按实例合计是 −0.90% 到 +0.65%，只算已经结束的请求也一样。现场有没有偏差，以第 1 批带回的步数为准。判据因此要两个条件同时满足（比例超过 1%，而且留空次数增加了）。这个条件的代价是：真实留空很少、偏差又是正的时候，两者叠加可能误判失败；用第 1 批带回的两次步数和留空次数可以分辨出来。
36. **Mooncake 计时行的前缀有两种写法，两种都认。** `[BatchPutTiming]` 行由 Mooncake 经 glog 写出，前缀里的日期写法随 glog 的版本不同：glog 0.6 写年份，行首是 `I20261119 08:36:03.863473  1664 client_service.cpp:3348] [BatchPutTiming] …`（glm5.3 现场，`glog lib=libglog-afa88425.so.0.6.0`）；glog 0.4 不写年份，行首是 `I1119 08:36:03.863473 …`（Mooncake 的 npu wheel 自带的 glog，实验室用的就是它）。拉取程序（`scripts/native_put.py`）两种都解析；行里有年份时按行里的年份换算时刻，没有时按那次调用的年份。这一版以前只认不带年份的写法，现场的行一行也解析不了，P 后台 wait_for_save/put 下的 3 段会一直为空。出处：单元测试 `tests/t51/test_native_put.py` 的 glog 0.6 一组（两种前缀、跨年的调用、旧签名包装那一行）；端到端测试 glm53 一套的计时行写成带年份的形式，dsv41 一套保留不带年份的形式。
37. **节点自检认「只取设备时间」的段，靠的是段定义的写法（下一版改进）。** `scripts/node_selfcheck.py` 把取值的每一项都以 `.device_duration_ns` 结尾的累加规则（glm53 段定义里是 forward、sampling 两条）当作只取设备时间，断言它们在样本上为空（样本只有 host 时间）。以后有人给这两条加回 host 兜底（例如在列表里再写一项 `stages.forward.duration_ns`），它们就不再被认作只取设备时间，自检改为照真值比较，不会报出口径变了。这一版的两条都只有设备时间一项，没有这个问题。下一版的改进：自检按规则名固定检查这两条只取设备时间，不靠写法来认。出处：`scripts/node_selfcheck.py` 第 167–175 行。
