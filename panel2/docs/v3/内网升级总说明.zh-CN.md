# 包二 v3 升级说明书：面板二（v2.1 → v3）

这份说明书把内网两个集群的面板二从包二 v2.1 升到 v3。两个集群用同一套步骤：放文件、核对 sha256，对每个集群执行一次更新脚本的 `run`，再等几分钟看看板。内网这次升级只看这一份；包二 v2.1 的《内网升级总说明》留在仓库里作参考，不再照着执行。

### 先说明几个名词

- **更新脚本：** `<更新脚本>`，一次升级、回滚一个集群，用 `--cluster <集群名>` 选集群。它有三个子命令：`run`（升级）、`rollback`（回滚）、`check`（可选的核对，只读，结果不影响 `run`）。
- **数据流：** 节点上的日志经拉取程序、采集器写进 ClickHouse 的那条链路，以及过滤器版本、mock 进程这些和它有关的状态。`run` 和 `rollback` 不看数据流：现场的测试数据、断开的链路、停掉的 mock 都不会拦住它们。
- **这个集群的数据：** 这个集群自己的 ClickHouse 容器里，库 `vllm_pd` 的请求数据：两张表 `phase_line`（每个请求的汇总）、`diag_event`（请求级事件）和建在它们上面的三个视图。`run`、`rollback` 先列出它们的行数，再删掉，更新以后从空表开始。过滤器自己的三张记录表 `filter_file`（文件头）、`filter_selfcheck`（自检行）、`filter_other`（白名单以外的事件）保留不删，和 v2.1 的 `bin/clear_data.sh` 一样：vLLM 不重启时过滤器不会重写文件头，删了以后检查会一直报缺进程的文件。ClickHouse 容器本身、它的用户和设置不删。
- **config_id：** `segments.json` 里的版本标签，看板只读当前 `config_id` 的行。v2.1 是 `pd-diag-v2-2026-11-13`，v3 是 `pd-diag-v3-2026-11-16`。**版本串**是 `config_id@` 加上 `segments.json` 的 SHA-1 前 8 位。

### 要做的几步

**结论：** 两个集群的面板二都是 v2.1，都用 v3 的更新脚本升级，都有自动备份和回滚。一个一个做，先做 `<mock 集群>`，再做 `<vllm 集群>`。

| 步 | 做什么 | 用时 |
|---|---|---|
| 1 | 建目录、拷文件、列目录、核对 sha256（两个集群共用，只做一次） | 拷文件看传输方式；其余几秒 |
| 2 | 对每个集群执行 `run --cluster <集群名>`：预检、备份、迁移、**删掉这个集群的旧数据**、更新 | 每个集群约 40 秒 |
| 3 | 等几分钟，看每个集群的看板 | 几分钟 |
| 回滚 | 出问题时，把那个集群回滚到 v2.1（单独一节） | 每个集群约 20 秒 |
| 附录 A | 可选的核对：`check`、查新记录的 SQL、`quality` | 每条几秒 |

### 升级以后看板上会看到什么

**结论：** 升级以后看板从空开始，只显示升级以后的请求。有请求以后，D 侧等 KV 的时间第一次有了自己的段，P 侧后台保存的五个子段有了数，排队时间明显变短。下面的数取自 rc1 的回放：把同事验收日志 rc1 的副本送进过滤器、采集器和 ClickHouse 以后，看板读到的值（出处：v3/rc1 分支 318fc17）。rc1 有三个请求：经 proxy 的同一个请求发了两次，第一次缓存池里没有它的 KV（冷请求），第二次命中缓存池（热请求）；另有一个直接发给 D 的请求（直连请求）。

| 看板上 | 升级以后 | rc1 回放的值 |
|---|---|---|
| 全部面板 | 升级时这个集群的旧数据删掉了，看板从空开始；升级以后有请求进来才有数 | — |
| D 侧 start_load_kv/wait_for_transfer、「最慢请求」表的「D 等 KV」一列 | 有值：D 从 P 读取 KV 的时间 | 冷请求 155.901 ms，热请求 2.633 ms，直连请求为空 |
| P 侧 start_load_kv/submit | 命中缓存池的请求有值 | 热请求 0.069 ms，冷请求为空 |
| 「P 侧：后台 wait_for_save（不计入 P 合计）」 | 保存任务的总耗时和五个子段有值；总耗时比五段之和略大，差额是各段之间的间隙 | 冷请求 4.913 ms（build_key 0.035、lookup 0.253、prepare 0.204、sync 0.026、put 4.166 ms）；热请求 0.323 ms（build_key 0.021、lookup 0.198 ms，其余三段为空） |
| queue_time（排队） | 只算到调度器第一次挑中请求，等 KV 的时间显示在 D 的 wait_for_transfer | P 侧 0.133、0.121 ms；D 侧 0.107、0.138、0.099 ms |
| 要先等 KV 的请求的 lookup、alloc、other | P 侧命中缓存池的请求 lookup 为空；D 的「第一步」是 KV 到了以后第一次执行的那一步 | — |
| 9 个空段（proxy 三段、P 的等 put 完成和 start_load_kv/wait_for_transfer、put 下三段、D 的 start_load_kv/submit） | 仍为空 | 所有请求都为空 |

`<mock 集群>` 的 mock 生成同样格式的日志，上面几处同样有值，值是 mock 生成的。

### 对同机其他服务的影响

**结论：** 升级和回滚只动这个集群自己的面板二：它的集群目录、ClickHouse 里的表和视图、采集器、拉取程序和看板。Grafana、Prometheus、ClickHouse 容器、ClickHouse 插件、面板一和另一个集群都不受影响，Grafana 不重启，vLLM 不重启。

| 机器 | 服务 | `run`、`rollback` 时 |
|---|---|---|
| 节点 | vLLM | 不重启：v3 没有改过滤器程序 `pd_diag_logfilter.py` 和日志配置 `pd_diag_logging.json`，只换 `segments.json`，过滤器自己重读 |
| 节点 | mock（`<mock 集群>`） | 重启一次，那几秒没有新日志 |
| 节点 | 面板一的 exporter | 不碰 |
| 监控机 | Grafana（面板一、面板二共用） | 不重启。只重新导入这个集群的面板二看板，打开着的页面要刷新；面板一的看板、数据源不动 |
| 监控机 | Prometheus | 不重启。面板二那一段不变时不写文件、不重新加载；有变化时重新加载一次，秒级，面板一的数据不断。`<vllm 集群>` 用自己的 Prometheus，面板一的 Prometheus 完全不碰 |
| 监控机 | 这个集群的 ClickHouse 容器 | 不重启。库 `vllm_pd` 的请求数据（两张表、三个视图）先删掉，再按 v3（回滚时按 v2.1）建成空表；过滤器的三张记录表、用户、只读用户的设置不变 |
| 监控机 | 另一个集群的 ClickHouse 容器 | 不碰 |
| 监控机 | 采集器 `vllm-pd-vector-<集群名>` | 重建一次：期间没有新数据，起来以后接着读 |
| 监控机 | 拉取程序 | 重启一次，几秒没有新数据 |
| 监控机 | 磁盘 | 更新脚本把新包和离线包解到 `<用户目录>/vllm-pd-panel2-update-v3/pack/`，约 390 MB（上一次走查实测 389 MB），另有迁移预览留下的 `preview/`（只有一份算出来的 `segments.json`，`du` 显示约 24K），升级后都不自动删；备份写到执行账号家目录的 `vllm-pd-update-backup/<时间>/`。删掉的数据不进备份 |

**机器：** 监控机。

## 第 2 步：对每个集群执行 `run`

**结论：** `run` 只查保护机器和别的服务的几项（两个包和 sha256、磁盘空间、集群目录、ClickHouse 容器、Grafana 账号、注册表），不看数据流；然后备份，迁移手改过的保留时长，**删掉这个集群在 ClickHouse 里的请求数据（两张表、三个视图，先列出行数；过滤器自己的三张记录表保留）**，再用新包更新。旧数据删掉以后不能恢复，备份里也没有；回滚以后看板同样从空开始。

**机器：** 监控机。

**命令：** 两个集群各执行一次，一个做完、看到「成功」再做下一个。先做 `<mock 集群>`：

```bash
cd <用户目录>/vllm-pd-update-v3 && python3 <更新脚本> run --cluster <mock 集群>
```

再做 `<vllm 集群>`：

```bash
cd <用户目录>/vllm-pd-update-v3 && python3 <更新脚本> run --cluster <vllm 集群>
```
