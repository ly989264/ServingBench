# 面板二诊断工具 `pd_panel2_diag.py`

对应讨论稿第 11 条（原 T65）。工具回答三件事：数据采齐了没有（采集）；每个请求缺了哪几种记录（每个请求）；每一段的 p50、p90、p99、均值、均值占比、「有值 / 请求」，看板显示的和工具自己从库里算的是否一致（各段和看板）。

## 怎么跑

在 glm53-test 的监控机上，用装面板的账号执行。工具是一个文件，放在哪里都可以，不用装：

```bash
. ~/vllm-pd-test-glm53/vars.sh && python3 -I -B pd_panel2_diag.py "$D" --from "2026-11-21 15:00" --to "2026-11-21 16:00"
```

- `$D` 是 test-glm53 的面板二目录（里面有 `deploy.env` 和 `segments.json`），换成别的集群的面板二目录也能用。
- 时间按北京时间写；不写 `--from`、`--to`，就是最近 1 小时。时间段里的请求不能超过 15 万个，超过时第三节不做，提示缩短时间段。
- 屏幕上二十行左右，最后一行是 `RESULT: OK` 或 `RESULT: FAIL（N 项）`，后面跟着 WARN 的项数。要带回来的就是这二十行。
- 完整明细写进 `~/vllm-pd-diag-reports/<集群>/<时间>.txt`：每个实例、每类进程的行数，每个缺记录的请求号，每一段工具算的值和看板的值。屏幕上有 WARN 或 FAIL、要细看时，再把这个文件带回来。

## 屏幕输出怎么读

| 节 | 行 | 意思 |
|---|---|---|
| 范围 | 第一行 | 集群、时间段、模型、过滤器版本、请求数（P、D 各有多少已结束） |
| 一、采集 | P、D 各一行 | 时间段里各类进程的记录行数和最后一条的时间 |
| | 过滤器自检 | 各进程报的版本是否和集群目录里的 `segments.json` 相同、粒度、出错计数 |
| | proxy | 时间段里 proxy 行的条数和最后一条的时间；proxy 自检的丢弃、出错 |
| | 拉取目录 | 拉取目录里各台的最新文件和库里的记录对不对得上（卡在拉取还是卡在采集器） |
| 二、每个请求 | P、D 各一行 | 已结束的请求是否都有 `core_summary[request]`；缺的，看板按 3 级算（第 8 条） |
| | 粒度 | 按 `core_summary[request]` 的 `diag_level`，各级各有多少请求 |
| | proxy 行 | 缺 proxy 行的请求分两种：请求在库里最后一条 proxy 行之前就结束了，算缺；结束得更晚的，算可能还没到库（proxy 在请求结束以后才写这一行，再加一轮拉取，第 5 条） |
| | put 下 3 段 | 3 级、put 有值，但 put 下的 3 段（来自 Mooncake 自己的文件）都是空的请求 |
| 三、各段和看板 | P、D 各一行 | 经 Grafana 取出看板「P/D 侧分段时延分布」原样的查询，把时间、模型、实例（全部）、层级（3）换成同样的值，在库里执行；再按 `segments.json` 的段定义，自己从库里的原始行算一遍，逐行比较。对得上是 OK；对不上是 FAIL，列出前两行和差在哪一列，问题在看板的算法或显示，不在数据 |

OK 表示这一项没有问题；WARN 表示数据缺了或者可能还没到，列出个数和最多 3 个请求号；FAIL 表示看板和库里的数对不上，或者工具没能做完；INFO 只是数字，不判断。

## 对现场零影响

- ClickHouse：只发 `SELECT`（工具自己先检查，每条查询都以 SELECT 或 WITH 开头），经本机的 HTTP 端口，用面板的只读账号 `vllm_reader`，每条都带 `readonly=2`、`max_execution_time=60`、`max_memory_usage=1000000000`（1 GB；监控机上的 ClickHouse 同时还在给看板出数）。
- Grafana：只用 `GET` 取看板。
- 不 SSH，不进容器，不发信号，不重启、不改任何服务。用 `python3 -I -B` 运行，只用标准库，不写 `.pyc`。
- 读：集群目录里的 `deploy.env`、`segments.json`；注册表 `~/.vllm-pd-clusters.json`（`deploy.env` 留空的端口、看板 UID 从这里取）；拉取目录里文件的修改时间（不读内容，每台最多看 2 万个文件）。
- 写：只写自己的报告文件。

## 已知

1. **只有 D 记录的请求：** v3.3-extra 的看板不算只有 D 记录的请求，工具遇到时只报一行，说明原因和个数。v3.4-extra 的看板算进这些请求，第三节直接对得上，不再报这一行。
2. **P 合计：** 工具看看板里有没有 else 行，认出是 v3.3-extra 还是 v3.4-extra。v3.3-extra 的 P 合计只算 API server 自己的（决定 C5）；v3.4-extra 的 P 合计加上 proxy，P 侧 proxy 一行也有均值占比。
3. **v3.4-extra 的看板：** 分组标题行（后台任务、第一步、第二步起 · 每步）跳过不比。else 行逐行比：每个请求的 else = 本侧合计 − 算占比的一级段（空按 0），小于 0 记 0，没有 `core_summary[request]` 的请求为空；均值占比按「段的耗时之和（空按 0）÷ 同一批请求的合计之和」算，每一行都在同一批请求上，第二步起各行也一样。「有值 / 请求」列在看板上隐藏时，看板的查询仍算这一列，工具照样比。「有值 / 请求」的写法（`k / n，未采 m`、`未采 m`）工具也认。
4. **抽样：** 时间段里超过 15 万个请求时，看板会抽样，工具不做第三节。
