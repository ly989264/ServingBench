# 上线后首批数据核对：p2d 埋点的四条判据

给面板那边写成 ClickHouse 查询用。这四条判据对应的，是重放前的结构判据（F01–F31）覆盖不到的风险 R1–R5（`README.zh-CN.md` 第 6 节）。查出结果不必停服，把命中的记录带回来看。

## 0. 共同约定

- 只看 `[PD_DIAG]` 行里 `event = "pd_transfer_summary"` 的记录。下文的 `scope`、`transfer_role`、`request_id` 等都是这条 JSON 的顶层字段；`links` 是数组，每项有 `kind`、`request_id`、`engine_id`。
- 四种记录：

| 记录 | 判定 | 写在哪里 |
|---|---|---|
| consumer link | `scope = "link"` 且 `transfer_role = "consumer"` | D 的 EngineCore |
| producer offer | `scope = "link"` 且 `transfer_role = "producer"` | P 的 EngineCore |
| task | `scope = "task"` | D 的 Worker，每个读任务一条，每个 TP rank 各一条 |
| request_generation | `scope = "request_generation"` | D 的 Worker，每个请求每个 TP rank 一条 |

- **请求号。** vLLM v0.30 给每个到达的请求号加了 8 位随机后缀，所以 `request_id` 在整个集群里唯一，按它关联即可，不需要再带 host、实例或 dp_rank。
  - D 上 consumer link 的 `links` 数组只有一项（`kind = "producer"`），这一项的 `request_id` 就是这个请求在 P 上的请求号。
  - P 上 producer offer 的 `request_id`，也是 P 的请求号。
- **TP rank。** task 和 request_generation 只取 `tp_rank = 0`，和面板的取法（C3）相同。glm5.3 的 D 是 TP1，本来就只有 rank 0。
- **时间窗。** 判据 3、4 是「有 A 却没有 B」，A 写出之后 B 可能还没到，所以只看至少 10 分钟以前入库的 A。
  - 按入库时间或面板表里的墙钟时间列来算。
  - 不要用 `timestamp_ns`：它是各进程的单调时钟，跨机器不能比，也不能和墙钟比。
- **前提。** 这四条要用到 consumer link、producer offer、task（`status`、`transfer_status`）和 request_generation 四种记录。面板现在的过滤器只保留段用到的事件，如果这几种记录没有进 ClickHouse，要先给它们放行，或者直接在原始日志上查。

## 1. 同一请求的 consumer link 多于一条（R1：同一请求读了不止一轮）

- **用的记录：** consumer link。
- **字段：** `request_id`、`execution_id`。
- **判定：** 按 `request_id` 分组，`count() > 1`（等价于 `uniqExact(execution_id) > 1`）的请求，都算命中。
- **正常情况下：** 0 个。V1 对每个请求只发起一轮读取：`update_state_after_alloc` 把 `do_remote_prefill` 置为 False。进入调度前就被拒绝的请求，也只补一次空读取。
- **带回：** 命中请求的全部 consumer link、task 和 request_generation。

## 2. task 记为成功，传输却失败（R2：READ 失败后没有抛异常）

- **用的记录：** task，`tp_rank = 0`。
- **字段：** `status`、`transfer_status`，以及 `native_calls[].status`、`native_calls[].native_return`。
- **判定：** `status = "succeeded"` 且 `transfer_status = "failed"`，命中。也可以放宽为：`status = "succeeded"`，且 `native_calls` 里有一项的 `status` 为 `"failed"` 或 `"cancelled"`。
- **正常情况下：** 0 条。V1 在 READ 返回值小于 0 时抛异常，task 记 `failed`。
- **带回：** 命中的 task 记录，以及同一 `request_generation` 下的全部 task 和 request_generation。

## 3. 有 consumer link，却没有 request_generation（R1、R3、R5）

- **用的记录：** consumer link（至少 10 分钟以前入库）、request_generation（`tp_rank = 0`）。
- **字段：** 两者的 `request_id`。
- **判定：** 对每条 consumer link，找不到 `request_id` 相同的 request_generation，命中。
- **已知的例外：** 以下几种命中是预期的，不算问题：
  - `do_virtual` 请求（D 请求的 `kv_transfer_params` 里带 `do_virtual: true`）只写 link。只有现场的 proxy 或客户端自己加这个字段时才会出现；记录里没有标记它的字段，要靠 proxy 那边确认。
  - 实例在读取完成之前退出或重启，这些请求也只有 link。
- **正常情况下：** 除上面的例外，为 0。
- **带回：** 命中请求的 consumer link，以及同一 `request_id` 的 task（如果有）。
  - 有 task、没有 request_generation：对应 R5。
  - task 也没有：对应 R1 的「不进入读取」或 R3 的「不读就标为完成」。

## 4. P 的请求在 D 上有 link，P 侧却没有 offer（R4）

- **用的记录：** D 上的 consumer link（至少 10 分钟以前入库），P 上的 producer offer。
- **字段：** consumer link 的 `links[].request_id`（取 `links[].kind = "producer"` 那一项）；producer offer 的 `request_id`。
- **判定：** 对每条 consumer link，取它 `kind = "producer"` 那一项的 `request_id`，记作 P 请求号；P 上找不到 `request_id` 等于它的 producer offer，就算命中。
- **正常情况下：** 0。P 只要把 kv_transfer_params 交给 D，就会在 `request_finished` 里先写 offer。前提是 P 的日志也进了同一个库。
- **影响：** offer 不进任何段，C2 也不用它，所以命中只说明 P、D 请求号的对照不完整，不影响面板上的数值。
- **带回：** 命中的 consumer link，以及 P 上同一时段的 producer offer 条数。

## 5. 一个查询草稿（字段名以面板表为准）

假设原始记录放在表 `pd_raw` 里：`line` 列存 JSON，`ingest_time` 列存入库时间。判据 1、2 可以这样写：

```sql
-- 判据 1
SELECT JSONExtractString(line, 'request_id') AS rid, count() AS links, groupArray(JSONExtractString(line, 'execution_id')) AS xs
FROM pd_raw
WHERE JSONExtractString(line, 'event') = 'pd_transfer_summary'
  AND JSONExtractString(line, 'scope') = 'link' AND JSONExtractString(line, 'transfer_role') = 'consumer'
GROUP BY rid HAVING links > 1;

-- 判据 2
SELECT line FROM pd_raw
WHERE JSONExtractString(line, 'event') = 'pd_transfer_summary' AND JSONExtractString(line, 'scope') = 'task'
  AND JSONExtractInt(line, 'tp_rank') = 0
  AND JSONExtractString(line, 'status') = 'succeeded' AND JSONExtractString(line, 'transfer_status') = 'failed';
```

判据 3、4 是两组记录做 left anti join：
- 判据 3：consumer link 的 `request_id` 不在 request_generation 的 `request_id` 集合里；
- 判据 4：consumer link 的 `JSONExtractString(JSONExtractArrayRaw(line, 'links')[1], 'request_id')` 不在 producer offer 的 `request_id` 集合里。

两条都加 `ingest_time < now() - INTERVAL 10 MINUTE`。
