# 反向重放工具：把现场复制版里新增的语句搬进 01 版

**适用情况。** 现场的本地补丁把某个函数换成「原版 v0.30.0 整份复制、再加几条语句」的版本。现在要处理的是 P 上 `patch_prefill_length_validation.py` 里的 `AsyncLLM.add_request`。01 把这个函数的整个函数体包进了 `with _api_submission(...)`，每一行都多了一层缩进，所以没法把 01 的改动按文本重放进现场的复制版。这个工具反过来做：

1. 找出复制版相对原版新增的语句；
2. 把它们插进移植版的同一个函数里，位置是相同的锚点语句之后；
3. 把合并后的函数写回现场那个文件，替换掉复制版。

**运行环境。** 只用标准库，Python 3.10 以上，在现场的 Python 3.11 上测过。不导入、也不执行三个输入文件里的任何代码。

```bash
python3 replay_field_insertions.py --field <现场补丁文件> --field-func add_request \
  --original <原版 v0.30.0 的 vllm/v1/engine/async_llm.py> --port <移植版的 vllm/v1/engine/async_llm.py> \
  --qualname AsyncLLM.add_request --write <输出文件> --report <报告.json>
```

不带 `--write` 时只做核对、出报告，可以给 f-3 用。报告里只有数字和哈希，不含源码：每一段新增在哪一层、在第几条语句之后，锚点的哈希，锚点在原版和移植版里各命中几次，新增几条语句及其哈希，三个文件的 sha256。

**退出码。** 0 表示四项核对都通过（带 `--write` 时已写出）；2 表示拒绝，什么都没写，报告里写明是哪一项没过；3 表示输入有误。

## 四项核对

| 项 | 内容 |
|---|---|
| C1 | 每个锚点在原版里正好命中一次，在移植版里也正好命中一次 |
| C2 | 复制版就是原版加上这几段新增：函数签名相同，原有的语句一条没删、没改。比较按语句做，任意层的嵌套块都会对齐 |
| C3 | 合并后的文件能编译；合并后的函数用到的每个名字都能解析。现场模块里没有的名字，从移植版模块导入，函数体开头加一行局部 import |
| C4 | 合并后的函数等于「移植版的函数 + 现场这几段新增」，每段都紧挨在它的锚点之后，此外只多那一行 import |

任何一项不过就拒绝。拒绝时由 vLLM 补丁里 `owner` 的默认值保证服务正常，只是 P 的 add_request 段为空。

## 测试（`test/`）

**阶段一**（`run_tool_cases.sh`，Python 3.11.2，`mdiag-debian-12-slim`）：`gen_variants.py` 用原版 `add_request` 生成 10 种模拟的现场改动，逐个跑工具。结果在 `test/results/`，10 种全部符合预期。

| 用例 | 现场改动 | 预期 | 结果 |
|---|---|---|---|
| T1 | 顶层插入一段长度校验（3 条语句） | 合并 | 合并，4 项通过 |
| T2 | 嵌套两层的 `else` 分支里插入 | 合并 | 合并 |
| T3 | docstring 之后、第一条语句之前插入 | 合并 | 合并 |
| T10 | T1 和 T2 同时做 | 合并 | 合并 |
| T4 | 改了一条原有语句 | 拒绝 | C2 拒绝 |
| T5 | 删了一条原有语句 | 拒绝 | C2 拒绝 |
| T6 | 插在一条被 01 改过的语句后面（`_add_request(...)` 调用） | 拒绝 | C1 拒绝（在移植版里命中 0 次） |
| T7 | 插在 `return queue` 后面，这条语句出现了两次 | 拒绝 | C1 拒绝（命中 2 次） |
| T8 | 改了函数签名 | 拒绝 | C2 拒绝 |
| T9 | 新增语句里有跨行字符串 | 拒绝 | C3 拒绝 |

**阶段二**（`run_phase2.sh`，vLLM 测试镜像）：把 T1、T2、T3、T10 合并出的文件当作现场补丁导入，导入时会把函数赋给 `AsyncLLM.add_request`，然后跑 8 个 HTTP 场景。结果（`test/results/phase2_runtime.txt`）：

- 写出的记录与不替换时逐条相同，0 处差别；
- 现场新增的语句确实执行了：每个请求一次，T10 两段共 14 次。
