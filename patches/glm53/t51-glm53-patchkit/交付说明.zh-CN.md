## 验证

**实验室走查**（`guides/lab/walk_A.sh`，`python:3.11.10-slim`，`docker run --rm`）：在干净的 vLLM v0.30.0、vllm-ascend `d4ad49796` 上，用这个 tar，按操作说明 A 原文执行第 1、3、4、9 步，以及第 7 步里能在容器里做的几条。clean（公开的 `mooncake_connector.py`）、site（模拟的现场修改）两种都通过：

- 备份拷到「宿主机」「监控机」再送回，核对 `OK`、`23`、`10`；变量兜底；p2d 重放 clean 是替换件 `f953b27c`、site 是 `ef9e4e43`，`p2d_extra` 和原版相同；25 + 11 + 1 个文件在 Python 3.11.10 上都能编译。
- 替身 `vllm serve` 进程：命令行重启前后相同、改了端口能比出来；日志配置的核对能认出没设的进程。
- 磁盘命令算出的每天增长和写进去的字节数相符，`[PD_DIAG]` 的计数能报出来；`/tmp` 是 tmpfs 时备份放到 `/root`。
- 回滚以后新模块的 `.pyc` 删到 0 个，两个包的 3851 个普通文件和公开源码逐个相同（不计 `__pycache__`）。
- 第 8 步核对启动日志 `PD_DIAG_STARTUP` 的预期行按 vllm-ascend 实测（t51-glm53-ascend `9dad4b6` 说明第 12.5 节）：P 的调度器 `BalanceScheduler`、D 的 `AsyncRecomputeScheduler`，runner `vllm_ascend.worker.model_runner_v1.NPUModelRunner`，`device_timing` 只在 `tp_rank=0` 上是 `on`（P 另 15 行 `off` 属正常）。实验室没有 vLLM 进程，这一条没有走。
- 检测脚本（最终版）：打补丁前 `verdict vllm=unpatched ascend=unpatched(site_local=0) p2d=unpatched mooncake=-`；打完 `verdict vllm=ok ascend=ok(site_local=0) p2d=ok mooncake=-`，`vllm=` 行 `state=v0.30.0+port`、`port=25/25`，`strict` 行 `vllm=29/29(port:25)`；回滚后回到 `unpatched`。

## 已知问题

1. **`window_min` 只写了上限。** 操作说明 A 第 7.3 节只写了「明显大于 35 就重抄重跑」，没有下限。第二次查询跑得太早时，窗口很短、步数很少，比例会很噪，输出里看不出是数据太少：第二次查询的 window_min 明显小于 20 时数据太少，等满 25 分钟左右再跑。合成用例的 `window_min` 是 14，这条规则没有被用例覆盖。
2. **面板包新增 test-glm53 说明 10.5 的自检计数查询，用的还是 `GROUP BY node, instance, pid`。** 面板包已经交付、冻结，下一版再改。补丁包操作说明 A 第 7.3 节里的同一条查询已经改成 `GROUP BY instance, pid`，以补丁包这一份为准。只在一个 pid 带两个 node 标签时，两份的结果才会不同。
