## 0. 先读

### 0.1 术语

- **监控机：** glm53-1 的 Grafana 和 Prometheus 所在的机器。除附录 A 以外，全部命令都在监控机上执行，用装 glm53-1 时用的账号。
- **集群：** 一组一起提供服务的 P、D 机器。各套集群的机器互不相同。
  - glm53-0、glm53-2 的布局可能和 glm53-1 相同，也可能不同，按现场填。
  - dsv4.1-flash 的每一套是 4 台 P 机器、2 台 D 机器：每台 P 机器 2 个实例，端口 7100、7101；每台 D 机器 8 个实例，端口 7100–7107。
- **集群名（内部名）和显示名：** 部署包的集群名只能用小写字母、数字和 `-`，Grafana 的 UID 也不能带点。所以 dsv4.1-flash 的 5 套在部署包里叫 `dsv41-flash-1` 到 `dsv41-flash-5`，容器、目录、注册表、看板 UID 都用这个名字。Grafana 页面上的文件夹和看板标题显示 `dsv4.1-flash-1` 到 `dsv4.1-flash-5`。glm53-0、glm53-2 的内部名和显示名相同。
- **实例、API server：** 一个 vLLM 实例是一组共同推理的 vLLM 进程，对外有一个 HTTP 端口，叫 API server。面板一按 API server 的顺序给实例编号：P 侧第 n 个（从 0 数）是 `P<n>`，D 侧是 `D<n>`。
- **DP rank：** 实例在数据并行（DP）组里的序号，即启动参数 `--data-parallel-rank` 的值。vLLM 把它写在 `/metrics` 每条指标的 `engine` 标签里。面板一要求 `P<n>`、`D<n>` 的 `engine` 标签正好是 n，所以清单要按 DP rank 从小到大写：
  - **机器的顺序：** 同一侧的机器，按这台机器上最小的 DP rank 从小到大排。用 vllm-ascend 的 `launch_online_dp.py` 启动时，最小的 DP rank 就是这台机器的 `--dp-rank-start`。例如 dsv4.1-flash 的 P 侧 8 个实例是一个 DP 组，4 台机器的 `--dp-rank-start` 依次是 0、2、4、6。
  - **端口的顺序：** 一台机器上的端口从小到大排。`launch_online_dp.py` 在一台机器上给第 i 个实例分配端口 `--vllm-start-port` + i、DP rank `--dp-rank-start` + i，所以端口越小 DP rank 越小。
  - 第 7 步从每个 API server 读出 `engine` 标签，逐个核对。
- **TP：** 一个实例的张量并行数，即启动参数 `--tensor-parallel-size`。不打补丁时 TP 不影响抓取目标，按启动参数如实填即可。
- **抓取目标：** Prometheus 每 15 秒读一次 `/metrics` 的地址。一套集群的抓取目标是：每个 API server，每台机器的 npu-exporter 和 node_exporter，以及 Mooncake master。
- **清单（`inventory.json`）：** 一套集群的机器、端口和抓取设置。面板一的部署包按清单生成 Prometheus 的配置文件 `prometheus.yml`。
- **清单文件（`clusters.txt`）：** 本目录里的文本文件，7 套集群的机器写在一起。每次只填这一次要加的那一套；`make_inventories.py` 每次只把指定的那一套转成清单。
- **部署包：** 包一 v1.0 的面板一部分，目录 `<用户目录>/vllm-pd-panel1-update-2/pack/vllm-pd-grafana-panel1`，从 `vllm-pd-grafana-panel1.tar.gz`（sha256 `60ce7f30…`）解出。glm53-1 现在的面板一就是用它装的。
- **注册表：** 监控机上执行账号家目录里的 `~/.vllm-pd-clusters.json`，记着每个已装集群的容器、端口、目录、看板、机器和模型文件夹。部署包每次加集群前都查它，名字、端口或机器和别的集群重复就停下。
- **模型文件夹（`MODEL_GROUP`）：** 部署包把看板放进的 Grafana 文件夹的标题，加集群时由 `--model-group` 给出。部署包只在顶层文件夹里找它，找不到就在顶层新建。本说明书让每套集群的模型文件夹等于它的子文件夹名（例如 `glm53-0`、`dsv4.1-flash-1`），再由整理看板命令把看板挪进上一层文件夹下面的子文件夹。
- **整理看板命令（`arrange_boards.py`）：** 本目录里的脚本，按对照表 `boards_layout.txt` 把每个集群的看板放进「上一层文件夹 / 子文件夹」。它会改 dsv 两张看板的标题（把集群名换成显示名），并删掉部署包在顶层建的空文件夹。只删空的文件夹，按 UID 操作，可以重复执行。子命令的说明见《动现有看板操作单》0.1。

### 0.2 装完一套以后的样子

以 `dsv41-flash-1` 为例，每套集群有自己的一组：

| 项 | 值 |

| 看板 | 「vLLM 服务侧监控面板 - Prefill实例（dsv4.1-flash-1）」「vLLM 服务侧监控面板 - Decode实例（dsv4.1-flash-1）」，在 `dsv4.1-flash/dsv4.1-flash-1` 里 |

### 0.3 对监控机上其他服务的影响

- 加一套只新建这一套自己的容器、数据卷、数据源和两张看板，往注册表里加一条；第一次加 dsv 集群时，Grafana 里多一个上一层文件夹 `dsv4.1-flash`。
- 不重启 Grafana，不改 glm53-1 的 `prometheus.yml`、Prometheus 容器和看板，不碰面板二、test 和已经加过的集群。第 9 步和第 13 步各记一次它们的状态，比较以后确认这一点。
- 监控机上每加一套多一个 Prometheus 进程，占用内存和 Docker 数据目录所在的盘，估算见附录 D。

### 0.4 前提条件

开始以前，下面几条要由现场保证。本说明书不写怎么做到，只在第 7 步核对。

1. 《动现有看板操作单》已经做完（第 4 步核对）。
2. 每台新机器上都装好了 npu-exporter 和 node_exporter，端口和 glm53-1 相同。端口值第 4 步会打印出来。
3. 这一套的 vLLM 已经在运行，每个实例有自己的 API server，没有跨两台机器的实例。
4. 这一套有一个 Mooncake master，知道它指标端口的 IP 和端口（附录 A 的 A4）。
5. 监控机能访问这一套每台机器的 API server 端口、npu-exporter 端口、node_exporter 端口，以及 master 的指标端口。
6. 这一套的机器不属于 glm53-1、test 或其他已登记的集群。
7. 这一套不打 vllm-ascend 的指标补丁。

## 2. 每套要你填的

每加一套，只在 `clusters.txt` 里填这一套的那几行：从 `集群 <集群名> …` 一行开始，到下一个 `集群` 行之前。别的几套的 `<…>` 可以留着，已经加过的几套保持原样。填完以后，这一套的行里不能再有 `<` 或 `>`。

| 填什么 | 在哪一行 | 是什么 | 怎么查 |
|---|---|---|---|
| master 的地址 | 集群行的 `master=<master 的 IP>:<端口>` | 这一套 Mooncake master 指标端口的 `IP:端口` | 附录 A 的 A4 |
| 机器 IP | 每个 `P <…>`、`D <…>` 行的第二项 | 机器的 IP，不带端口 | 现场的机器表 |
| 机器的顺序 | 行的先后 | 同一侧的机器按最小的 DP rank 从小到大（`P0` 所在的机器写在最前面）。用 `launch_online_dp.py` 启动时，就是按 `--dp-rank-start` 从小到大 | 附录 A 的 A1 |
| 端口 | `端口=` | 这台机器上每个 API server 的端口，从小到大。dsv 的模板已经预填 `端口=7100,7101`（P）、`端口=7100-7107`（D）。glm53-0、glm53-2 的模板不写端口，表示用 glm53-1 的端口（第 4 步打印的值） | 附录 A 的 A1；不同就改 |
| TP | `TP=` | 这台机器上每个实例的 TP。dsv 的模板里是 `TP=<P 实例的 TP>`、`TP=<D 实例的 TP>`，要填数字。glm53-0、glm53-2 不写，表示用 glm53-1 的 TP | 附录 A 的 A1 |
| 机器台数 | 机器行的行数 | dsv 每套 4 个 P 行、2 个 D 行。glm53-0、glm53-2 的模板按 glm53-1 写了 8 个 P 行、4 个 D 行，台数不同就增删行 | 现场的机器表 |
| 实例数 | `实例数=` | 只在 glm 机器上的实例数和 glm53-1 不同时写，例如 `端口=9000 实例数=8` 表示从 9000 起连续 8 个端口 | 附录 A 的 A1 |

P 10.1.1.3
P 10.1.1.4
P 10.1.1.5
P 10.1.1.6
P 10.1.1.7
P 10.1.1.8
D 10.1.2.1
D 10.1.2.2
D 10.1.2.3
D 10.1.2.4
```

按第 4 步实验室的默认值，这一套是 P 8 个实例、D 64 个实例。如果 glm53-0 的 D 机器每台只有 8 个实例，就把 4 个 D 行都写成 `D 10.1.2.1 端口=9000 实例数=8` 这样。

**示例二：dsv41-flash-1。** 端口已预填，填 IP、master 和 TP（下面的 TP 是示例，按附录 A 查到的填）：

```

P 10.1.3.1 端口=7100,7101 TP=4
P 10.1.3.2 端口=7100,7101 TP=4
P 10.1.3.3 端口=7100,7101 TP=4

## 附录 A：在 P、D 机器上查实例数、端口、DP rank 和 TP

A1 到 A3 在每台 P、D 机器上执行，A4 在监控机上执行。四条命令都只读，不影响 vLLM。

**A1：从启动参数列出这台机器上的 API server。** 只列 `vllm serve`（或 `python -m vllm.entrypoints.openai.api_server`）进程。`launch_online_dp.py` 这类启动脚本的进程（带 `--dp-rank-start`、`--dp-size-local` 等参数）和它调用的 shell 脚本不算 API server，不列。

```bash
ps -eo args | python3 -c '
import os, sys
def opt(a, *names):
    for i, x in enumerate(a):
        for n in names:
            if x == n and i + 1 < len(a):
                return a[i + 1]
            if x.startswith(n + "="):
                return x.split("=", 1)[1]
    return "-"
def api_server(a):
    if not a or os.path.basename(a[0]) in ("bash", "sh", "dash", "zsh"):
        return False
    for i in range(len(a) - 1):
        if os.path.basename(a[i]) == "vllm" and a[i + 1] == "serve":
            return True
        if a[i] == "-m" and a[i + 1] == "vllm.entrypoints.openai.api_server":
            return True
    return False
rows = [a for a in (line.split() for line in sys.stdin) if api_server(a)]
for a in sorted(rows, key=lambda a: int(opt(a, "--port")) if opt(a, "--port").isdigit() else 0):
    print("端口 %-6s DP rank %-4s TP %-4s DP 总数 %s" % (opt(a, "--port"), opt(a, "--data-parallel-rank", "-dpn"),
          opt(a, "--tensor-parallel-size", "-tp"), opt(a, "--data-parallel-size", "-dp")))
print("共 %d 个 API server" % len(rows))
'
```

对：每个 API server 一行，按端口从小到大。例如实验室用模拟进程按 `launch_online_dp.py --dp-size 8 --tp-size 4 --dp-size-local 2 --dp-rank-start 6 --vllm-start-port 7100` 的样子起的那台 P 机器：

```
端口 7100   DP rank 6    TP 4    DP 总数 8
端口 7101   DP rank 7    TP 4    DP 总数 8
共 2 个 API server
```

- `-` 表示启动命令里没写这个参数：没写 `--port` 时 vLLM 用 8000；没写 TP 时是 1。启动参数写在配置文件里（`--config`）时，这里看不到，用 A2、A3。
- `--data-parallel-rank` 的简写是 `-dpn`。注意 `-dpr` 是另一个参数 `--data-parallel-start-rank`，不是这个实例的 DP rank。
- 启动参数里的 `--pcp-size 1` 对应 vLLM 的 `--prefill-context-parallel-size`（简写 `-pcp`，默认就是 1），表示不做 prefill 上下文并行。它对实例数、端口、DP rank 和本说明书的填法都没有影响。

**A2：从进程名看这台机器上有哪些 DP rank。** vLLM 把每个 DP 的引擎进程命名为 `VLLM::EngineCore_DP<rank>`：

```bash
ps -eo args | grep -o '[V]LLM::EngineCore_DP[0-9]*' | sort -t P -k 2 -n | uniq -c
```

对：每个 DP rank 一行，例如 `1 VLLM::EngineCore_DP6`。行数就是这台机器上的实例数。进程名来自 vLLM 源码（`vllm/v1/engine/core.py` 里的 `EngineCore_DP{dp_rank}`）；只有一个实例、不开 DP 时进程名是 `VLLM::EngineCore`，这条命令没有输出。

**A3：从 `/metrics` 看每个端口的 DP rank。** 这是面板一实际用来核对顺序的值。把 `PORTS` 换成 A1 列出的端口：

```bash
PORTS="7100 7101"; for p in $PORTS; do printf '端口 %s ' "$p"; curl -s -m 3 "http://localhost:$p/metrics" | grep -o '^vllm:[^{]*{[^}]*engine="[0-9]*"' | grep -o 'engine="[0-9]*"' | sort -u | tr '\n' ' '; echo; done
```

对：每个端口一行，例如 `端口 7100 engine="6"`，`engine` 的值就是这个 API server 的 DP rank。一行里什么都没有，说明这个端口上不是 vLLM 的 API server。

**A4：查 Mooncake master 的指标端口。** 面板一抓的是 master 的管理端口（`/metrics`），默认 9003。在监控机上执行，把地址换成这一套 master 的 IP：

curl -s -m 3 http://10.1.0.101:9003/metrics | grep -c '^master_' ; python3 -c 'import json,sys; print("glm53-1 的 master：", json.load(open(sys.argv[1])).get("mooncake_master", {}).get("address"))' /data/grafana/vllm-pd-grafana-panel1/glm53-1/prometheus/inventory.json

对：第一行是一个大于 0 的数（这个端口上有 master 的指标）；第二行是 glm53-1 的 master 地址，可以对照端口的写法。第一行是 0 时，端口不对，或这台机器上不是 master。

**vLLM 跑在容器里时：** 容器用宿主机网络（`--network host`）时，A1 的端口就是机器的端口；用端口映射（`-p`）时，以 `docker ps --format '{{.Names}} {{.Ports}}'` 里宿主机一侧的端口为准，A3 也用宿主机端口。

## 附录 B：清单文件格式

`#` 后面是注释，空行不算，字段之间用空格分开。

| 行 | 写法 | 说明 |
|---|---|---|
| 集群行 | `集群 <集群名> master=<IP>:<端口>` | 开始一套集群。集群名用 `clusters.txt` 里已经写好的，不要改 |
| 机器行 | `P <IP> [端口=…] [实例数=…] [TP=…]`，D 机器写 `D` | 属于它上面最近的集群行。IP 不带端口 |

机器行的可选项：

| 写法 | 含义 |
|---|---|
| 不写 | 用第 4 步打印的 glm53-1 同一侧的值 |
| `端口=9000` | 一个实例，端口 9000 |
| `端口=7100-7107` | 8 个实例，端口 7100 到 7107 |
| `端口=7100,7101` | 2 个实例 |
| `端口=9000 实例数=8` | 8 个实例，从 9000 起连续 8 个端口 |
| `实例数=8` | 8 个实例，从默认的第一个端口起连续 8 个 |
| `TP=4` | 这台机器上每个实例的 TP |

规则：

- 一个端口就是一个实例（一个 API server）。`端口=` 写了几个端口，`实例数=` 就要写几；只写一个端口时 `实例数=` 表示连续几个。
- 同一侧的机器、一台机器上的端口，都按 DP rank 从小到大写。第 n 个 API server（从 0 数）就是实例 `P<n>` / `D<n>`。
- 同一台机器只能出现一次：各套之间不共用机器，P 和 D 也不共用。
- 同一侧的机器 TP 不同时，`make_inventories.py` 改用部署包 README 附录 B 的写法生成清单（`api_servers`，每个 API server 一项），第 6 步的输出会写「api_servers 写法」。抓取目标和实例名不变。
- 本说明书里的示例地址都是这一组：glm53-0 的示例 P `10.1.1.1`–`10.1.1.8`、D `10.1.2.1`–`10.1.2.4`、master `10.1.0.100`；dsv41-flash-1 的示例 P `10.1.3.1`–`10.1.3.4`、D `10.1.4.1`、`10.1.4.2`、master `10.1.0.101`。

两个完整的示例见第 2 节。

**和 glm53-1 比（按 API server 个数换算，不是实测）：** 每个抓取目标的序列数只和它的种类有关，所以一套集群的抓取量大致和 API server 个数成正比。

- 5 套 dsv41-flash-N 合计 5 × 24 = 120 个 API server，glm53-1 是 72 个，换算下来约是 glm53-1 的 1.7 倍。
- glm53-0、glm53-2 按 glm53-1 的布局时，各和 glm53-1 相同。
- 7 套合计 120 + 2 × 72 = 264 个 API server，约是 glm53-1 的 3.7 倍。

**15 天的磁盘：** 每轮样本数 ÷ 15 秒 × 86,400 秒 × 15 天 × 每个样本的字节数。每个样本的字节数，Prometheus 文档给的平均值是 1–2 字节。

**实测 glm53-1（可选，只读）：** 读 glm53-1 的 Prometheus 自身指标和一次查询，再看 Docker 数据目录的剩余空间。端口 18102 是 glm53-1 的 Prometheus 主机端口。

输出 9 行。换算：

- glm53-1 已存天数 = （第 6 行 − `prometheus_tsdb_lowest_timestamp_seconds`）÷ 86,400。
- glm53-1 每天的数据量 = （`prometheus_tsdb_storage_blocks_bytes` + `prometheus_tsdb_wal_storage_size_bytes`）÷ 已存天数。
