# 接口一（采集接口 pd_diag/v1）规范

接口一由集群端的采集进程（`pd_fetcher.py`，运行在 proxy 机器上）提供，由监控机上的入库进程（`pd_ingest.py`）调用。采集进程把每个请求的诊断记录合并成一份请求文档，连同每分钟一份的状态文档，按序号写进写出队列；入库进程经本接口按序号读取，写进 ClickHouse。

本规范只固定接口的结构。当前有哪些段只经段定义接口在运行时传递，不写进本规范，也不写进任何配置文件。

同目录的文件：

| 文件 | 内容 |
|---|---|
| `request.v2.schema.json` | 请求文档（`schema` 为 `vllm_pd.request.v2`）的 JSON Schema |
| `status.v1.schema.json` | 状态文档（`schema` 为 `pd_diag.status.v1`）的 JSON Schema |
| `contract.v1.schema.json` | 段定义接口响应（`schema` 为 `pd_diag.contract.v1`）的 JSON Schema |
| `status_api.v1.schema.json` | 状态接口响应的 JSON Schema |
| `samples/` | 样本，取自实验室的运行结果，见第 7 节 |
| `SHA256SUMS` | 以上各文件的 SHA-256，发布脚本据此核对两端软件包中的副本相同 |

## 1. 接入参数

| 一方 | 参数 | 所在文件 | 说明 |
|---|---|---|---|
| 提供方 | `listen_port` | 集群端 `fetcher.json` | 采集进程监听的 TCP 端口，缺省 9300，监听所有地址 |
| 调用方 | `fetcher_url` | 监控端 `ingest.json` | `http://<proxy 机器的 IPv4 地址>:<listen_port>`，例如 `http://10.1.0.20:9300` |
| 调用方 | `interface` | 监控端 `ingest.json` | 调用方依赖的接口名称和主版本，随软件发布写为 `pd_diag/v1`，不需填写 |

接口不做身份认证，不限制来源地址。所有端点只读，只接受 `GET`；返回的内容只有请求号、时刻、token 数、各段时延和计数，不含 prompt 和输出文本。

## 2. 端点

| 端点 | 用途 | 响应类型 |
|---|---|---|
| `GET /pd_diag/v1/docs` | 增量读取接口：按序号读取写出队列里的请求文档和状态文档 | `application/x-ndjson`，每行一份文档 |
| `GET /pd_diag/v1/contract` | 段定义接口：当前段定义及其 `config_version` | `application/json`，一个对象 |
| `GET /pd_diag/v1/status` | 状态接口：接口主版本、文档的 `schema`、`config_version`、集群名和采集进程的计数 | `application/json`，一个对象 |

其他路径返回 404，响应体为 `{"error": …, "endpoints": [三个端点]}`。

### 2.1 增量读取接口

参数（查询字符串）：

| 参数 | 类型 | 缺省 | 取值 | 含义 |
|---|---|---|---|---|
| `after` | 整数 | 0 | ≥ 0 | 调用方已读到的最大序号；返回序号大于它的文档 |
| `max_bytes` | 整数 | 4194304 | 1–67108864 | 本次响应体的字节上限 |

响应：

- 状态码 200；响应体为若干行，每行一份文档（UTF-8 编码的 JSON 对象，以换行结尾），按序号递增排列。没有新文档时响应体为空。
- 单次上限：在不超过 `max_bytes` 的前提下尽量多返回；第一份文档本身超过 `max_bytes` 时仍返回这一份，保证读取能前进。
- 响应头：

| 响应头 | 含义 |
|---|---|
| `X-PD-Interface` | `pd_diag/v1` |
| `X-PD-Cluster` | 集群名 |
| `X-PD-First-Seq` | 写出队列中现存最旧一份文档的序号 |
| `X-PD-Head-Seq` | 写出队列中最新一份文档的序号 |
| `X-PD-Last-Seq` | 本次返回的最后一份文档的序号；没有返回文档时等于 `after` |

错误：`after`、`max_bytes` 不是整数或超出取值范围时返回 400，响应体为 `{"error": …}`。

### 2.2 段定义接口

无参数。响应对象的结构见 `contract.v1.schema.json`：

| 字段 | 含义 |
|---|---|
| `schema` | `pd_diag.contract.v1` |
| `interface` | `pd_diag/v1` |
| `cluster` | 集群名 |
| `config_version` | 段定义的版本：`segments.json` 的 `config_id`、`@`、文件内容 SHA-1 的前 8 位 |
| `config_id` | `segments.json` 的 `config_id` |
| `sides` | P、D 两侧在看板上的名称和总时长标签 |
| `segments` | 每段一项：代码名 `code`（路径以 `.` 连接）、所属的组 `group`、侧 `side`（`p` 或 `d`）、阶段 `phase`（`proxy`、`ttft`、`tpot`、`background`）、上级 `parent`、顺序 `order`、深度 `depth`、起始粒度 `from_level`、单位 `unit`、在请求文档中的路径 `doc_path`、在 `request_doc` 中的列名 `column`、标签 `label` 及若干标志 |

`segments.json` 修改后，采集进程在 2 秒内重新读取；`config_version` 随之改变，新写出的文档按新的段定义计算。

### 2.3 状态接口

无参数。响应对象的结构见 `status_api.v1.schema.json`，字段：

| 字段 | 含义 |
|---|---|
| `interface`、`major` | `pd_diag/v1` 和主版本 1 |
| `cluster` | 集群名 |
| `doc_schemas` | 三种文档的 `schema`：`request`、`status`、`contract` |
| `config_version` | 当前段定义的版本 |
| `head_seq`、`oldest_seq` | 写出队列中最新、最旧一份文档的序号 |
| `open_requests` | 尚未写出的请求数 |
| `sources` | 每个来源（实例、proxy worker）一项：读取位置 `read_seq`、来源的最新序号 `head_seq`、读取失败 `errors`、退避 `backoffs`、运行号变化 `run_changes`、未读出即被覆盖的记录数 `ring_overwritten_lines`、距最近一次成功读取的秒数 `last_ok_seconds`、最近的错误 `last_error`、安全点落后的秒数 `behind_seconds`、proxy worker 是否已退出 `gone` |
| `fetcher` | 与采集进程状态文档（第 4.2 节，`scope` 为 `fetcher`）相同的计数 |

调用方在启动时调用状态接口，核对 `interface` 的主版本是自己支持的版本之一，并核对集群名与库中已有数据的集群名相同；不符时不读取任何文档。

## 3. 序号、游标与去重

- **序号：** 写出队列第一次建立时，序号从当时的微秒时间戳起算，之后每写一份文档加 1。请求文档和状态文档共用这一个序号。写出队列清空重建后，新序号从重建时的微秒时间戳起算，仍大于此前所有序号。
- **游标：** 调用方的游标是库中 `request_doc`、`status_doc` 两表 `max(seq)` 的大者，不另存文件。
- **跳号：** 调用方要的序号已因写出队列达到总量上限被删除时，接口从现存最旧的一份接着返回。调用方由 `X-PD-First-Seq` 大于 `after + 1` 得知跳过的份数，计入自己的 `ingest_gap`。
- **重复：** 同一请求可能写出多份文档（迟到的记录使 `doc_version` 加 1），调用方也可能在写入后、查询游标前崩溃而重复写入。调用方按 `(cluster, request_id, doc_version)` 去重，查询时取 `doc_version` 最大的一份。
- **采集进程重启：** 从写出队列最后一份完整的行接着编号；最后一行只写了一半时截掉，这份文档在重新读取后重新写出。

## 4. 文档

每份文档是一个 JSON 对象，由 `schema` 字段区分种类。调用方按每份文档的 `schema` 分别处理；遇到不认识的 `schema` 主版本时停止读取并报错，游标不前进。文档中不认识的字段忽略。

### 4.1 请求文档（`vllm_pd.request.v2`）

一个请求一份。结构见 `request.v2.schema.json`，样本见 `samples/`。

| 字段 | 含义 |
|---|---|
| `schema`、`cluster`、`seq` | 种类、集群名、序号 |
| `doc_version` | 文档的版本：判为 `complete`、`no_proxy` 的第一份为 1，判为 `incomplete`、`evicted` 的第一份为 0，每次因迟到的记录重写加 1 |
| `closed` | 写出时的判定，见下表 |
| `request_id` | 请求号（proxy 生成，去掉 `chatcmpl-` 等前缀） |
| `client_request_id` | 客户端请求体里的 `request_id`；没有 proxy 的记录时为 `null` |
| `session_id` | 保留，当前为 `null` |
| `model` | `fetcher.json` 的 `model`，不填时为 `cluster` |
| `ts` | 请求到达的时刻（UTC，毫秒，ISO 8601）：P 的 API server 收到请求的时刻，没有 P 的记录时取 D 的 |
| `route` | `p`、`d`：处理这个请求的 P、D 实例名；`retries`：proxy 的重试次数 |
| `result` | `status`、`finish_reason`、`http_status` |
| `tokens` | `prompt`、`cached`、`output` |
| `latency_ms` | 端到端、首 token、每 token 时延，P、D 两侧的总时长和各自的官方时延；`starts_at` 为 `proxy` 或 `instance`，说明端到端时延的起点 |
| `ttft`、`tpot`、`background` | 各段：`ttft.p`、`ttft.d`、`tpot.d`、`background.p` 之下每段一个对象 `{level, ms}`，子段在 `sub` 中；`tpot.d` 之下各段另有 `per_step_ms`；`tpot.steps` 为 D 第一步之后的步数 |
| `checks` | `p_unattributed_ms`、`d_first_unattributed_ms`：总时长与第 1 级各段之和的差 |
| `recorded_level`、`diag_level` | 记录实际达到的粒度和实例设定的粒度，各分 `p`、`d` |
| `attempts` | 尝试次数（退回 P 重算时大于 1） |
| `sides` | `p`、`d`：`start` 该侧 API server 最早的开始时刻，`executions` 该侧的步数 |
| `missing` | 为空的字段的路径；判为 `incomplete` 时另列缺少的必需记录（`required: <侧> <记录>`） |

段的值为空时 `ms` 为 `null`，路径同时列在 `missing` 中。段对象的路径就是段定义接口中的 `doc_path`。

`closed` 的取值：

| 取值 | 判定 |
|---|---|
| `complete` | 有 proxy 的记录，两侧都有 `api_summary[http]` 和 `core_summary[request]`，此后 `complete_quiet_seconds` 内没有这个请求的新记录 |
| `no_proxy` | 没有 proxy 的记录：两侧都齐，或一侧齐而另一侧没有任何记录（直接发给 P 或 D 的请求），此后 `no_proxy_wait_seconds` 内没有新记录；proxy 来源关闭时，按 `complete` 的规则判定后写为 `no_proxy` |
| `incomplete` | `incomplete_idle_seconds` 内没有新记录，必需的记录仍不齐 |
| `evicted` | 在途请求超过 `max_open_requests`，最早的请求按当时的样子写出 |

proxy 的记录是可选的。proxy 没有打补丁、proxy 来源关闭、`proxy_source.socket_dir` 不存在、为空或其中的套接字无法连接时，采集进程照常读取各实例，请求按 `no_proxy` 写出；这时 proxy 的段为空，`client_request_id` 为 `null`，端到端时延从实例起算（`starts_at` 为 `instance`），状态文档中没有 `scope` 为 `proxy` 的一份（套接字目录中留有无法连接的套接字文件时，该 proxy worker 的状态文档 `gone` 为 `true`、`run_id` 为 `null`）。`no_proxy` 是正常的判定，不表示异常。

### 4.2 状态文档（`pd_diag.status.v1`）

每分钟一批，按 `scope` 分三种。结构见 `status.v1.schema.json`。计数除注明的以外都从进程启动起累计；某一时段的值为时段末减时段初。

| `scope` | 每分钟几份 | 内容 |
|---|---|---|
| `instance` | 每个实例一份 | `run_id`（API server 的运行号，重启后改变）、`host`、`config_version`、`diag_level`；`processes`：实例内每个进程一项，节点过滤器的自检计数；`ring`：实例缓冲区的上限和覆盖计数；`fetch`：采集进程读取这个实例时的计数 |
| `proxy` | 每个 proxy worker 一份 | `run_id`、`gone`；`proxy`：proxy 缓冲区的计数；`buffer_overwritten`；`fetch` |
| `fetcher` | 一份 | 采集进程自身：`config_version`、与之不符的实例 `config_mismatch`、段定义变化的累计次数 `segment_changes` 和最近 20 次 `segment_changes_recent`、在途请求数、已写出和重写的文档数、按 `closed` 分的份数、`late_records`、`late_dropped`、`log_dropped`、`log_write_errors`、写出队列和请求摘要日志的占用、Mooncake 计时的配对计数 |

`processes` 每项的计数（节点过滤器自检记录 `pd_filter_selfcheck` 的原值）：

| 计数 | 含义 |
|---|---|
| `seen`、`written`、`accumulated` | 收到的记录、写出的记录、按请求累加的记录 |
| `partials_written`、`evicted`、`inflight` | 写出的部分和、空闲淘汰的请求、在途请求 |
| `dropped`、`errors`、`config_errors`、`version_dropped`、`rank_dropped`、`no_event` | 过滤掉的记录、处理出错、配置读取出错、版本不符丢弃、非 rank 0 丢弃、没有事件名的记录 |
| `outlet_dropped_lines` | 发送队列满而丢弃的记录行 |
| `exec_missing` | 按步记录缺少执行号的次数 |
| `cand_maps`、`cand_applied`、`cand_unpaired`、`cand_evicted_full` | 候选窗口：映射的步数、取到值的步数、离开窗口时仍有请求没取到值的步数、未到保留时长即因步数上限移出的步数 |
| `acc_fallback` | 各累加规则留空的次数，键为规则名 |
| `mooncake` | 只在 pool 进程：Mooncake 计时的计数 |

过滤器在某一项不适用时不写这一项，状态文档中相应地没有这个键。

## 5. 版本规则

| 变更 | 是否升主版本 | 双方要做的事 |
|---|---|---|
| 文档新增字段、状态文档新增计数、端点新增可选参数 | 否 | 调用方不需要升级 |
| 删除字段；改变字段的含义、类型或单位；改变游标或去重规则；改变端点路径 | 是：文档改 `schema` 中的版本号，端点改路径中的版本号 | 调用方先升级到同时支持新旧两版，提供方再写出新版本；提供方全部升级后取消对旧版本的支持 |
| 段的新增、删除、改名 | 否，`config_version` 改变 | 需要显示时重新生成看板；改名等同于删除一段、新增一段 |

## 6. 调用方的要求

- 每次读取前查游标，发 `GET /pd_diag/v1/docs?after=<游标>&max_bytes=4194304`；取满 4 MiB 就接着取，取不满等 5 秒。
- 启动时和每次读到带新 `config_version` 的文档时调用段定义接口，以响应自带的 `config_version` 为键保存段定义。
- 连不上采集进程时每 5 秒重试一次，并记录连续失败的次数。

## 7. 样本

`samples/` 下的文件取自实验室的运行结果：实验室的模拟实例按节点文件格式提供记录，经采集进程写出。数值是实验室数据，不是现场流量。

| 文件 | 内容 |
|---|---|
| `request.<closed>.json` | `closed` 为 `complete`、`no_proxy`、`incomplete`、`evicted` 的请求文档各一份 |
| `request.level<1-3>.json` | 两侧粒度 1、2、3 的请求文档各一份 |
| `request.empty_fields.json` | 含空字段（`ms` 为 `null` 并列入 `missing`）的请求文档 |
| `status.<scope>.json` | `scope` 为 `instance`、`proxy`、`fetcher` 的状态文档各一份 |
| `contract.json` | 段定义接口的一次响应 |
| `status_api.json` | 状态接口的一次响应，含实例和 proxy worker 两种来源 |

## 8. 固定值

以下各值随软件发布固定，不作为配置项：

| 项 | 值 |
|---|---|
| 接口名称与主版本 | `pd_diag/v1`（端点路径前缀 `/pd_diag/v1/`） |
| 文档的 `schema` | 请求文档 `vllm_pd.request.v2`；状态文档 `pd_diag.status.v1`；段定义接口响应 `pd_diag.contract.v1` |
| 采集进程的目录 | proxy 机器上 `/data/pd-diag/fetcher/`：`fetcher.json`、`segments.json`、写出队列 `spool/`、请求摘要日志 `summary/`、游标文件 `cursor.json`、进程锁 `fetcher.lock` |
| 写出队列 | 文件 `docs.<该文件第一份文档的序号>.jsonl`，每个至多 64 MiB；每秒同步到盘一次 |
| 状态文档的间隔 | 60 秒 |
| `segments.json` 的检查间隔 | 2 秒 |
| 段定义变化的保留条数 | 状态文档中最近 20 次 |
| 时刻的格式 | UTC，毫秒，`YYYY-MM-DDTHH:MM:SS.mmmZ` |
| 段的单位 | 毫秒 |
