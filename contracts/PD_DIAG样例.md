# `[PD_DIAG]` 日志样例

本文给出一个请求在 P、D 两侧的真实 `[PD_DIAG]` 日志行，供核对记录格式时对照。记录格式本身以《记录格式约定》（[记录格式约定-glm5.3-v1.3.3.zh-CN.md](记录格式约定-glm5.3-v1.3.3.zh-CN.md)）为准；各段取哪条记录的哪个字段，以 `panel2/vllm-pd-grafana-panel2/profiles/glm53/segments.json` 为准，逐段列表见 [docs/20-面板二.md](../docs/20-面板二.md) 第 3 节。

## 1. 出处

| 项 | 值 |
|---|---|
| 来源 | T51 的 CPU 端到端验证（2026-11-19），第二遍，场景 `pd`。原始文件在 T51 P/D 传输补丁的开发仓库（不在本仓库）`cpu_e2e/results/py311/vllm030cpu_40152b2/pd/` 下的 `P.log.gz`、`D.log.gz`，环境说明在同一仓库的 `cpu_e2e/README.zh-CN.md` |
| vLLM | v0.30.0 官方 CPU wheel，打 T51 vLLM 补丁提交 `40152b2`（最终的现场补丁）；Python 3.11.10；aarch64 容器，无网络 |

## 2. 这份样例和现场的区别

- **只有补丁 01 的三种记录。** 样例里是 `api_summary`（`scope` 为 `http`、`engine_submission`、`request`）、`core_summary`（`scope` 为 `request`、`execution`）、`worker_summary`（`phase` 为 `execute`、`sample`）共 7 种。CPU 上没有 vllm-ascend，没有缓存池记录 `pool_task`、KV 传输记录 `pd_transfer_summary`，也没有 Mooncake 的 `[BatchPutTiming]` 行和 proxy 的行。
- **Worker 记录来自测试侧的模拟。** CPU 上 vLLM 用 V1 runner；现场由 vllm-ascend 补丁在 V1 runner 上加 `@pd_execution`、`@pd_sample` 两个装饰器，测试框架把同样的两个装饰器套到 CPU runner 上。设备计时没有模拟：记录里 `timing_domain` 为 `host_monotonic`，没有 `device_duration_ns`。按 glm53 段定义（只取设备时间），这些记录的 forward、sampling 为空。
- **两侧的请求号不同。** 测试用的代理不发 `X-Request-Id`，P 侧请求号是 `cmpl-8d0d0eb88d0d4cb3-0-98c0857d`，D 侧是 `cmpl-bec91a96428d6179-0-ac25817e`。两者对应同一个客户端请求，依据是测试脚本的发送顺序（两份日志里各自的第一个请求，P 侧先结束、D 侧随后开始）。面板二按 `X-Request-Id` 配对两侧，这样的请求在单请求拆解里另一侧为空（说明书 3.1）。
- **行首。** `[PD_DIAG] ` 之前是 vLLM 默认格式的控制台前缀（进程名和 pid、级别、`月-日 时:分:秒`、源文件和行号）；《记录格式约定》规定的是 `[PD_DIAG] ` 之后的 JSON。
- 这次运行按 glm53 段定义，47 段里 22 段有值（出处：上述 `cpu_e2e/README.zh-CN.md` 第 0 节结论 3）。

## 3. 脱敏

| 项 | 处理 |
|---|---|
| 主机名 | 每行 JSON 的 `"host"` 字段（原值是测试容器的主机名）换成 `"<主机名>"`；所选每一行里只有这一处出现该主机名 |
| pid | 未替换。它们是测试容器内的进程号，不含机器信息，而且嵌在 `observation_id`、`execution_id`、`engine_id`、`record_id` 等编号里，替换会破坏编号之间的对应 |
| 路径、地址、账号 | 所选行里没有文件系统路径、网络地址或账号；唯一像路径的值是 HTTP 路由 `"route":"/v1/completions"`，原样保留 |
| 其余 | 与原日志逐字节相同；替换后每行 `[PD_DIAG] ` 之后的 JSON 仍可解析（用 `python3 -I` 逐行核对） |
